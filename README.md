# Constellation

把散落的需求星點，連成一幅完整的星座。

Constellation 是一套給 AI 編碼助理用的**開發工作流**。它不是框架、不是函式庫，而是一組「規則檔＋機器閘門」：
規則檔告訴 AI 每個階段該怎麼做事，機器閘門在關鍵時刻擋下不該過的東西。裝好之後，你只要在專案裡說
「我要做某某功能」，AI 就會自己走完**訪談 → UI 定稿 → 拆票 → 實作 → 出貨**這五步，中途換一個新的
對話視窗接手也不會斷線。

## 為什麼需要它

用 AI 寫程式，最常踩的四個坑：

| 坑 | Constellation 的對策 |
|---|---|
| **需求沒問透就動手**，做到一半才發現方向錯了 | ① 訪談階段用設計樹把問題問到見底，沒問完不准動手 |
| **設計圖和成品長得不一樣**，做出來又要重畫 | ② 定稿的是一份真能跑、能點的畫面，落地是格式轉譯而不是照著圖重畫；定稿後檔案上鎖 |
| **AI 說「完成了」，其實根本沒跑過** | 每張票關閉前必須有真實執行的證據，證據帶機器簽章，手打時間戳騙不過去 |
| **換一個對話視窗，前面聊的全忘光** | 所有狀態寫進專案裡的 `.constellation/` 檔案，新視窗讀檔就接得上 |

四個設計目標，依優先序：

1. **快** — 儀式最少化，閘門只設在關鍵點，能平行的票就平行做。
2. **真** — 驗證走真實鏈路（真點擊、真打 API、真查資料庫），機器擋假完成，**AI 的嘴不算數**。
3. **可接續** — 狀態全部外部化成檔案，中斷即中斷，讀檔即接手，不靠對話記憶。
4. **雙 runtime 真共用** — 一份母本源碼，Claude Code 與 Codex 同時生效，改一次兩邊同步。

還有一條貫穿全域的自律：**工作流本身不得成為工作量**。每加一個機制之前先問——它省下的時間，有沒有
超過它消耗的時間？答案是否，就不加。本文件的「已知限制」那一節，就是這條原則的具體落實：好幾個缺口
是明知道存在、刻意選擇不補，而不是沒看到。

## 五步流程

```
① 訪談 (grill)     批次追問到問題清單見底，決議即時寫進檔案
② UI 定稿 (design)  把設計基底送上設計工具 → 它自己設計 → 調到滿意 → 拉回專案一次性轉譯落地
③ 合成拆票 (weave)  不再發問；把決議合成任務卡，垂直拆成可平行的票（含驗收條件、檔案界線）
④ 逐票實作 (build)  無依賴的票平行開工、一張張序列整合；每票內部：測試先行 → 實作 → 實跑驗證 → 關票
⑤ 出貨 (ship)      全量真鏈路驗證 ＋ 兩個互不參考的視角各審一次
```

流程會**依任務大小自動伸縮**，不是每件小事都要走完整套：

- **小流程**：③ 不拆多票，直接產一張任務卡，單線做完＋實跑驗證，再走輕量的 ⑤。
- **大流程**：完整五步。
- **要不要做 ②（UI 定稿）跟大小流程互相獨立** — 純後端／無畫面的任務直接跳過 ②，不管走大流程還小流程。

大小怎麼分、要不要 UI，由 AI 在訪談收尾時依改動範圍提議（會動幾個檔、有沒有新資料結構、跨不跨模組），
你一鍵拍板。

### ① 訪談（grill）

把要釐清的範圍建成一棵**設計樹**：每個決策都可能有前置依賴，父節點就是「答了這題才問得下去」的那一題。
所有前置都已拍板、現在就能問的題，合起來叫 **frontier**（前線）。AI 一次算出前線上有哪些題，然後
**一則訊息只問一題**依序問完；你的答案會解鎖新的子題，也可能整條子樹被剪掉（因為那些子問題根本不成立了）。

三條鐵律：

- **每題附推薦答案**，講清楚後果與代價，用白話、不用術語轟人。
- **事實不問人** — 能讀檔、跑工具、查官方文件得到的答案，AI 自己去查；只有真正需要你拍板的取捨才問你。
- **前線清空前禁止動手實作**；清空之後還要你明確點頭，才能進下一步。

為了防止「你沒想到、AI 也沒問到」的漏網之魚，訪談有**四道保險**：

1. **前線清空才算完成** — 設計樹每個分支都要走到底，不能有任何東西被默默假設。
2. **收尾盲點掃描** — 前線清空後，換一個獨立視角重掃設計樹（邊界情況、錯誤路徑、權限、資料生命週期、
   相依故障），掃到漏網就生成新題再問一輪，直到掃描零新發現。
3. **獨立盲點審** — 把落檔的決議全集交給一個**看不到訪談對話、只看檔案**的審查者（避免被討論過程的
   思維慣性污染），找矛盾、找沒定義的概念、找缺席的異常路徑、找**該問而沒人問的問題**。有發現就轉成
   新題再問，**交替迴圈直到連續一輪零新發現**。大流程必跑，小流程可省。
4. **增量重訪** — 訪談決議全部落檔，任何時候都能重開訪談：既有決議視為已拍板的節點，重算前線只補問
   新增與遺漏的部分，不會把你問過的再問一遍。

訪談收尾會寫下一份固定的決議檔，五個欄位：大小分岔／是否需要 UI／高風險標記（權限・金流・個資）／
必備模組排除／一句話任務摘要。這份檔案同時是機器可讀的「訪談已完成」標記 — **沒有它，一律回到訪談**，
免得訪談中途被打斷卻被誤判成已完成。

訪談引擎也有**獨立入口**：不必是開發任務，任何想法、任何決定都可以拿來拷問一輪。

### ② UI 定稿（design）

這一步要解決的根本問題是 **mockup 與成品不符**。做法是讓定稿物是一份**完整可執行的設計規格** —— 真能跑、
真能點的畫面，不是給人看一眼就丟的圖；落地是**一次性轉譯**（把它的檔案格式換成專案自己的元件格式），
不是看著圖重畫。這裡誠實講清楚：不能宣稱「原封落地」（格式不同，一定要轉一次），但仍遠勝重畫 ——
視覺與互動細節都被你確認過，而且有一份真的跑得起來的東西可以對照。

主線七步：

1. **把設計基底送上去** — 專案已經有能跑的畫面，就送它**真正的設計 token／可重用元件／全域 CSS／字型**
   （直接給真東西最保真，不必反推近似值）；如果是空地專案，才從內建的 **150 套品牌設計系統資產庫**
   挑一套當起點。
2. **把需求丟給它生成** — 需求描述來自訪談定版的決議。重點是**讓它自己設計**：你講你要什麼，它先做
   一版給你反應，你再一路改到它變成你的。要多個方向就用追問迭代（「再給我一版側邊欄式的」），
   **不回頭在本地手工做變體**。
3. **你在畫布上確認／調整** — 評論、語意化參數旋鈕、圖層樹編輯，多輪來回到滿意為止。
4. **拉回專案** — 直讀設計稿檔案，一併拉回 token 對照表。
5. **一次性轉譯成專案元件** — 多數語法是機械對應；真正機械化不了的只有「動態拼接的 inline style
   要拆成 class modifier」（機器分不出哪段是狀態、哪段是常數），另外 inline style 會蓋掉 `:hover`、
   假資料要換成真 API，這兩個陷阱必踩。實測 347 行設計稿轉出 467 行 JSX ＋ 492 行 CSS，行為與視覺零落差。
6. **單向門** — 轉譯完成後，**專案裡的元件程式碼即唯一真相**，設計稿降為參考資料，**不建立任何回頭
   同步機制**。要再改 UI 就走「解凍既有元件直接改程式碼」或「重跑 ② 產一份新的設計稿」。
7. **定稿即凍結** — 定稿的檔案清單寫進 `design-frozen.json`，實作期間機器閘門會攔截任何對這些檔案的
   編輯；**要改定稿 UI 必須先經你同意、解凍並記錄原因**，日誌留軌跡供出貨時核對。「討論定版的畫面被
   無聲改掉」從機制上根絕。

**用不上設計工具時的降級路徑**：判斷依據是「工具此刻在不在、通不通」，不是「跑在哪個 runtime」——
離線、額度用完、這個環境沒有這個工具、工具在但登入不通，任一成立就走降級。而且**不默默降級**：
會先白話告訴你落差在哪，包含必須誠實講的那句——「AI 自己寫幾個版本，那幾版是同一個判斷的幾種寫法，
不等於真的比較過不同方案」——然後讓你選「換到有這個服務的環境把這一步做完」，或「不換，由 AI 自己
寫畫面程式碼、用文字來回修到滿意」。選自己寫時預設**先做一版再靠迭代長出方向**，不一次攤三版。

**小工程不必問**（改一個按鈕／加一個欄位／既有設計語言下的單一元件／修 bug）——不是所有跟畫面有關的
工作都需要設計服務，直接改程式碼給你看就好。要問的是新產品、全新頁面、資訊架構重新決定、複雜操作流程。

### ③ 合成拆票（weave）

**這階段只合成，不發問。** 輸入只有訪談產出的決議與定稿的 UI，輸出是一批票。

- 決議沒覆蓋到的細節：自行做合理假設，寫進票的「決議記錄」，不停下來問（屬於小事，事後可追溯即可）。
- 若發現決議之間**真的互相打架**（不是細節缺口），代表訪談沒問透——不在這裡自己拍板，退回去請你補問一輪。

拆票時每張票都會劃定 `zone`（檔案界線）與 `blocked-by`（依賴關係），這兩個欄位決定哪些票可以同時開工。
票清單合成完會呈交給你確認；**你點頭之後才會寫入機器可讀的核准標記**，沒有這個標記就不准進實作階段。

### ④ 逐票實作（build）

每張票內部都走同一個循環，不論是不是平行：

1. **領票** — 挑一張還沒開工、依賴也都完成的票，領票當下就改狀態為進行中（不是等關票才一次改），
   讓其他視窗讀檔就知道這張正在做。
2. **測試先行** — 在驗收條件對應的接縫上先寫會失敗的測試。垂直切片：一個驗收條件對一段測試，
   不是整票功能寫完才開始實作。
3. **實作轉綠** — 讓測試通過，這條驗收條件真的實跑過了才勾起來，跑綠一條勾一條。
   - **禁止套套邏輯測試**：測試的期望值不能用跟實作一樣的算法算出來，那等於沒測。
   - **禁止用 mock 冒充真依賴**：真依賴還沒就緒就把這張票標成 blocked，不能用 mock 假裝過關。
4. **實跑驗證落證據** — 跑驗證器，把指令、結果摘要、時間寫進票的「驗證證據」欄。
   逐票驗證會**縮圈**：票裡有指定的驗證指令清單就跑那份，沒有才跑全量測試——測試量隨專案增長，
   票級恆全量會讓驗證時間越拖越長。**驗證失敗不得靠改窄清單洗綠**，該修的是程式碼。
   - **斷路器**：同一張票連續失敗 5 次就強制停下來請你拍板，不無限重試；也不准刪掉失敗計數檔硬闖。
5. **關票** — 驗證器綠燈後才能改成完成。機器閘門會檢查證據存在、夠新鮮、驗收條件全勾，不過就直接擋下。
6. **提交** — 程式改動**與票檔本身**放進同一個 commit，讓票的狀態與 git 歷史對得上。

**平行編排**：兩兩之間 `zone` 沒有交集、也沒有依賴關係的票，可以同一批開工；有依賴鏈的票會等前置票
完成後才在下一批被領走。整合則是**一張張序列**做：合併 → 跑該票驗證 → 關票 → 下一張，合併前檢查
worker 有沒有越界動到不屬於自己的檔案。平行的代價（token 加倍）會在每批開工前明講。

**遇到大事會停下來問**：驗收條件互相矛盾、要動資料結構、涉及權限／金流／個資、破壞性資料庫操作——
這些一律停下來請你拍板。小事（命名、邊界處理細節）自決，記進票的決議記錄留追溯。平行的 worker 遇到
大事就把該票標 blocked 留言，其餘票繼續跑，主線收集後統一問你。

### ⑤ 出貨（ship）

**步驟 1：全量真鏈路驗證。** 一次跑齊所有 journey 測試加上完整回歸，不是只挑被改到的部分；一樣走真點擊、
真 API、真查資料庫。全量證據集中寫進一份 `ship-evidence.md`，帶簽章。

如果全量跑出紅燈——**全量只當書擋，不當除錯迴圈**。一次紅燈的全量跑完，手上就是完整的壞掉清單；
修復期間一律用秒級迴圈驗單點（只重跑上次失敗的、或指名那幾個檔案），修一條驗一條，
**不得每修一個問題就重跑一次全量**（全量動輒數十分鐘，N 個問題會付 N 次全價；書擋節奏最壞只付頭尾兩次）。
全部單點轉綠後，回來重跑一次完整全量拿正式證據——**不得沿用上次的綠燈、跳過已經綠的套件**，因為為了
修 A 而動的程式碼可能弄壞 B，最終證據必須來自同一次完整全綠。

**步驟 2：獨立兩軸審查。** 另開乾淨的上下文審查，不沿用實作期的對話記憶（避免「這是我剛寫的，
看起來沒問題」這種確認偏誤）。兩軸**平行跑、分開報告、禁止合併排名**——這兩軸問的問題本質不同，
硬湊成一個總分沒有意義：

- **Standards 軸**：只看程式碼品質。優先套用這個專案自己既有的規範（lint 設定、既有 style、命名慣例）；
  沒覆蓋到的地方才退回通用的 code smell 當基準線——基準線是判斷用的參考，不是見到就一定要改的鐵律。
- **Spec 軸**：逐票對照。把每張票的驗收條件一條條拿出來核對實作有沒有真的做到，不管程式碼好不好看。
  另外核對凍結名單的日誌：每一筆解凍都應該有對應的同意脈絡可查，查不到的列為阻擋級發現。

**第三軸（條件觸發）— security 紅軍**：訪談收尾標記為高風險（涉權限／金流／個資）時自動加開，
用攻擊者視角**實測**攻擊面（越權存取、參數竄改、注入、金額運算邊界、個資外洩路徑），不是看程式碼推測——
能實際打 API／操作 UI 重現的才算數。一般任務不加開，平時速度不變：**審查跟著風險走，不跟著流程走。**

發現分**阻擋級**（修完才出貨）與**建議級**。阻擋級修完之後，除了受影響範圍要複驗綠燈，還要**針對該發現
複審**確認修法成立，但不重跑全量審查。

**步驟 3：歸檔。** 出貨完成就把本輪的票、訪談收尾決議、出貨證據、凍結名單移進 `archive/<日期>-<摘要>/`，
下一輪任務從乾淨狀態開始，新舊輪不混淆。

## 狀態存在哪裡

每個使用 Constellation 的專案，會在自己的儲存庫裡開一個 `.constellation/` 目錄，分兩軌：

```
.constellation/
├── tickets/T-NNN-<slug>.md   # 工作軌：一票一個 markdown 檔
├── CONTEXT.md                # 知識軌：專案領域詞彙表
├── decisions/NNN-slug.md     # 知識軌：極簡決策記錄
├── config.json               # 驗證指令設定 ＋ 票清單核准標記
├── design-frozen.json        # 定稿 UI 的凍結名單與解凍日誌
├── ship-evidence.md          # 出貨階段全量驗證的簽章證據
└── archive/<日期>-<摘要>/     # 出貨後的歷史歸檔
```

**票長這樣**：

```markdown
# T-003 登入限流
status: open | in-progress | blocked | done
blocked-by: T-001                  # 依賴關係，可留空
zone: src/auth/**, tests/auth/**   # 檔案界線（平行時互斥用）

## 目標（行為契約，禁寫實作內部路徑／程式碼片段）
## 驗收條件（合成階段寫定，逐條可勾）
- [ ] ...實跑可驗證的條件...
## 決議記錄（實作期小事自決落此，可追溯）
## 驗證指令（可選；票級縮圈清單，省略則跑全量）
## 驗證證據（關票時由驗證器寫入：指令＋結果摘要＋時間）
```

票名用**人話**取（「登入限流」，不是「Ticket 3」），對話裡也一律用名字指稱，裸編號只留給檔名跟
`blocked-by` 這種機器可讀欄位。

**知識軌的兩份檔案都刻意保持極簡**：
- `CONTEXT.md` 只收這個專案特有的詞彙（通用程式概念不收），每個詞 1～2 句；同義詞選一個定案，其餘標為避用。
- `decisions/` 的決策記錄每則 1～3 句（背景＋決定＋原因），而且**三個條件同時成立才寫**：難以逆轉 ＋
  沒背景會讓人驚訝 ＋ 真的經過權衡。過時的用 `superseded by NNN` 標記，不刪除。

**接續機制**：新的對話視窗一開場，閘門就會自動注入「有哪些票、各自什麼狀態、進行中的做到哪」。
中斷即中斷，讀檔即接手。

## 機器閘門：五件組

規則靠紀律，紀律靠閘門兜底。五個閘門全部小而專，**只在關鍵事件觸發，平時零開銷**：

| # | 閘門 | 觸發時機 | 它做什麼 |
|---|---|---|---|
| 1 | **git 守門** | hook | 擋下破壞性 git 操作、以及未經確認就開／切分支 |
| 2 | **commit 守門** | hook ＋ git pre-commit | commit 前掃描機密與垃圾產物 |
| 3 | **session 開場注入** | hook | 從 `.constellation/` 重建現況，注入到新視窗的開場 |
| 4 | **驗證器** | 指令 | 實跑驗證（分逐票／出貨兩級），通過的證據帶簽章寫進票 |
| 5 | **關票刷卡機** | hook | 票要標完成時，機器驗簽章、驗新鮮度、驗收條件要全勾；兼任定稿 UI 的凍結守衛 |

幾個關鍵設計：

- **閘門 2 有兩條呼叫路徑、同一套判定**：一條攔 AI 發起的 commit，另一條是 git 原生的 pre-commit
  （由開場自動冪等安裝），兜住你自己在終端機手打、或子行程／npm script 發起的 commit。機密一旦進了
  git 歷史就不可逆、而且不會自我暴露，所以這層值得雙保險。
- **簽章讓「機器擋假完成」真正成立**：驗證器用一把只存在本機、不進 git 的密鑰簽章（簽章綁定該儲存庫，
  防跨專案重放），刷卡機驗簽——**手填時間戳過不了關**。閘門 2 另外做一道稽核：commit 時被標成完成的票
  必須帶著通過驗簽的證據，堵住「用 shell 指令繞過刷卡機改檔」這條旁門。
- **驗證器內建斷路器**：同一個目標連續 5 次失敗就強制停下請你拍板，不會無限重試。
- **被閘門 2 擋下驗證垃圾時**，有一支清理工具可以收拾：預設先列出要刪什麼（dry-run），加 `--apply`
  才真的刪。它單向引用閘門 2 的白名單，所以「被擋的」和「被清的」永遠是同一套標準。風險分兩級：
  絕對垃圾（log／產物目錄／暫存檔）不論有沒有被 git 追蹤都清；截圖與錄影只清 git 沒追蹤過的，
  已經 commit 的資產一律不碰。**它是工具不是閘門**——沒有它照樣擋得住，只是要自己手動收拾。
- **git 守門的逃生口**：真的需要繞過時，設環境變數 `CONSTELLATION_GIT_OK=1`。

除這五件之外**不加新硬閘**，其餘一切靠規則檔的紀律——要加閘門必須先回頭修訂設計藍圖。

## 驗證怎麼算數

**完成 = 實跑綠燈，不是程式碼看起來對。** 讀完程式碼覺得邏輯應該沒問題，不算驗證通過。
每一條驗收條件都要有一次真實執行留下的證據，才准打勾。

依產出物型別走真鏈路：

| 涉及 | 怎麼驗 | 禁止 |
|---|---|---|
| UI | 用瀏覽器自動化工具**真點擊**，跑過使用者實際會走的路徑 | 讀元件程式碼推斷「應該會動」 |
| API | **真打**進執行中的服務，看實際 status／body | 讀 route handler 推斷回應長相 |
| 資料 | **真查資料庫**，直接讀資料表 | 讀 migration／model 檔推斷資料有沒有寫進去 |

三者都涉及時（多數功能票都是）——三段全跑，不是挑一段當代表。

涉及資料的票固定走這條四段鏈：

```
假資料 → 真 create API（seed）→ 真資料庫（落地）→ UI 操作／真 API 呼叫 → 真資料庫讀回（核對最終狀態）
```

假資料只用在「餵給誰」這一步，之後每一步都是真依賴：不能自己寫 SQL insert 繞過 create API
（繞過去就測不到 API 層的驗證邏輯了），也不能用 mock 代替最後那次讀回。

**驗證分兩級**：逐票級跑票內指定的縮圈清單（沒指定就跑全量測試）加上該票驗收條件的實跑檢查；
全量 journey 與完整回歸留到出貨一次跑齊。

## 遇到 bug 與衝突

工作流另外附兩份 playbook，讓 AI 在特殊情境走對節奏：

- **除錯迴圈** — 除錯是跟開發新功能不同的任務型態。核心信念是：**先建立一個可靠的紅綠回饋迴圈，
  才有資格開始排查**。「還沒讓 bug 重現過就一頭栽進去讀程式碼、腦補出一套理論」正是頭號失敗模式。
  playbook 列了十種建迴圈的手法（失敗測試 → HTTP 直打 → CLI diff → 無頭瀏覽器 → 重放 trace →
  拋棄式腳本 → fuzz → 二分 → 差分 → 人工腳本），找到第一個能滿足完成判準的就停，不用往後找更花俏的。
- **合併衝突** — 立場是**永遠解決，絕不 `--abort`**。衝突擺著不會消失，abort 只是把它原封不動丟給未來，
  而且已經做過的追溯判斷全部作廢。動手前先追溯兩邊改動各自想達成什麼（commit 訊息、原始票、
  `git blame`），再決定怎麼合；真的卡住就停下來問人要背景或裁決，不是退回 abort 逃走。

## 安裝

需求：Windows、Node.js、PowerShell。跑一次：

```powershell
./install.ps1
```

它做五件事：

1. **為每個 skill 各建三條 junction**（目前是總控與獨立訪談兩個 skill），分別接到 Claude Code 與 Codex
   的使用者層 skill 路徑。**三邊 runtime 讀的是同一份實體檔案，不是各自複製一份**——改母本任何一個
   規則檔，兩邊立刻同步生效，不會有版本漂移。Windows junction 免管理員權限。
2. **掛上兩邊的 hooks**。閘門的 Node 腳本本體只有一份、兩邊共用；觸發設定分兩檔維護
   （`hooks.claude.json` 與 `hooks.codex.json`），因為 matcher 有差異。**寫入設定不等於生效**：
   Codex 端還要你自己在 Codex 裡跑一次 `/hooks` 審閱並信任這些 hook，設定才會真的啟用——
   安裝的對賬步驟只會提醒你這件事，實際執行要你手動做。
3. **生成簽章密鑰**，放在你的家目錄（不進 git、跨專案共用同一把）。已存在就不覆蓋，重跑安裝不會讓
   舊簽章失效。
4. **檢查 Codex 端的 hooks 功能有沒有開**。抓不到 codex 指令或偵測不到這個功能時只提示、不中止安裝。
5. **對賬檢查**：確認 junction 有沒有指到正確位置、兩邊 hooks 有沒有都掛上，避免「裝了但沒生效」。

## 雙 runtime 共用

Claude Code 與 Codex 的 skill 格式核心相容（同樣的 frontmatter 必填欄位），hooks 事件名幾乎一一對應、
schema 同構（只差存放位置）。所以架構是**單源母本 ＋ junction 雙掛載 ＋ 觸發層各自適配**：

- 一份 `SKILL.md` 主體兩邊通用，另加一個只有顯示名稱與簡述、不含邏輯的 Codex 外觀層檔案。
- 閘門腳本本體一份共用，觸發設定分兩檔（Codex 端的 matcher 要多涵蓋它原生的編輯工具）。
- 工作狀態天然共通：票與詞彙表活在專案的 `.constellation/` 裡，哪一邊接手都讀同一份。

**缺工具時紀律不變、形式退化**：

| Claude Code 端 | Codex 端等效 |
|---|---|
| 彈窗提問 | 文字批次問答（同一套前線規則，一則訊息一題） |
| Workflow 票平行編排 | 序列逐票做，不平行 |
| 設計工具畫布 | **不按 runtime 品牌判斷**——看工具此刻在不在、通不通。確認用不上時先告知落差，再讓你選「換環境做完這一步」或「不換、AI 自己寫畫面程式碼來回修」 |

實務分工建議：訪談與 UI 定稿**傾向**在工具較齊的那一端做，另一端當第二實作／獨立審查環境。
兩點限定：① 判斷依據永遠是**工具此刻在不在**，不是環境的品牌——工具齊的那端離線或額度用完照樣走降級；
② **小工程不必為此換環境**，改一個按鈕、加一個欄位、修個 bug，直接在手上這個環境改給你看就好。

## 已知限制

以下缺口經對抗審查確認存在，但依「審查跟著風險走／工作流不得成為工作量」原則**刻意不補機制**，
白紙黑字揭露：

- **未達門檻的訪談答案不落檔**，中斷重訪時可能重問——這是設計如此，為的是避免訪談狀態檔膨脹。
- **同一次編輯裡「改成完成＋刪掉證據」的複合操作**理論上騙得過刷卡機的現檔檢查——由 commit 守門的
  稽核在提交時兜底。
- **驗證通過後 24 小時內把程式碼改壞，仍可關票**——改壞的程式碼會在出貨全量驗證時爆出來（自我暴露型），
  不為它加即時防護。
- **安裝腳本非交易式**（中途失敗可能半完成），多份 clone 的場景卸載可能誤拔——單人單機低頻情境，
  有備份與重跑冪等即可。
- **不建立逐條驗收條件的機器追蹤體系**——驗收品質由「關票須全勾＋出貨 Spec 軸逐票對照」把關。
- **設計工具的參數旋鈕落地時必然流失**：畫布上能轉的那幾顆旋鈕，落地後不會變成專案裡可切換的設定，
  只會落成一組固定的預設值——要保留哪幾個當真的 props，轉譯時自己判斷並寫進定稿記錄。
- **轉譯是單向門，設計稿與專案程式碼之後各走各的**：之後在畫布上再改設計稿，改動不會流回專案。
  這是刻意的——設計稿第二次改動時，轉換器的輸出會覆蓋手工命名的 class 樹與 modifier 結構，
  第二次以後比第一次更貴，雙向同步的維護成本遠超它省下的時間。
- **UI 定稿那一步的檔案形狀規則是從工具行為反推的**（哨兵檔、入口檔名優先序、註標慣例），
  **工具改版就可能整批失效**。屆時的處理是**重新實測一輪**定位是哪一層不認，不是硬撐或猜著改。
- **「另一端到底能不能用設計工具」尚未實測，所以條文不賭答案**：正確答案是「未經驗證的不確定」，
  不是「已知不行」。因此條文不寫死哪邊有、哪邊沒有，改成每次進 ② 當場確認一次——用不上就自然走降級，
  哪天真的掛上且登入走得通，同一條條文自然走主線，不必改規則。**不為這個不確定加任何探測機制或
  相容性清單**，也**刻意不把任何未實測的替代服務寫進條文**——寧可少一條路，也不寫一條沒人驗過、
  照著走會撞牆的路。
- **上一輪定稿的畫面，在下一輪失去閘門層的機器保護**：凍結名單隨輪歸檔，下一輪從空名單開始。
  退而靠拆票時劃 zone（不把那些檔案排進本輪的票）與出貨 Spec 軸逐票對照兜住；真要繼續保護，
  就在本輪定稿時把它們一起寫進新名單。換來的是「凍結名單與票同生命週期」——跨輪累積的解凍日誌會讓
  下一輪審查查不到已歸檔的同意脈絡而誤報阻擋級發現，那個假警報比這個缺口更常真的擋住出貨。

## DESIGN.md 是憲法

本專案的一切實作以 `DESIGN.md` 為唯一依據。任何實作細節與它有出入時，以 `DESIGN.md` 為準；
真的需要偏離，先回頭修訂 `DESIGN.md` 並經使用者核准，不得自行擴充範圍。
