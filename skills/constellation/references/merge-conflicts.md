# 合併衝突處理

> 改寫自 resolving-merge-conflicts 精髓，貼合 Constellation。適用時機：build 階段序列整合合併 worker
> 改動時撞到真衝突（不是 zone 劃分疏漏那種可以退回重做的情況，是同一段程式碼被兩邊都動到、git 標出
> 重疊 hunk），或任何時候跑 rebase 撞到衝突。

## 立場：永遠解決，絕不 `--abort`

衝突擺著不解決，問題不會消失——`--abort` 只是把它原封不動地丟回未來（不管是未來的自己還是別人），
而且屆時已經做過的追溯判斷全部作廢，等於白工。**每個衝突都要解到底**；真的卡住時該做的是停下來問
使用者要背景或裁決，不是退回 `--abort` 逃走。

## ① 動手前先追溯兩邊原始意圖

看到衝突 hunk 的當下，先搞懂「這兩段改動各自想達成什麼」，再決定怎麼合——不是憑 hunk 表面文字猜。
追溯來源：

- **commit 訊息**：`git log` 兩條分支各自的紀錄，尤其衝突那段程式碼最近幾次改動的訊息。
- **原始票**：這段程式碼屬於哪張票，回去讀那張票的「目標」與「決議記錄」，搞懂當初為什麼這樣寫。
- 沒有票可查（改動來自票產生範圍之外的既有程式碼）時，`git blame` 配對應的 commit 訊息一樣是
  原始意圖的來源。

先追溯清楚，再動手改衝突段落——順序反過來（先憑感覺挑一邊、事後才補理由）容易把兩邊真正想做的事
弄擰。

## ② 逐 hunk 解決：盡量保留雙方意圖

多數衝突其實是 diff 演算法標記重疊，兩邊改的是不同的東西——這種直接兩者都留，不要因為 git 標了
衝突記號就順手刪掉一邊。

真的兩邊互斥、留一個就得丟一個時：

- 選**符合這次 merge 目標**的那邊——在 Constellation 序列整合語境下，「這次 merge 目標」就是正在
  整合的那張票的驗收條件；如果被犧牲的另一邊改動屬於別的票，確認那張票是否已經知道這件事，沒有的話
  補一句提醒，不要悶著頭讓它憑空消失。
- 在票的「決議記錄」（或 commit 訊息）寫一句**為什麼選這邊、丟掉的是什麼**——這是可追溯的取捨，
  不是無聲刪掉。
- **絕不憑空發明新行為**：手上只有兩個版本可選（或兩者都留），不創造一個誰都沒寫過的「和稀泥」邏輯
  去迴避取捨——那等於引入一段沒人審過、沒人測過的程式碼，比選錯一邊風險更高。

## ③ 解完後的健康檢查（順序固定）

```
typecheck → test → format
```

合併最容易打壞的是型別與 import（兩邊各自加減了引用），抓型別成本最低、先跑；測試比較花時間，放
中間；format 不影響邏輯正確性，留到最後收尾——不要把順序反過來，在還沒抓到型別錯誤前就先跑貴的
步驟。三關都過，這次合併才算真的解完，不是 hunk 標記消失就結束。

## ④ rebase 模式：一路 continue 到全部完成

rebase 撞衝突是一連串、不是一次性的。解一個 `git rebase --continue` 一個，同一套「追溯意圖 →
保留雙方意圖 → 健康檢查」節奏套用在每一個衝突上；解到一半覺得麻煩就 `--abort` 回去重來，等於讓
已經做完的追溯判斷全部作廢，而且 rebase 本身不會因為 abort 就消失——大概率還是得重新面對同一批
衝突，純粹白做。真的卡住（需要的背景或裁決超出自己能判斷的範圍）才是叫使用者來仲裁的時機，不是
拿 `--abort` 當退路。
