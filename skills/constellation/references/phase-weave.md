# Phase ③ 合成拆票（weave）

一句話：這階段只合成、不發問——把 grill／design 定案的決議轉成可平行、可驗證的票。

## 進場 / 離場

- **進場條件**：先讀 `decisions/grill-close.md`（grill 收尾時寫下的固定決議檔，記著大小流程、是否需要 UI、高風險標記、必備模組排除、一句話任務摘要五欄），確認 grill 的 frontier 已清空、使用者已確認決議。**大流程時該檔檔尾還要有「盲點審：已收斂（第 N 輪）」這一行**（使用者喊停時是「盲點審：使用者喊停（第 N 輪）」，效力相同）——沒有代表獨立盲點審還沒跑完，先 Read 本檔同目錄的 `phase-grill.md` 照「完整性四保險」第 3 點接回，收斂後才進場合成（小流程可省略盲點審，不看這一行）。若該檔記著**需要 UI**（值是 `是（架構有得選）` 或 `是（照既有架構做）`，兩者都算需要，都得先有定稿），但 `decisions/` 底下還沒有 design 定稿的決議記錄（本檔同目錄的 `phase-design.md` 收尾寫的那一筆：用了哪一套設計系統當基底、需求是怎麼描述給 Claude Design 的、生成了幾個方向、使用者選了哪一版、在 canvas 上調了什麼、轉譯成專案元件時做了哪些判斷）→ 代表 UI 還沒定稿，先 Read 本檔同目錄的 `phase-design.md` 轉交過去做 UI 定稿，定稿完成後再回到本階段接手。

  **⚠ 判定「UI 已定稿」要過機器三驗，不是只看有沒有那筆定稿記錄**（案例見決議 017——舊版只驗過第①條，放行過「定稿記錄寫得很完整、畫面根本沒落地」的任務）：
  1. `decisions/` 有 design 定稿記錄，且那筆記錄裡有「逐區塊元件清單」，以及對應的拍板紀錄——**記錄裡含下列其一（哪一種由記錄自己註明，weave 不必判斷當時工具在不在）**：**A.** Artifact 連結＋逐互動結果；**B.** 使用者拍板回覆原文（`phase-design.md` 步驟 7 的必記項）；
  2. `.constellation/design-frozen.json` 存在，且 `frozen` 陣列**非空**；
  3. `frozen` 裡**每一個路徑都真的存在於 repo**（逐一確認檔案在不在，不是看字串長得像不像）。

  **任一條不成立就是 UI 沒定稿**，轉交 `phase-design.md` 補做，並把「哪一條沒過」明確講給使用者聽，不要含糊說「UI 還沒好」。這三條是純檔案存在性與內容檢查，**兩個 runtime 都做得到，不因 runtime 而異**（`tickets/` 有票之後，開場哨兵才會接手再驗一次，見母本 §5 閘門 3——weave 剛進場、票還沒落地時哨兵不會響，這三驗仍是這裡要親自做的）。

  **反過來，不得因為下列理由誤判成「沒定稿」**——「照既有架構做」那條路徑本來就只生成一版，那筆記錄會寫成「一版——照既有架構做…」，這樣一樣算已定稿；這次沒用上 Claude Design（不論什麼原因）而由執行端自己寫畫面的那筆記錄，會寫成「這次沒用上 Claude Design、原因是什麼、使用者選了哪條路」，同樣算已定稿。不能因為看不到「生成了幾個方向」就判定 UI 沒定稿、又把任務轉回 design，那會轉個沒完。若不需要 UI，或 UI 已定稿完成，才直接進場合成拆票。**進場時一併讀 `.constellation/decisions/engineering-defaults.md`（工程預設清單，若存在）**——核准票清單前要核對這份清單，見下方「完成後：呈交票清單摘要」。
- **離場條件**：票（或小流程的單一任務卡）連同 `zone`／`blocked-by` 都已落檔、`.constellation/config.json` 就緒，且 `"approved": true` 已寫入——大流程要等使用者對票清單摘要點頭確認才寫入，小流程摘要給使用者看到後直接寫入、不必等回覆（細節見下面「完成後：呈交票清單摘要」）；本輪 `.constellation/` 產物與定稿改動已本機 commit（不推送，細節同下）→ 交棒給本檔同目錄的 `phase-build.md`。

## 本階段唯一動作：合成，不發問

本階段開始後，禁止再對使用者開新題。輸入只有 `CONTEXT.md`、`decisions/*.md`（grill 產出）與定稿 UI（design 產出，若有）。

- 決議沒覆蓋到的細節：自行做合理假設，寫進對應票的「決議記錄」，不停下來問——這屬於「小事」（出處：母本 DESIGN.md §8，部署後 runtime 不需讀取），事後可追溯即可。
- 若合成過程中發現決議之間互相矛盾（不是細節缺口，是真的打架），代表 grill 沒問透。這種情況不在 weave 裡面自己拍板，退回去用 AskUserQuestion 彈窗告知使用者、把矛盾點講清楚，請使用者補問一輪 `/grill` 再回來合成。

## 大小流程判斷（沿用 grill/design 定案的分岔）

- **大流程**：完整拆票，產出多張票。
- **小流程**：不拆票，改產一張「單一任務卡」——仍套用票模板，但沒有 zone 衝突要處理，`zone` 直接寫這次預計觸及的檔案清單，也沒有 `blocked-by`。落檔後直接進 build，單線程做完＋實跑驗證。

## `next-round/` 的收尾（併入、放棄、流程外做掉）

讀 `decisions/grill-close.md` 檔尾的「下輪待辦」狀態行——`下輪待辦：併入 T-xxx、T-yyy；放棄 T-zzz`（見 `phase-grill.md`「訪談收尾」，這是狀態註記、不是「一句話任務摘要」的一部分，也不靠記得彈窗裡打過什麼字）。「併入」列的票 `git mv` 進 `tickets/`，**票號不變**（沿用既有編號，不重新分配）。搬進來後不是原樣照抄：`zone` 與驗收條件照下面「拆票規則」重新核對一次——票是上一輪留下的，這一輪的程式碼可能已經變了，內容要跟上現況，不是搬過來就算數。沒有這一行、或行裡沒有「併入」半句，這一步略過。

「放棄」列的票，以及某張票後來被用流程外做掉（決議或 `HISTORY.md` 那一行查得到對應的流程外落檔，見決議 027、032）——這兩種都不進 `tickets/`：把票 `git mv` 到 `.constellation/archive/next-round-closed/`，在對應的決議記錄補一句原因（放棄或已用流程外解決）。`next-round/` 裡剩下沒被併入、也沒被放棄的票原樣留著，等下一輪再問，不要因為這次沒選中就順手清掉。

**這張票還沒進過 git（例如上一輪 build 期才剛開、還沒 commit）時，`git mv` 會失敗（exit 128，not under version control）**——改用一般的檔案搬移（先搬檔案，再 `git add` 新位置），不要因為 `git mv` 報錯就中止或跳過這張票。

**`next-round/` 裡的票不驗、不關**：要做，先經上面這步搬進 `tickets/`——關票刷卡機認的範圍是 `tickets/`，留在 `next-round/` 的票就地改成 `status: done` 也拿不到驗證證據、過不了關，不算真的關掉。

**搬票要在合成其餘新票之前一次做完，不要分兩段**：換 session 若正好卡在「併入票已搬、新拆的票還沒落檔」或反過來「新票已落檔、併入票還沒搬」中間，`.constellation/tickets/` 這時是不完整的清單。寫入 `"approved": true` 之前，回頭核對「下輪待辦」狀態行列出的每一張併入票是否都已經在 `tickets/` 底下——缺一張就代表這步還沒做完，不能核准；核准前呈交使用者看的票清單摘要，同樣要包含這些併入票，不能只列這輪新拆的。

小流程有併入票時，這些票各自獨立、不併進單一任務卡；輕量⑤（見本檔同目錄 `phase-ship.md`）的驗證範圍要涵蓋這些併入票的驗收條件，不能只驗任務卡本身那幾條。

## 拆票規則

票的欄位格式套用本檔同目錄的 `ticket-template.md`，這裡不重複定義格式，只講怎麼填：

- **切法**：每張票是一個能單獨跑通驗證的行為單元（垂直切片），不是「拆前端/拆後端」那種技術層切法。
- **最小經濟尺寸**：每張票都有固定成本（runner 驗證、證據、關票、地圖維護、commit），拆細必須換得到平行度或獨立驗收價值——沒有實際平行收益、也沒有獨立驗收價值的相鄰行為，優先合併成同一張票（同 zone、共用測試 setup 的尤其該合），不要為了「可以平行」把票拆到固定成本比工錢還貴（決議 012）。
- **前置重構（鋪路票）**：合成時順手判斷「有沒有一步便宜的前置整理，能讓後面幾張票都變簡單」（先讓改動變容易，再做那個容易的改動）——有就開成一張票排依賴鏈最前；沒有就不硬找，**以本次改動受益為限**，不藉此順手美化無關程式。
- **目標**：寫行為契約，不寫實作內部路徑或程式碼片段——這樣即使實作方式後來變了，票本身還站得住。
- **驗收條件**：從決議（與定稿 UI，若有）逐條轉譯成可勾選、可實跑驗證的條件。每條動筆前先問自己「跑什麼指令、點什麼畫面，能驗證它」，答不出來就代表這條寫得太抽象，要拆得更具體。
- **⚠ 畫面的驗收條件以「定稿記錄的逐區塊元件清單」為分母，逐區塊寫**：zone 落在定稿檔案上的票，清單裡的每個區塊都要有對應的驗收條件；對不到的要明確標「本票不涵蓋，由 T-XXX 承接」，不能默默跳過。
  **並且禁止一種寫法**：**不得用「與 T-XXX 的行為一致」「內容與 API 行為一致」這類句子涵蓋畫面**——這句話寫下的那一刻，畫面版面就沒有人負責了（案例見決議 017）。**「行為一致」只能用來描述資料與邏輯，畫面一律逐區塊寫。**
- **⚠ 量級門檻（`grill-close.md` 高風險標記含「大量資料」時）**：會讀寫大表、或資料量會隨時間拉長而變大的票，驗收條件必須包含可實跑量測的門檻「在 N 筆下 < X 秒」——N、X 直接抄訪談時「大量資料」那三題的答案（現在幾筆、一年後幾筆、多久算可接受），不是憑感覺抓；並註明測試要用接近 N 的資料量造測試資料，不能拿小資料集矇混過關。
- **zone（可選）**：這張票預期觸及的檔案 glob（例如 `src/auth/**, tests/auth/**`），填了只供整合時檢查越界，不用來判斷誰能平行（見下面「zone 與平行」）。
- **blocked-by**：這張票要等哪張票的產出先落地（共用型別、資料庫 schema、共用元件）才能開工，就填哪張。
- **exclusive（可選，DB 隔離不了才標）**：資料隔離規則、平行紅燈重跑、`exclusive` 的「單獨時段」怎麼運作，見本檔同目錄 `phase-build.md`「保護二」與 `verification-playbook.md`「測試資料衛生」，這裡不重複；只有本質上隔離不了的操作（套 migration／改 schema、整庫快照型資料保險、量級壓測）才標 `exclusive:`（格式見 `ticket-template.md`）。
- **起站埠**：這張票的驗證需要起本地 server 時，weave 逐票指定一個埠號、寫進票「驗證指令」清單之前的說明文字供 worker 照用（格式見 `ticket-template.md`）；埠號怎麼傳進測試框架見 `verification-playbook.md`「測試資料衛生」，這裡不重複；瀏覽器驗證改用測試執行器自己開的瀏覽器，不搶共用分頁。
- **必備模組對賬（web 系統）**：拆完票後對照本檔同目錄 `user-defaults.md` 的必備四模組
  （使用者管理／角色管理／權限管理／使用紀錄）——每個模組都要有對應的票或明確併入某張票的
  驗收條件；使用者當次明示不要的，grill-close.md 應有記錄才可省略，不得默默漏掉。

## zone 與平行

- 票要不要平行，不再由 `zone` 重不重疊決定——平行預設走 worktree（每張票各自在獨立工作樹動工，檔案系統天生互不干擾，見本檔同目錄的 `phase-build.md`「平行編排」）。
- `zone` 欄改為可選：填了不影響能不能平行，只在 build 階段整合時用來檢查這張票有沒有動到宣告範圍外的檔案，越界即退回重做或人工介入；不填就略過這道檢查。
- 真正決定順序的是 `blocked-by`：這張票要等哪張票的產出先落地才能開工，就填哪張；沒有依賴關係的票各自進獨立工作樹平行做，不必等 zone 不重疊。
- 拆票時優先把「共用基礎」（型別定義、schema、共用元件）獨立成一張票，用 `blocked-by` 排在依賴鏈最前面——這張做完之後，依賴它的票才能開工，後面能平行的票也才會變多。

## 寬改動例外：expand–contract 三段式

單一機械改動、爆炸半徑跨大半 repo 的任務（rename 資料表欄位、共用型別改形、全域 API 簽名變更）——垂直切片會讓大量 worktree 同時碰同一批檔案、合併時全面互撞，沒有一張能獨立轉綠，這型任務**不硬套垂直切片**，改走三段式：

1. **expand（一張票）**：新形態與舊形態並存，不動任何既有呼叫端——這張票落地後系統行為不變。決議記錄註明「舊形態存活至 contract 票」，防止中途被當死 code 順手清掉。
2. **migrate（多張票）**：按爆炸半徑分批（每個模組／目錄一批）把呼叫端換成新形態；每批一張票、各自 `blocked-by` expand 票。因為舊形態還在，每批都能獨立綠燈過刷卡機；批與批之間沒有 `blocked-by` 依賴時照常平行。
3. **contract（一張票）**：全 repo 確認零殘留（grep 舊形態名）後刪掉舊形態；`blocked-by` 全部 migrate 票。

批次真的無法獨綠（連並存都做不到）時退一步：各批共用一條整合分支、最後加一張 integrate-and-verify 票統一驗證——綠燈只在那張票承諾。

## 每票「驗證指令」縮圈（建議寫，抓不準就省略）

拆票時順手為每張票寫「## 驗證指令」section（格式與逐欄規則見本檔同目錄的 `ticket-template.md`；標題必須剛好是「## 驗證指令」，標題後不要加括號說明或任何後綴，否則 runner 不認、整張票退回跑全量）：

- **動機**：`commands.test` 是全量快速套件，測試量隨輪持續增長，票級全量重跑會讓驗證時間隨專案越來越久——縮圈把票級成本鎖在「這張票的影響面」，不再付全專案累積測試量的錢。
- **怎麼抓**：全域靜態檢查（typecheck／lint）照抄保留＋依票的 zone 與行為影響面挑測試子集（用測試框架的目錄／pattern 過濾，例如 `pnpm test:unit tests/auth`），寧寬勿窄。**不限單元測試**——整合／db 測試同樣照領域子集納入（例如 `pnpm exec playwright test --project=db tests/callcenter`），讓 db 重的票在票級就驗到自己領域的整合面，不必整套全量留到 ship 才第一次跑（全量整合套件動輒數十分鐘，領域子集通常兩三分鐘）。
- **抓不準就省略**（zone 影響面橫跨大半專案、或測試目錄組織對不上 zone）：整段不寫，runner 自動 fallback 跑 config 全量——縮圈永遠是顯式的，省略永遠安全。
- **ship 不受影響**：出貨全量 test＋journey 照舊，跨票迴歸在那裡把關。

## 生成 `.constellation/config.json`

自動探測這個專案既有的驗證指令，寫成：

```json
{
  "commands": {
    "test": ["npm test"],
    "journey": ["node e2e.mjs"]
  }
}
```

使用者本來就長開、不希望被碰的埠，可另加 `"protectedPorts": [3000]`——runner 每條指令收尾的埠差集補刀一律跳過這些埠（不確定要不要加就別加，這是逃生閥不是預設值）。這次任務判定「大量資料」時筆數門檻不是預設 10 萬筆，也可另加 `"largeDataRows"`（可選欄位）調整。

探測順序：先看 `package.json` 的 `scripts.test`／`scripts.e2e`／`scripts.journey`，找不到再看既有 CI 設定（如 `.github/workflows/*.yml`）裡出現的測試指令。兩邊都探不到，對應陣列留空，並在 `config.json` 加一個 `"_note"` 註記欄記「驗證指令待補」（例如 `"_note": "package.json 與 CI 設定都探不到驗證指令，待使用者補上"`），同時在對應那張票（或小流程的任務卡）的「決議記錄」留一筆同樣的待補說明——不為此發問，本階段一律不再開新題。`gates/verify-runner.mjs` 會讀這份 config 決定要跑什麼（細節見本檔同目錄的 `verification-playbook.md`）；指令是空陣列時，依賴它的驗收條件在 build 階段跑不出證據，該標 blocked，等使用者補上指令才解除。

**journey 合併規則**：探測出的 journey 指令若屬同一測試框架的多個 project／多支分開呼叫（如 `playwright test --project=e2e` 與 `--project=auth` 兩支），合併成單一次呼叫（`--project=e2e --project=auth`）——production build、服務啟動、登入 setup 這類昂貴固定成本在一次 journey 裡只付一次，拆開呼叫會重複付。

`approved` 欄位本階段核准時寫 `true`；出貨（ship）歸檔會把它重設回 `false`，讓下一輪重新從未核准狀態開始（規則見本檔同目錄的 `phase-ship.md`）。

## 完成後：呈交票清單摘要

- **大流程**：收尾前用 AskUserQuestion 彈窗做封閉確認：列出票清單（票名、zone、blocked-by 關係，讓「誰能平行」一目了然），問使用者「照這樣拆票進 build，還是要調整？」；推薦選項的說明加一句「核准後會在本機 commit 本輪 `.constellation` 產物（decisions、CONTEXT、MAP、tickets、config、design-frozen.json、design-baseline.json）與定稿改動，不推送」——worker 的工作區要看得到這些才不會落在舊版上（見母本 DESIGN.md §7）。彈窗本身必須能獨立看懂（已知顯示 bug 會讓同回合彈窗前的文字整段不渲染）。
- **小流程**：單一任務卡不開核准彈窗——訪談收尾那次拍板已經包含「這件事怎麼做」，任務卡只是把那個決定轉成票格式，不是新的待核准內容。任務卡內容在 build 開工的第一句話向使用者摘要一次即可，直接把 `"approved": true` 寫入 `.constellation/config.json`，不必等使用者回應。
- 呈交票清單時（大流程）一併附上**「決議→承接處對照表」**（決議 032）：分母只算**本輪**——`grill-close.md` 之後編號的決議（本輪訪談新落的 `decisions/NNN-slug.md`）**一筆有幾款就列幾列**＋工程預設清單逐條＋ design 定稿記錄的逐區塊元件清單逐區塊（若有 UI），每列寫出對應到哪張票號／哪條驗收條件承接了它，標「不適用」要寫一句理由；跨輪舊決議不列進來。欄位：`款` / `來源檔` / `承接票號` / `對應驗收條件或不適用（附理由）`，有 UI 時多一欄 `定稿畫面跟這款有沒有衝突`。核准彈窗本體要帶一份壓縮版「款 → 票號」對照（已知顯示問題：彈窗前的正文常不渲染），全表照常寫在彈窗前的正文。這張表只給人核對，不得變成任何閘門的檢查欄位。
- 使用者要求調整：回到拆票規則重新合成受影響的票就好，不必整批重來。
- **工程預設清單對照**（`decisions/engineering-defaults.md` 存在時才做）：逐條核對每一條工程預設都已對到某張票的某條驗收條件——對不到就代表這條工程預設沒有落實到票裡，先回頭補上對應的驗收條件，這輪還沒核對完不得寫入 `"approved": true`。核對中若發現某條工程預設其實該由使用者拍板（例如它其實是「兩條決議打架」，或指揮官的工程預設擴大／收窄了使用者拍板的範圍，見 `phase-grill.md`「完整性四保險」第 3 點的阻擋級判準），比照上面「本階段唯一動作」段落「若合成過程中發現決議之間互相矛盾」處理：退回去用 AskUserQuestion 彈窗告知使用者，不在 weave 裡自己拍板。
- **大流程使用者確認後**（不是彈窗一發出就算數，要真的等到使用者點頭或回覆同意），把 `"approved": true` 寫入 `.constellation/config.json`——這是機讀的核准標記（見 DESIGN.md §4），防止中斷後新 session 看到票清單就直接開工、跳過核准這一步；沒寫入這個標記前，總控（`skills/constellation/SKILL.md` Step 0）會判定票清單尚未核准並退回本階段重新確認。
- **寫入 `approved: true` 後，立刻本機 commit**：只 `git add` 本輪 `.constellation/` 產物（`decisions/`、`CONTEXT.md`、`MAP.md`、`tickets/`、`config.json`、`design-frozen.json`、`design-baseline.json`；不含 `.servers.json`、失敗計數檔這類執行期狀態檔）與定稿改動，`git commit`，**不推送**——build 階段 fan-out 開 worktree 時，worker 的工作區要看得到這些才不會落在舊版上（見母本 DESIGN.md §7「worktree 基底須含本輪產物」）。小流程同樣要有這筆 commit 才能進 build。
- 才進本檔同目錄的 `phase-build.md`（小流程已在上面直接寫入 approved，同樣要有這筆 commit 才能進 build）。
