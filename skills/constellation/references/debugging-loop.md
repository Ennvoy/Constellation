# 除錯迴圈

> 改寫自 diagnosing-bugs 精髓，貼合 Constellation。除錯是跟開發新功能不同的任務型態，遇到 bug 走這份 playbook，不是照票的驗收條件流程硬套。

## 核心信念

先建立一個可靠的紅綠回饋迴圈，才有資格開始排查——迴圈一旦可靠，剩下的定位工作是機械性的收斂，不是靠經驗直覺硬猜。**建迴圈之前就一頭栽進去讀程式碼**，正是這份紀律要防的頭號失敗模式：讀了半天程式碼、腦補出一套理論，卻沒有一次真的讓 bug 重現過。

## ① 建回饋迴圈

依序嘗試以下十種手法，找到第一個能滿足下面四項完成判準的就停下來,不用往後找更花俏的：

1. failing test（寫一個目前會失敗的測試）
2. curl／HTTP 直打（有服務在跑就直接打進去看回應）
3. CLI diff（跑指令，比對實際輸出跟預期輸出的差異）
4. headless browser（無頭瀏覽器跑一次操作路徑）
5. 重放捕捉的 trace（有錄下來的請求／事件紀錄，重放一次）
6. 拋棄式 harness（現寫一支一次性腳本，專門觸發這個情境）
7. property／fuzz 迴圈（餵大量隨機輸入找出會炸的那個）
8. 二分 harness（對半砍輸入／程式碼路徑，找出問題落在哪一半）
9. 差分迴圈（拿兩個版本／兩條路徑的行為互相比對差異）
10. 最後手段：人機互動腳本（寫一份步驟腳本，請人工照著操作、回報看到什麼）

其中第 2、4 種（直打服務、無頭瀏覽器）常常要自己起一台 server：**經 `gates/serve.mjs` 起、迴圈收工 `stop`**（見本檔同目錄 `verification-playbook.md`「臨時 server 的起與收」）。除錯天生要起起停停好幾輪，不記帳就會囤一排佔著埠的舊 server，而那些舊 server 之後會被 e2e 當自己人沿用、拿舊 build 蓋出假綠。

**完成判準（四項都要滿足）**：
- 能變紅——迴圈真的會在 bug 存在時失敗
- 確定性——每次跑結果一樣，不是偶發
- 快——秒級可以跑完一次，不是等半天
- agent 可自行執行——不需要每次都靠人工介入才能觸發

滿足以上四項後，**SHALL 實際跑過一次，把輸出貼出來**再往下走——「應該可以重現」不算數，跑一次見到紅燈才算數。

貼出來與落檔的輸出先遮密（金鑰／token 改 `<REDACTED>`，迴圈指令用環境變數引用）——除錯輸出常整段落進票或決議，規則同本檔同目錄 verification-playbook「證據遮密」。

**迴圈到手後，把它當產品再磨一輪（收緊三問）**：能更快嗎（快取 setup、跳過無關初始化、縮小範圍）？訊號能更利嗎（直接斷言使用者講的那個症狀，不是只看「沒炸」）？能更確定嗎（釘死時間、種子化隨機、隔離檔案系統）？30 秒又偶發的迴圈只比沒有好一點；2 秒且確定性的迴圈是除錯超能力——每個假設的驗證成本差十倍。

**非確定性 bug（有時壞有時不壞）**：目標不是一次到位的完美重現，是**拉高重現率**——連跑 100 次、平行多開、加壓、注入 sleep 擠窄時間窗；壞五成查得動、壞百分之一查不動，先把率拉到查得動再進假設階段。完成判準的「確定性」對這類 bug 讀作「釘住的高重現率」。

**建不出可靠迴圈時**：停下來，列出已經嘗試過哪些手法、卡在哪裡，跟使用者要環境或權限（例如需要某個帳號、某個服務的存取、某台機器）——不要在迴圈不可靠的狀態下硬著頭皮繼續猜。

## ② 重現＋最小化

迴圈能穩定觸發 bug 後，**一次刪一個變因**（拿掉一個步驟／一段輸入／一個條件，看 bug 還在不在），持續縮減，直到剩下的每一個元素都是 load-bearing——拿掉任何一個，bug 就不重現了。最小化後的重現步驟，就是後面儀器化與修復要盯著的範圍。

## ③ 假設

列出 3–5 個**可證偽**的假設（每個假設都要有辦法設計出一個測試證明它對或錯，不能是「感覺是這裡」這種無法證偽的說法）。按可能性／驗證成本排序，**先給使用者看過**再動手一個個測——不要同時改好幾個假設對應的地方，那樣測出結果分不清是哪個假設應驗了。

## ④ 儀器化

優先順序：**debugger／REPL 斷點單步 ＞ 有目標的 log ＞ 絕不是「先全部下 log 再撈輸出」**。全面撒 log 會把訊號淹沒在雜訊裡，還會留下一堆事後要清的殘骸。

- 每一行 debug log 加**唯一前綴**（例如 `[DBG-a4f2]`），事後一次 grep 就能全部找到、全部清掉。
- **效能迴歸**：先建 baseline（量出現在的數字），再用二分法定位是哪次改動／哪個環節拖慢的——不要用「猜哪段程式碼慢」然後到處加計時 log。

## ⑤ 修復＋回歸測試

只在**正確的 seam**（介面邊界、可測試的切入點）上補回歸測試，不要為了「有測試」硬塞一個測不到重點的地方。**如果找不到正確的 seam——這件事本身就是一個發現**，代表架構上缺一個可測試的切入點，記錄下來（可以進票的決議記錄，或視情節嚴重度提到使用者面前），不要為了交差硬寫一個測不到東西的測試。

## ⑥ 清理＋檢討

修好、回歸測試綠了之後才做這一步，順序不提前：

1. 清光所有 `[DBG-*]` 前綴的暫時 log
2. 刪掉 ②③④ 階段用過的拋棄式 prototype／harness
3. 把**驗證過的假設**（真正的成因、為什麼會發生）寫進 commit message——不是寫「修了一個 bug」，是寫清楚根因
4. 最後才問「什麼架構變化能防止這類 bug 再發生」——這一題留到最後問，避免在 bug 還沒修好時就分心去想重構，拖慢當下要收斂的除錯迴圈
