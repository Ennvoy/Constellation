# 票模板（tickets/*.md）

> 合成拆票（weave）時產生、逐票實作（build）時更新、關票時驗證證據寫入。完整規則（出處：母本 DESIGN.md §4、§7、§8，部署後 runtime 不需讀取）。

## 命名規則

- 編號：`T-NNN`（三位數，遞增）。序號用過就永久保留給那張票的歷史，票被刪除或合併也不重複使用該號碼。
- 檔名：`tickets/T-NNN-<slug>.md`，`slug` 是票名的 kebab-case（英文小寫＋連字號），例如 `T-003-login-rate-limit.md`。
- 票名（H1 標題 `# T-NNN <票名>`）用**人話**取，講這張票做什麼——例如「登入限流」，不是重複編號或抽象分類（不要取「Ticket 3」「Auth 相關」這種）。
- **對話與文件中一律用票名指稱**（「登入限流那張票」），不單獨丟裸編號。編號只用來對檔名、對 `blocked-by` 這種機器可讀欄位；人在追票時靠名字辨認，不是靠數字。

## 完整模板

```markdown
# T-003 登入限流
status: open | in-progress | blocked | done
blocked-by: T-001            # 依賴關係，可留空
zone: src/auth/**, tests/auth/**   # 檔案界線（平行時互斥用）

## 目標（行為契約，禁寫實作內部路徑/程式碼片段——durability over precision）

## 驗收條件（合成階段寫定，逐條可勾）
- [ ] ...實跑可驗證的條件...

## 決議記錄（實作期小事自決落此，可追溯）

## 驗證證據（關票時由 runner 寫入：指令＋結果摘要＋時間）
```

## 逐欄說明

### status

四態，只沿此路徑走：`open → in-progress → blocked/done`；`blocked` 排除依賴後回 `in-progress`。**只有驗證證據齊備、關票刷卡機（閘門 5）通過才能標 `done`**——不是自己覺得做完就改字串。

### blocked-by

列這張票**動工前必須先關**的票號（逗號分隔多筆，可留空）。合成拆票時依此排 fan-out 批次：無依賴、`zone` 不重疊的票同批平行；`blocked-by` 未清空的票留到下一批。實作期若發現漏列的依賴，補上並在「決議記錄」寫一句為什麼。

### zone

這張票**允許動的檔案 glob**（可多個，逗號分隔）。平行 fan-out 的前提就是各票 zone 互斥——整合前檢查 worker 改動沒有越界（出處：母本 DESIGN.md §7，部署後 runtime 不需讀取）。zone 抓太寬會擋到別票平行、抓太窄會讓票做不完就撞牆；兩者都盡量在合成時抓準，實作期真的要跨出既定 zone 就先在決議記錄留言，不要悶著頭跨。

### 目標——durability over precision（核心紀律）

寫的是**行為契約**：這張票完成後系統對外該有什麼樣的行為／介面／型別，不是「打開哪個檔案改哪幾行」。

**禁止**寫具體檔案路徑、程式碼片段、變數名、函式簽名這類會隨實作漂移的細節——票凍結後實作手法可能換人換做法，寫死路徑的目標下一秒就過期，從指引變成誤導。

**對照例子**：
- 目標該寫成：「使用者 15 分鐘內連續 5 次登入失敗，第 6 次起回 429，直到冷卻期滿」
- 不該寫成：「在 `authController.ts` 的 `login()` 函式裡加一個 `failCount` 變數判斷」

**唯一例外**：design 階段產出的**design 定稿元件片段**，若它比散文描述更精確地表達視覺／互動契約，可以內嵌片段，但**必須註明來源**（例如「沿用 design 定稿 `LoginForm.tsx` 的錯誤訊息呈現方式，見 design canvas 定稿記錄」）——那不是猜實作，是已經拍板的成品規格。

### 驗收條件——必須實跑可驗證

每條驗收條件要能被**一個真實動作**驗證，不是靠讀 code 目測。寫的時候想清楚「關票時我要跑什麼指令、點什麼畫面，才能打勾這條」：

- 可驗：「POST `/login` 帶錯誤密碼連打 6 次，第 6 次回應 status 429」（真打 API）
- 可驗：「UI 上連續打錯密碼 6 次後，畫面顯示冷卻倒數，送出按鈕變 disabled」（真點擊）
- 不可驗：「登入限流邏輯正確」（沒有動作可驗，只是重複目標本身）
- 不可驗：「程式碼有做限流判斷」（讀 code 目測，不是實跑）

驗證方法與分級規則見本檔同目錄的 `verification-playbook.md`；寫驗收條件前先掃一眼那份手冊，避免寫出驗不了的條件。

### 決議記錄

實作期間的**小事自決**（命名細節、邊界處理、發現的漏列依賴）落此，一行一句「決定＋原因」即可，不必長篇——這是可追溯的軌跡，不是給人審核用的申請書。碰到需求級分歧（驗收條件矛盾、要動資料結構、涉權限／金流／個資、破壞性 DB 操作）不在這裡自己定案，那類事要彈窗問使用者（出處：母本 DESIGN.md §8，部署後 runtime 不需讀取），問完的結果才記在這。

### 驗證證據

關票當下由驗證 runner（閘門 4）寫入，格式固定四件：**指令**（實際跑了什麼）＋**結果摘要**（通過／失敗、關鍵輸出）＋**時間戳**＋**`sig` 簽章行**（runner 用本機 secret 對這筆證據簽出的簽章）。人不手填這欄——手填等於繞過閘門；關票刷卡機（閘門 5）會驗證 `sig` 簽章是否有效、時間戳是否在 24 小時新鮮度內，兩者有一項不過就直接擋下，不准標 `done`。手填的時間戳沒有對應簽章，一定過不了刷卡機（出處：母本 DESIGN.md §5，部署後 runtime 不需讀取）。
