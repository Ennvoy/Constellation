# Phase ② UI 定稿（design）

一句話：把這個專案的設計基底同步上 Claude Design → 讓 Claude Design 自己設計出這次要的畫面 → 使用者在它的 canvas 上調到滿意 → 拉回 repo、**直接改專案的正式頁面 code** → **執行端在本地逐一點過每個互動、整頁截圖交使用者看圖拍板**（瀏覽器工具或 Artifact 任一缺，退回使用者本地點）→ 才算定稿，定稿即凍結。

解決的根本問題是 mockup 與成品不符（出處：母本 DESIGN.md §3，部署後 runtime 不需讀取）。**定稿物＝專案裡真的改好、能用瀏覽器打開點完的正式畫面**——「canvas 上的稿」與「元件檔案存在於 repo」**兩者都不算定稿**；**沒有在本地跑起來的正式畫面上逐一點過每個互動、並經使用者看過拍板，這一步就沒有完成**。落地手段仍是一次性轉譯（把它的檔案格式換成專案自己的元件格式），不是看著圖重畫；不可以宣稱「原封落地」（格式不同，一定要轉一次），但仍然遠勝「看著 mockup 重畫」。

> **定版點在本地跑起來的正式畫面上（步驟 5b），不在 canvas**：canvas 上的點頭只是方向確認，若定版簽名簽在那裡，轉譯與凍結就發生在使用者視野之外、做沒做他都看不到（案例見決議 017）。5b 由誰點過、以什麼形式交使用者拍板，依決議 023 修訂，見下步驟 5b。

**方向感（這階段最容易走反的地方）**：Claude Design 的價值在於**它自己會設計**——官方定位是「你講你要什麼，它先做一版給你反應，你再一路改到它變成你的」。所以**不要**在本地先做好幾個版本再推上去讓使用者挑：那等於白繞一趟雲端，也浪費了它自己會設計這件事。大工程另有一條並列的路——**執行端自己寫畫面 code**（見最後的「路徑二：執行端自己寫畫面 code」），它不是降級、是進場時讓使用者選的另一條路；小工程則一律直接改 code、不進產線（見「小工程直通」）。

## 進場 / 離場

- **進場條件**：本檔同目錄的 `phase-grill.md` 收尾時判定這次任務**需要 UI**（不是純後端／無 UI 任務），frontier 已清空、使用者已拍板。`decisions/grill-close.md` 的「是否需要 UI」欄值是 `是（架構有得選）` 或 `是（照既有架構做）`，**兩者都進場**——差別只在步驟 2 要不要請 Claude Design 生成多個方向讓使用者比較；同步基底、確認調整、拉回、轉譯、寫定稿記錄、凍結一律照跑。
- **大流程時，進場前要先看到盲點審收斂**：`decisions/grill-close.md` 檔尾要有「盲點審：已收斂（第 N 輪）」（使用者喊停時是「盲點審：使用者喊停（第 N 輪）」，效力相同）才能進場——沒有就代表獨立盲點審還沒跑完，先 Read 本檔同目錄 `phase-grill.md`「完整性四保險」第 3 點接回盲點審，收斂後才回來進場。兩個 runtime 做法相同（小流程可省略盲點審，不看這一行）。
- **設計進行中收斂行被刪也要停**：若在本階段進行中因增量重訪而刪掉了收斂行（`phase-grill.md`「完整性四保險」第 3 點：落了新的訪談決議就刪行重跑），畫面製作即暫停——不得繼續生成、轉譯或凍結，先接回盲點審重新跑到收斂，才能恢復進行中的設計工作。
- **進場後第一件事**：先分流小／大工程（見下方「小工程直通」）——小工程不論 Claude Design 可不可用都直接改 code、不進產線；大工程才確認這次到底用不用得上 Claude Design（見步驟 1 之前的前置判斷）。用得上就**彈窗問使用者這次 UI 走哪條路**（路徑一 Claude Design／路徑二 執行端自己寫，問法見最後那一節），選路徑一走步驟 1～7、選路徑二走最後的「路徑二：執行端自己寫畫面 code」；用不上就只剩路徑二，照實講明是哪一種原因再走那一節。
- **離場條件（五項全中才准離場，缺一項就是這一步沒做完）**：
  1. 使用者已在 canvas 上挑定並調到滿意（只生成一版的路徑沒有「挑」這個動作，改為看過這一版、講完要改哪裡並調到滿意）——**這一項只是設計方向確認，不等於定版**；
  2. 已**直接改專案的正式頁面 code**（步驟 5）——不是產一份放在旁邊的元件檔，也不是掛在暫時網址上的預覽版；
  3. **已依步驟 5b 完成定版**（執行端逐一點過每個互動、截圖發 Artifact 給使用者看圖拍板；工具缺才退回使用者本地點過拍板）；
  4. 定稿記錄已寫，且**附了逐區塊元件清單**（步驟 7）；
  5. 凍結名單已寫：`design-frozen.json` 的 `frozen` **非空**、且**每個路徑都真的存在於 repo**。
  才交給本檔同目錄的 `phase-weave.md`（它進場會用機器把第 4、5 項再驗一次）。
- **走路徑二的離場條件**：沒有 canvas、沒有「拉回」這一步（東西本來就長在 repo 裡），**其餘五項一字不減**——尤其第 3 項（步驟 5b 的定版：使用者看 Artifact 拍板，或工具缺退回本地點過拍板）在路徑二同樣必須發生；定稿記錄另含「這次走的是哪條路、為什麼」（使用者在進場提問裡選的，或路徑一此刻不可用、是哪一種原因）。
- **無 UI 任務**：本檔同目錄的 `phase-grill.md` 判定不需要 UI 時，本階段完全不運行，也不會去建立或動任何 Claude Design 專案，直接由 grill 交給 weave。

## 小工程直通（先於一切工具判斷，不限走哪條路）

**不是所有跟畫面有關的工作都需要設計服務。**只改一個按鈕、修一個小地方、加一個欄位、在既有設計語言底下做單一元件、修畫面的 bug——這類**不論 Claude Design 此刻可不可用，一律直接改 code 給使用者看**（改完照步驟 5b 做：經 `gates/serve.mjs` 起本地 server、執行端逐一點過、整頁截圖發私人 Artifact 請他看圖拍板，拍板後 `stop`；瀏覽器工具或 Artifact 任一缺，才退回給他網址請他自己點），不動用設計產線、也不必問要不要換環境；工具可用時把小工程推上產線，同樣違反「流程本身不得成為工作量」（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取；決議 012）。改完照「路徑二：執行端自己寫畫面 code」一節「路徑二實際怎麼做」的第 4 點往後走（給他看、依文字回饋改、滿意即定稿、寫記錄、凍結——定稿記錄寫「小工程，直接改 code 給使用者看」）。

**要走產線（要問走哪條路）的是這幾種大工程**：新產品、全新頁面、資訊架構要重新決定、複雜的操作流程。（`grill-close.md` 記著 `是（照既有架構做）` 的需求多半落在小工程那一側，但「照既有架構做的全新頁面」或複雜流程仍算大工程——判斷依據是這次要決定的東西有多大，不是那一欄的值。）

## 這階段誰動手：多數步驟自己代操，只有一步非使用者親自不可

Claude Design **沒有可以程式呼叫的「生成」介面**——DesignSync 工具只有讀檔、寫檔、建專案那幾個方法，「生成畫面」與「在 canvas 上編輯」都只存在於網頁上。所以這階段會真的去操作瀏覽器好幾次，要分清楚哪幾次自己做完就好、哪一次一定要停下來等使用者（下面這張表講的是路徑一 Claude Design 的分工；路徑二的分工見最後的「路徑二：執行端自己寫畫面 code」，但「哪一版、改哪裡由使用者親自拍板」這條在兩條路上都一樣）：

| 步驟 | 誰動手 |
|---|---|
| 1　推基底上去 | 自己（DesignSync 寫檔） |
| 1d 觸發編譯 | **自己代開瀏覽器**載入專案頁面（不載入就不會編譯），使用者不必在場 |
| 2　丟需求生成 | **自己代開瀏覽器**輸入需求、送出、等它畫完，使用者不必在場 |
| 3　方向確認與調整 | **⚠ 使用者親自**——挑哪一版、調哪裡是設計決策，不可代為拍板。**但這一步不算定版** |
| 4　拉回 repo | 自己（`get_file`） |
| 5　直接改專案的正式頁面 code | 自己 |
| **5b　執行端逐一點過每個互動、截圖發私人 Artifact 給使用者看圖拍板** | **自己**點過每個互動、截圖、發 Artifact；**⚠ 使用者親自看圖拍板——這是唯一的定版點**，不可代為拍板、不可跳過去寫定稿記錄。瀏覽器工具或 Artifact 任一缺，退回使用者本地點 |
| 6／7　單向門、定稿記錄與凍結 | 自己（**前置：5b 的拍板已經發生**） |

所以實際節奏是：**先把基底推上去、把畫面生成好，然後才把使用者叫來**——給他 canvas 網址、告訴他手上有哪些工具（見步驟 3），請他看、調、或直接用文字講要改什麼（用文字講的話由自己動手改，不必逼他去拖拉）。方向定了之後**自己把正式頁面 code 改完、把本地 server 起好、逐一點過每個互動、整頁截圖**，才第二次把使用者叫來——這次發的是**私人 Artifact**，請他看圖拍板（步驟 5b；瀏覽器工具或 Artifact 任一缺，才改給本地網址請他自己點）。不要在步驟 1、2 進行中就把網址丟給使用者要他等；不要跳過步驟 3 自己覺得哪一版好看就往下走；**更不要跳過 5b 直接寫定稿記錄**（案例見決議 017）。

**使用者要被叫來兩次，這是刻意的**：第一次確認「設計方向」（canvas），第二次確認「真的做出來的東西」（Artifact 或本地畫面）。少了第二次，「定稿」兩個字就沒有任何人驗過。

## 開工前先分清兩件事：基底哪裡來、要不要多個方向

這兩件事互不相干，各自有各自的決定方式，不要混成一題：

- **基底哪裡來＝事實，自己讀 repo 就知道，絕對不問使用者**（鐵律「事實不問人」，出處：母本 DESIGN.md §2，部署後 runtime 不需讀取）：repo 裡已經有能跑的畫面（既有頁面／元件／樣式）→ 基底就是既有 code 本身，把它真正的 tokens／可重用元件／全域 CSS／字型推上去；repo 是一片空地（全新專案、還沒有任何畫面）→ 才挑一套設計系統當起點。做法見步驟 1。
- **要不要多個方向＝真決策，使用者在訪談收尾已經拍板**：讀 `decisions/grill-close.md`「是否需要 UI」欄的值——`是（架構有得選）` 就在步驟 2 請 Claude Design 生成多個方向，`是（照既有架構做）` 就只生成一版。**這裡不重問**，值已經在檔案裡了。

兩件事交叉出四條路，實際走法：

| repo 有沒有既有 UI（自己探測） | grill-close.md 記的值 | 這階段怎麼走 |
|---|---|---|
| 沒有（空地） | `是（架構有得選）` | 挑一套設計系統推上去當基底 ＋ 請 Claude Design 生成多個方向讓使用者比較 |
| 沒有（空地） | `是（照既有架構做）` | 挑一套設計系統推上去當基底 ＋ 只生成一版 |
| 有 | `是（架構有得選）` | 把既有 tokens／元件／全域 CSS／字型推上去當基底 ＋ 生成多個方向 |
| 有 | `是（照既有架構做）` | 同上基底 ＋ 只生成一版，需求描述裡明講沿用既有的資訊架構 |

**這次是改造某個既有畫面時**（改版、重排、換互動方式）——**現況結構必須送上去，兩條路擇一、每張改造型畫面都要做**（原因：只推通用基底、憑文字描述生成，Claude Design 可能畫出「相似但結構不同的新頁面」而不自知；這步有機器閘門把關，見下）：

- **(a) 推現況元件**：現況本來就是形狀合規的共用元件時，把那幾個元件一起推進設計系統當基底——生成時它會先讀設計系統再設計，自然參考到現況長什麼樣。
- **(b) 從真 code 抽精確結構餵進需求描述**：頁面級 tsx 推不進設計系統的檔案形狀時用這條（實測有效）——把現況的**表頭層級、欄位順序與名稱原文、合併儲存格結構、區塊標題與口徑說明文字**逐字抽出來寫進需求描述，明講「這是真系統現況、照此結構畫，本次只改動 X」。

不論走哪條，都要把判別結果記進 `.constellation/design-baseline.json`（格式見步驟 2 的現況覆蓋檢查）。**落地硬規則**：改造型畫面在步驟 5 轉譯時一律是**改現有 code 的增量修改**（加欄／移欄／加區塊），絕不照設計稿整頁重畫——canvas 稿對改造型只是「新增部分長什麼樣」的參考。**不另外做「現況對照組」這種機制**；使用者真的想拿新舊並排看，就在 canvas 上跟現況畫面對照著看，或請 Claude Design 再生成一版貼近現況的版本。

## 步驟 1：把專案的設計基底同步上 Claude Design

這步的目的只有一個：**讓 Claude Design 設計的時候，用的是這個專案真正的東西，不是它自己想像的近似值**（官方原話是「用你真正的元件，不是近似品」）。做完這步，之後每一次生成都會先讀它、再設計。

> **這整步是手工做法**：官方的 `/design-sync` skill **目前在本機取不到**（實查：Claude Code 2.1.220 已是 npm 最新版本，安裝檔裡搜不到 `design-sync` 字串、官方 marketplace 沒有這個 skill、官方 changelog 從未提及）。所以下面的檔案結構與哨兵都是從 app 端行為反推出來的手工做法。**哪天官方 skill 真的可用了，本步驟應該直接改成呼叫它**，不要繼續維護手工版。

**動手推檔案之前，先確認這次到底用不用得上 Claude Design**：實際確認一次能不能把基底推上去、能不能開它的 canvas。**看的是「工具此刻在不在、通不通」，不是「現在跑在哪個執行環境」**——用不上的原因很多種（沒網路、額度用完、這個環境裡沒有這個工具、工具在但登入不通），任何一種成立就代表**路徑一此刻走不了、只剩路徑二**，照實講明是哪一種再走最後那一節，**不默默改成自己寫**。確認得出「用得上」、而且使用者在進場提問裡選了路徑一，才往下做 1a。

### 1a. 先確認要推的是「設計系統專案」

- 用 `list_projects` 找這個專案有沒有既有的 design system 專案；沒有就 `create_project` 新建（用它建出來的就是設計系統型別）。
- 推之前用 `get_project` 驗一下 `type` 是不是 `PROJECT_TYPE_DESIGN_SYSTEM`。
- **型別在建立時就固定、之後不能改**：不能拿一個普通專案（`PROJECT_TYPE_PROJECT`）充當設計系統，把檔案推上去它也不會變成設計系統，只是白推。

### 1b. 基底的內容從哪來

**A. repo 是一片空地（全新專案／還沒有任何畫面）** → 起點**自己定，不問使用者**：

- 若 `CONTEXT.md`／`decisions/` 裡訪談階段已經記錄使用者的風格偏好，直接沿用，不重問。
- **使用者主動點名要某種調性**（「我要 Notion 那種」「深色沉穩一點」）就照他講的做——那是他自己給的輸入，不是我們去問他。
- 沒有既定偏好、也沒被點名：**從 Claude Design 內建的六套（Modernist／Classical／Nocturne／Organic／Broadsheet／Industry）裡自己選一套**，依這次任務的調性與受眾選定即可。**不要為此開彈窗**——空地專案沒有既有 code 可對，這題怎麼選都不會錯到需要使用者來擋，把他叫來回答等於憑空多一道他不想答的題；真的選歪了，步驟 3 在 canvas 上、步驟 5b 在本地畫面上都還攔得住。**選了哪一套、為什麼選它，寫進步驟 7 的定稿記錄**。
- 選定後把那套的 tokens 照下面 1c 的形狀寫成檔案推上去，做客製化延伸，不是套用預設樣式了事。

**B. repo 已經有既有 UI** → 基底就是既有 code 本身：

推上去的是**既有的 tokens、可重用元件、全域 CSS、字型**——**不是推做好的頁面**。不必反推、不必猜近似值，直接給真的東西最保真。實務上就是把 repo 裡的設計變數檔、共用元件、全域樣式、字型宣告整理成 1c 的形狀推上去；專案裡沒有集中的 tokens 檔就現場從既有樣式抽出那幾組值（主色／背景／文字／邊框／狀態色、字級階層、間距節奏、圓角與陰影、互動狀態的表現方式），寫成 `tokens.css` 推上去。

**不要為此在 repo 裡新增任何檔案**——設計系統的檔案活在 Claude Design 專案那邊，repo 這邊不留快照（快照會過期，既有 code 才是唯一真相，而且不新增檔案就不用維護它；流程本身不得成為工作量，出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。

**⚠ 基底用 code，需求不用 code——這是兩個不同的真相**：上面那句「既有 code 才是唯一真相」只適用於**視覺語言**（tokens、元件、全域樣式）。改造既有畫面時，現況 code 是**改版前**的狀態；「這一輪欄位要改成什麼、哪些欄位要拿掉」一律以**本輪決議**為準，兩者衝突時**決議勝出**。

把 code 裡的欄位清單（型別定義、表單狀態、驗證規則）直接餵給設計服務，等於把改版前的規格當成需求送出去——而且它會照著做、做得很像真的，事後看不出哪裡不對。

> 實例：某輪任務的決議已把表單第 1 組的「活動名稱／簡稱」兩個自由文字欄整個移除、改成兩個結構化必填欄位，也把另一組的欄位搬走大半；執行端卻在使用者反映「這組是幻想的」之後，去讀既有 `types.ts` 抄欄位餵過去，於是整組被做成**改版前**的樣子。使用者一眼看出：「我們不是討論了活動名稱不要……討論的你都忘光了嗎」。錯的不是設計服務，是餵進去的需求來源選錯了。

### 1c–1f. 檔案形狀、哨兵、驗證與呼叫坑（動手推檔前必讀）

**動手寫任何要推上去的檔案之前，先 Read 本檔同目錄的 `design-sync-details.md`**——app 端只認特定檔案形狀，形狀不對不會報錯、只會完全隱形；哨兵缺了前面全部白做。那份檔案是實測反編譯拿到的字面規則全集（樣式入口鏈、token 宣告位置、元件三件套、哨兵與編譯驗證、DesignSync 呼叫坑），照它逐條做完再回來走步驟 2。

## 步驟 2：把需求丟給 Claude Design 生成

- **動筆寫需求之前，先對每一張要設計的畫面做一次「現況覆蓋檢查」**（與下面的決議覆蓋檢查平行的硬檢查點）：逐張判別這張是**全新頁面（new）還是改造既有畫面（rework）**；rework 必須先照「開工前先分清兩件事」末段的 (a)/(b) 兩條路之一把現況結構送上去。判別結果寫入 `.constellation/design-baseline.json`：
  ```json
  { "screens": [
    { "screen": "雙北運力報告", "kind": "new", "sources": [] },
    { "screen": "尖峰完成數報表", "kind": "rework", "sources": ["app/(dashboard)/peak/PeakPageClient.tsx"] }
  ] }
  ```
  `sources` 填現況結構的來源檔（repo 相對路徑：推上設計系統的來源檔、或抽精確結構的那支檔案）。**這份檔案有機器閘門把關**：定稿凍結（寫 `design-frozen.json`）時 close-gate 會驗它存在、每張 rework 的 sources 非空且路徑真的存在，不合格直接擋下（fail-closed）。出貨歸檔時隨其他 design 產物一併歸檔。
- **接著對每一張畫面做「決議覆蓋檢查」**——這是本步驟唯一能自己抓到「漏讀決議」的機制，不可跳過（憑印象挑決議一定會漏，而漏掉的那幾筆往往正是改動最大的那幾筆）：
  1. 列出 `.constellation/decisions/` 的**全部檔名**。檔名是英文 slug、語意可讀，例如 `079-activity-identity-without-name` 一眼就看得出跟「活動識別不用名稱」有關。
  2. **逐一判斷每個檔名與這張畫面有沒有關係**——判斷的依據是檔名，不是憑印象回想自己讀過什麼。**`decisions/engineering-defaults.md`（工程預設清單，若存在——固定檔名，不是編號遞增的 `NNN-slug.md`，也不是下面第 3 點的交接檔 `HANDOFF.md`）不適用這條依檔名判斷的邏輯**：檔名本身看不出跟哪張畫面有關，一律全文讀完、逐條判斷是否與這張畫面有關，不得因為檔名判斷不出來就跳過。
  3. 判定相關的（含上一步認定相關的工程預設清單條目）**全部讀完**再動筆。交接檔（`HANDOFF.md`）點名的那幾筆只是起點，不是全集。
  4. 把「這張畫面對應哪幾筆決議」記下來；**後續每一輪修正都照同一份清單複查**，不要重新憑印象挑。
  漏讀的代價在本階段特別高：設計服務**不會空著讓你發現漏了**，它會補一個看起來完全合理的東西（抽查比例、二審流程、假的地區狀態…），不去查決議根本看不出是編的。
- **動筆寫需求描述之前，先 Read 本檔同目錄的 `design-taste.md`**，把版面紀律一併講進需求裡（適用範圍先判一次——後台介面與行銷頁該生效的條文不同）。不講它，它就照自己的預設排版，出來的東西常常功能都對、卻一眼看得出是機器排的；把要守的量化規則寫進需求，比事後在轉譯階段一條條回頭修便宜得多。
- 在 `https://claude.ai/design` 的輸入框描述這次要做的東西——內容來自訪談定版的決議（`CONTEXT.md`＋`decisions/*.md`），不是憑印象重寫一遍需求。`Design system` 欄選步驟 1 那個專案。
- 它會**先讀設計系統再設計**（實測畫面會顯示「I'll start by exploring the design system.」、「Listing files ×2, Reading ×3」這類動作）。
- **`grill-close.md` 記的是 `是（架構有得選）` → 要多個方向，就用它自己的迭代追問**（「再給我一版側邊欄式的」「這次改成逐步精靈那種流程」）。**不要回頭在本地手工做幾個變體**——那是舊流程，等於白繞一趟雲端。
- **記的是 `是（照既有架構做）` → 只生成一版**，並在需求描述裡明講沿用既有的資訊架構（例如「照現有的列表頁排法，只多一個狀態篩選器」）。需求本來只有一種合理排法時（列表加個篩選器、表格多一欄、表單多一個欄位），硬要多個方向只會生出沒人要的假選項，那是流程自己在製造工作量（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。
- 產出的檔名形如 `<Name>.dc.html`，住在它新建的一個**普通專案**（`PROJECT_TYPE_PROJECT`）裡，不是住在步驟 1 那個設計系統專案裡。
- **成本／效果的實測參考**（拿來設定預期，不是拿來吹）：一句需求描述換到的產出，比本地手工做三個變體完整得多——它自己補上了鍵盤快捷鍵、批次勾選、佇列分類與計數、作者歷史、垃圾自動篩選統計、三組快速回覆模板，並自己跑了一輪自檢把問題修掉。

## 步驟 3：使用者在 canvas 上確認設計方向（**這一步不算定版**）

請使用者去 canvas 上看，並講清楚他手上有哪些工具（多數人不知道 `Tweaks` 是什麼）：

- **`Comment`**：對特定元素留 inline 評論。
- **`Tweaks`**：**語意化的參數旋鈕**，來自設計稿裡宣告的 `data-props`——例如 `density: comfortable|compact`、`autoAdvance`、`showShortcuts`。它不是拖拉像素，是「這個畫面本來就設計成可以切換的那幾個選項」。
- **`Edit`**：圖層樹 ＋ 選取／文字／框線工具，有 `Simple`／`Pro`／`Code`／`Tweaks` 四種模式。
- **`Present`**／**`Share`**：全螢幕呈現與分享。

- **它自己生成的 `.dc.html` 支援直接編輯**；反過來說，**本地推上去的純 `.html` 卡片會顯示「This file does not support automatic edits. You can edit the preview; we will describe changes to Claude to apply on exit.」**——那條翻譯裂縫只存在於「本地推上去的檔」，不存在於「它自己生成的設計」。這正是新流程比「本地做好再推上去讓人挑」好的地方之一。
- 可以多輪來回，調到使用者滿意為止。滿意與否這類封閉確認一次一題、2–4 個選項、白話寫清楚後果與代價（Claude Code 端 AskUserQuestion 彈窗；Codex 端改文字點列）。
- **⚠ 這一步的點頭是「方向對了」，不是「定稿了」**：問法與回報用語都要照這個講（例如「這個方向可以往下做嗎」，不要問「這樣可以定稿嗎」）。真正的定版在步驟 5b——**專案 code 改完、本地跑起來、經使用者拍板**之後。這裡拿到點頭就直接寫定稿記錄，是本階段最容易犯、也最貴的一個錯（案例見決議 017）。

## 步驟 4：拉回 repo

- 用 DesignSync 的 `get_file` 直接讀 `<Name>.dc.html`——**不需要任何匯出功能**。（`list_files` 對這種普通專案同樣有效，用來先看有哪些檔。）
- 一併拉 `_ds/<namespace>/_ds_manifest.json` 回來，當轉譯時的 token 對照表（設計稿裡用到的變數名對得回你的 tokens）。
- **`get_file` 單檔上限 256 KiB**；設計稿大到超過就分次拉相關檔案，不要以為是工具壞了。
- 拉回來的 `.dc.html` **轉譯完就不留在 repo 裡**（用暫存目錄接它，轉完刪掉）。不是因為它佔空間，是因為一份躺在 repo 裡的設計稿會讓人想「改設計稿再同步一次」——那正是步驟 6 要防的事。真的需要回頭看當初定稿長什麼樣，有兩層軌跡夠用了：定稿記錄寫了關鍵判斷，Claude Design 那個雲端專案原檔也還在。它不是工作流要追蹤的檔案，也不進凍結名單。

## 步驟 5：直接改專案的正式頁面 code（轉譯是手段，交付物是能跑的畫面）

**動手位置的四條硬規則**（案例見決議 017）：

1. **改的是正式檔案、正式路由**——不掛暫時網址、不開 `?variant=`、不做 `/preview/` 預覽區、不留新舊兩份並存。**保險是 git**，不行就復原。（理由：暫時位置永遠要多一次「扶正」，而扶正那一步一旦被跳過或做半套，就會出現「兩種品質的畫面並存」；某專案現在就是三塊 1:1 的元件與四頁重畫的舊面板並存。）
2. **不另建假資料檔層**（`mock-data.ts` 這種獨立假資料檔）。要假值就把最小範例值寫死在元件裡，build 接真 API 時整段刪掉——獨立假資料檔會被寫進凍結名單，事後刪它還得先走解凍流程，多一道純手續。
3. **資料來源看後端有沒有**：**後端已經存在 → 直接接真 API**（省掉「先假資料、再換真的」那一圈白工）；**後端還沒有 → UI 先做**、範例值寫死，並在定稿記錄記明哪幾處是寫死的、由哪張票換掉。順序是使用者定的：**先把 UI 做對，後端後接**。
4. **改完要能真的跑**：`pnpm dev`（或該專案的等效指令）起得來、頁面打得開、點得動。**留著「按了沒反應」的示意 stub 就不算改完**——那是 mockup 的行為，不是這一步的交付物。

`.dc.html` 是 Claude Design 專屬的 runtime 格式，**不能直接當專案元件用**，所以這一步的技術動作仍是轉譯。它長這樣：

```html
<x-dc>
  <helmet><script src="_ds/…/_ds_bundle.js"></script><style>…全域 CSS…</style></helmet>
  …template：純 HTML ＋ inline style 字串，用 {{ expr }} 綁值…
</x-dc>
<script type="text/x-dc" data-dc-script data-props="{…語意化參數定義…}">
  const DATA = [...];                    // Claude Design 產的假資料
  class Component extends DCLogic { state = {…}; renderVals() { return {…} } }
</script>
```

執行時它需要 `support.js`（dc-runtime）＋ `window.React`／`window.ReactDOM`——專案端不需要這些，轉譯就是把它換成專案自己的寫法。

**動手轉譯前，先 Read 本檔同目錄的 `design-translate-details.md`**——完整轉譯對應表（多數語法機械對應；唯一真正機械化不了的是動態 inline style 拼接字串要拆成 class modifier）、兩個必踩陷阱（inline style 打敗 `:hover`、假資料要換真 API）與成本實測都在那份，照表逐項轉。

改完**自己先預檢一次**再交件——不要只憑「我照表轉完了」就宣告完成：

- **不論手上有沒有瀏覽器工具**：對照本檔同目錄的 `design-taste.md` 把落地後的畫面與 code 掃一遍。轉譯最容易走味的就是間距節奏、層次與動效這幾樣（拆 style、重命名 class 的過程中一點一點漏掉），那份收的是能用眼睛數、能用 grep 抓的條目，逐條過比憑感覺看可靠。
- **手上有瀏覽器工具時**（Claude Code 端多數情況）：自己把頁面打開快速看一眼、點幾個互動抓明顯破圖——這是自己抓漏用的粗篩，不必按 5b 的逐區塊清單全跑一遍（那件事留給 5b 做一次就好）。
- **手上沒有瀏覽器工具時**（Codex 端裸 CLI 沒有內建瀏覽器，見母本 §9 降級表與 §11.5）：降級為「打 HTTP 確認頁面回 200 ＋ 關鍵區塊的標記真的出現在回傳的 HTML 裡」＋跑既有的元件 render 測試；**交件那句話必須誠實講明「我沒有親眼看過渲染結果，破圖請直接說」**。不得因為看不到就跳過預檢，也不得假稱看過。

**預檢是給自己抓破圖用的，不能取代步驟 5b**——5b 是**正式交使用者拍板的那一輪**（不論是看 Artifact 還是他自己在本地點過），兩件事不可互相頂替。

## 步驟 5b：執行端逐一點過每個互動、截圖發私人 Artifact 請使用者看圖拍板（**唯一的定版點**）

這一步的存在理由：**「定稿」這兩個字必須有人在真的畫面上驗過**。舊條文把使用者的拍板放在 canvas（步驟 3），轉譯與凍結全發生在他視野之外——做沒做他都看不到（案例見決議 017）。

怎麼做：

1. **起本地 server**：**經 `gates/serve.mjs` 起**（開場注入已直接印出它的絕對路徑；沒有注入時，例如 worker，與驗證 runner 同目錄），指令用該專案自己的（`pnpm dev`／`npm run dev`／等效），拿到本機網址。**它起之前會先查那個埠有沒有殘留的舊 server**——查到它只回報、不會擅自殺（它分不出那是不是使用者自己開著的），所以要當場講明、確認可以清掉才明確下 `stop`；不要拿一台不知道誰起的舊 server 當成自己剛改好的畫面驗（那台跑的很可能是舊 build，看起來像做完了，其實什麼都沒變）。起不來就先修到起得來——**這一步不能用「我改好了但跑不起來」交件**。
2. **照逐區塊元件清單（步驟 7 那份，在此步先從剛改好的 code 機械抽出）逐一點過每個分頁、子分頁與互動**——含載入／空／錯誤三種狀態，不留「按了沒反應」的示意 stub；在清單上逐互動標「通過／問題」。
3. **每個畫面整頁截圖、不裁切**：寬表格分段截完整，不得漏掉清單內任何一個區塊（案例見決議 023）；截圖前遮個資，或改用測試資料（本地站常連正式庫）。
4. **發一頁私人 Artifact**：每個畫面的整頁截圖＋逐互動的通過／問題結果（畫面多、截圖直接內嵌 data URI 容易撞 Artifact 16MB 上限——超過就轉 WebP 壓一輪，或改走 assets 上傳附連結，不把原始 PNG 全塞進頁面）。使用者看這頁拍板（Claude Code 端 AskUserQuestion 彈窗；Codex 端照母本 §9 降級為文字點列）——**已知顯示 bug：彈窗前的文字常常不渲染，Artifact 連結要寫進彈窗的 question 或推薦選項說明裡**，不能只貼在正文，不然使用者當下可能看不到要拍板的是哪張圖；「不可代為拍板」不變，**使用者隨時可以要本地網址自己點**。他要改就改完重截、再發一次 Artifact，多輪來回都可以。
5. **拍板通過，才准往步驟 6、7 走**；**同時把 server 收掉**——`serve.mjs stop`，並在正文一句話講明釋放了哪個埠。**只有使用者明說要留著繼續看才留**，留的話同樣一句話講明留著哪個埠，別讓它無聲掛著拖到下一輪（囤積的 dev server 會吃掉連線、拖慢後面每一次驗證）。

**「已改未重截」不算定稿**：使用者要求改動之後，圖還是改動前那一版就不能拿去請他拍板；一定要重截更新過才能再送 Artifact。

**瀏覽器工具或 Artifact 任一缺，退回使用者本地點**（Codex 裸 CLI 兩者都沒有，見母本 §9 降級表）：起本地 server、把網址交給使用者、明確請他自己點過拍板；定稿記錄改附**使用者拍板回覆原文**＋逐區塊元件清單（沒有逐互動標記）。**沒有瀏覽器工具時**，交件那句話要**誠實講明「我沒有親眼看過渲染結果，破圖請直接說」**——不得因為看不到就跳過步驟 5 末尾的既有預檢，也不得假稱看過；**有瀏覽器工具、只是缺 Artifact 時**，執行端其實已經自己點過畫面，這句話不適用，照實講「已經點過、只是這次沒有 Artifact 可發，請你自己點過拍板」即可。

硬規定：

- **不可代為拍板**——執行端自己覺得「跟稿長得一樣」不算數。
- **不可跳過去寫定稿記錄或凍結**。沒有這次拍板，`decisions/` 的定稿記錄與 `design-frozen.json` 都不准動；weave 進場另有機器三驗兜底（見 `phase-weave.md` 進場條件），跳過會在那裡被擋下並退回本階段。
- **代價要誠實記著**：這一步吃執行端逐項實點與整頁截圖的用量額度（母本 §11.5 有記）；額度用完導致圖來不及重截時，適用上面「已改未重截」，不能拿舊圖請人拍板。

## 步驟 6：這是單向門（本階段最重要的一條紀律）

轉譯完成後，**專案裡的元件 code 就是唯一真相**，`.dc.html` 降為參考資料。**不建立任何「回頭同步」機制。**

理由要講明白：設計稿第二次改動時，轉換器的輸出會覆蓋掉手工命名的 class 樹與 modifier 結構，**第二次以後比第一次更貴**，不是更便宜。要再改 UI 就走這兩條路：

- **解凍既有元件、直接改 code**（改動不大時；解凍流程見本檔同目錄的 `phase-build.md`「撞到凍結怎麼辦」）。
- **重跑一次本階段，產一份新的一次性設計稿**（整體結構要換時）。

不做雙向同步——那正是母本 §0 反教訓要防的機制膨脹。

## 步驟 7：收尾——寫定稿記錄、定稿即凍結（**前置：步驟 5b 的使用者拍板已經發生**）

- 收尾寫一筆 `decisions/NNN-slug.md`（**定稿記錄是 decisions 的特例格式**——不套「背景＋決定＋原因＋證據」四要素，用下列自己的欄位；定稿脈絡本身就是拍板證據，不必重複填），記這幾件事：**這次走的是哪條路、為什麼**（走路徑一就一句話帶過；走路徑二就寫是使用者在進場提問裡選的，還是路徑一此刻不可用——不可用要照實寫是哪種原因：沒網路／額度／這個環境沒有這個工具／登入不通；屬於「小工程直接做、沒問使用者」的就照實寫「小工程，直接改 code 給使用者看」）、**基底是哪一套、為什麼選它**（既有 code 的 tokens／元件；空地專案則寫自己選定的內建那一套，或路徑二現場定出的那組 tokens）、**需求是怎麼描述給 Claude Design 的**、**生成了幾個方向**、**使用者選了哪一版**、**在 canvas 上調了什麼**、**轉譯時做了哪些判斷**（動態 style 怎麼拆、class 怎麼命名、哪些 Tweaks 參數在專案端沒有對應物、哪些檔案還留著寫死的範例值——詳細清單見下方「預授權檔案清單」）、**Artifact 連結，以及使用者拍板時看到的逐互動結果**（就是下面「逐區塊元件清單」那份、標好通過／問題，不再另抄一份；退回使用者本地點時，這裡改附使用者拍板回覆原文＋逐區塊元件清單——**沒有瀏覽器工具**時另外註明執行端沒有親眼看過渲染結果，**有瀏覽器工具只是沒有 Artifact 可發**時不寫這句，因為執行端其實已經點過）、以及下面這兩項——

  **⚠ 必附：逐區塊元件清單**（這一輪新增的必記項，不是可選）。格式是三層：**畫面 → 區塊 → 區塊內部元素與互動**，從剛改好的 code 機械抽出（元件函式名＋JSX 結構就是清單，不要憑印象重寫）。例如：

  ```
  單一活動／數據分析
    ├ 身份別子分頁（全部／小黃／多元／多元試跑／未知，各帶人數）
    ├ KPI 五卡（參加者數・成長人數・成長趟數・成長承接率・成長上線時數；無「整體判斷」）
    ├ 活動條件與獎金結構（每日達標三條 AND ＋ 保底級距表 ＋ 超越級距表，依類型增減）
    ├ 逐日成效表（14 欄，表頭換行）
    ├ 指標趨勢（圖表卡隨類型與啟用條件增減）
    ├ 獎勵發放（總額大字 ＋ 保底／超越兩欄「逐日發放表」：日期・長條・金額・占比%）   ← 這一層就是關鍵
    └ 參加隊員清單（搜尋・可排序・分頁・兩個徽章 legend・點列進司機頁）
  ```

  **為什麼非附不可**：散文顆粒度只到「有哪幾個區塊」，區塊**內部**（上例的「兩欄逐日發放表」）會在下游拆票時整段蒸發，而下游看不出它蒸發了（案例見決議 017）。這份清單同時是三件事的分母：weave 拆驗收條件的分母、ship 的 Spec 軸逐條對照的分母、以及下一輪比對「上一輪定案過、這一輪不見了什麼」的基準。只生成一版的路徑，「生成了幾個方向」就照實寫「一版——照既有架構做，經使用者拍板不比方向」，其餘照寫。

  **⚠ 必附：預授權檔案清單**（同樣是這一輪新增的必記項，不是可選）。逐筆列出這次轉譯後還留著寫死範例值的檔案：**檔案路徑 → 預計由哪張票接真資料**。例如：

  ```
  app/(dashboard)/peak/PeakPageClient.tsx → T-012 接尖峰報表 API
  components/ActivityKpiCards.tsx → T-014 接 KPI 彙總 API
  ```

  **這份清單即 build 階段的預授權**：換掉寫死值、接真 API、加純資料用的 prop——這類不動版面、不動互動的改動，build 期照這份清單直接改，不必為此另外彈窗解凍；預授權取代的是彈窗、不是取代解凍動作，順序仍是①先把路徑從 `frozen` 移除、`log` 補一筆 `unfreeze`（`reason` 寫「依定稿記錄預授權：T-XXX 接真資料」，不必彈窗）→②改檔→③補回 `frozen`、`log` 補一筆 `refreeze`。**只有動到版面、互動、視覺，才走 `phase-build.md`「撞到凍結怎麼辦」那節的彈窗流程**——預授權只鬆綁「接資料」這一種改動，不是把整份凍結名單解開。
  **走了哪條路就寫在這段文字裡，這樣就夠了**——不為了追溯在 `.constellation/` 的任何檔案裡多開欄位（哪條路徑、哪個環境、工具版本、來源檔的雜湊、轉譯警告、誰核准的，一律不加）。那些欄位一加就得永遠餵它、永遠對賬，正是「流程本身不得成為工作量」要防的事（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。
  **這筆記錄在四條路徑上都一定要寫**——它同時是下游 weave 判斷「UI 已定稿」的依據（見本檔同目錄的 `phase-weave.md` 進場條件），少寫這筆會讓 weave 判定 UI 沒定稿、把任務又轉回本階段。它也是 `ticket-template.md`「目標」段落唯一例外提到的「design 定稿記錄」的來源——後續票要引用定稿的視覺／互動細節時，指到這筆決議即可。
- **定稿即凍結**（出處：母本 DESIGN.md §3「定稿即凍結」，部署後 runtime 不需讀取）：把全部定稿元件的檔案路徑（repo 相對路徑）寫入 `.constellation/design-frozen.json` 的 `frozen` 陣列，並在同檔的 `log` 陣列裡逐一補一筆：
  ```json
  { "path": "src/components/LoginForm.tsx", "action": "freeze", "at": "<ISO 時間戳>", "reason": "design 定稿" }
  ```
  **`frozen` 不得為空、且每個路徑都必須真的存在於 repo**——空名單或指到不存在的檔案，等於步驟 5 沒真的做，weave 進場的機器三驗會擋下並退回本階段（session 開場的哨兵也會印警示）。
  另外在同一個檔案記一個 **`source` 欄**，存這次定稿的取稿座標：Claude Design 的 `projectId` ＋ 實際取用的檔名清單（走路徑二、沒有雲端稿時寫 `null` 並註明是自己寫的）。日後走查照它取稿，不憑記憶找專案——曾經因為憑記憶找錯專案而誤判「當初的設計稿已被覆蓋、看不到了」，實際上稿一直都在，害得那次走查用錯的前提結案：
  ```json
  { "source": { "projectId": "<uuid>", "files": ["tab-detail.jsx", "tab-all.jsx"], "at": "<ISO 時間戳>" }, "frozen": ["…"], "log": ["…"] }
  ```
  `.constellation/design-frozen.json` 不存在就直接新建（`frozen` 與 `log` 兩個陣列都要有）——上一輪出貨時這份名單已經跟票一起歸檔進 `.constellation/archive/`（出處：母本 DESIGN.md §4，部署後 runtime 不需讀取），所以每一輪都是從空名單開始，開工時看不到這個檔案是正常的，不要去 `archive/` 把舊名單撈回來沿用。
  ⚠ **寫入 frozen 非空的那一刻會過「現況覆蓋閘門」**（close-gate）：`.constellation/design-baseline.json` 不存在、screens 為空、或任一 rework 畫面的 sources 空缺／路徑不存在，凍結動作會被直接擋下——被擋代表步驟 2 的現況覆蓋檢查沒做，回去補做而不是繞過。**從這一刻起，這些檔案受閘門 5（關票刷卡機）凍結保護**——實作期（build）任何工具想編輯這些檔案都會被機器擋下，不能悄悄改掉使用者已經看過拍板的畫面。
- **定稿後 UI 不再重畫**：後續拆出的每張票都對著這份定稿開發，不能因為某張票有新想法就回頭再跑一輪生成。build 階段若發現定稿漏了某個狀態（例如錯誤訊息、loading、空狀態）——沿用定稿的視覺語言把那個狀態補上，算票內部的「小事」，不用回頭重跑本階段；只有發現定稿的**整體結構方向**本身有問題（不是漏了一個狀態，是整個資訊架構要換），才算「大事」（出處：母本 DESIGN.md §8，部署後 runtime 不需讀取），停下彈窗問使用者要不要回頭重跑一次本階段。

## 路徑二：執行端自己寫畫面 code

**這是與路徑一（Claude Design）並列的一條路，不是降級。**兩條路的差別只在「誰動筆設計、使用者在哪裡調」：路徑一是它自己設計、使用者在 canvas 上調到滿意、再拉回 repo 轉譯落地，代價是要等雲端來回幾趟；路徑二是執行端直接改專案的正式 code、起本地 server，照步驟 5b 逐一點過、截圖發 Artifact 請使用者看圖拍板（瀏覽器工具或 Artifact 缺才給網址讓他自己點），改哪裡用文字講就好，代價是下面那句誠實話。**定版點（步驟 5b）兩條路一模一樣**，定稿記錄與凍結也一樣照跑。

**`design-taste.md` 是路徑二唯一的品質依據，動筆前必讀**（本檔同目錄）：路徑一有 Claude Design 自己的設計判斷兜底，路徑二沒有——版面構圖、間距節奏、層次、動效分寸全靠執行端自己拿捏，不讀那份就是憑感覺畫。它同時是交件前的機械自檢清單：畫面改完、交使用者拍板之前，照它掃一遍再交。

### 分流已前移：會走到本節的都是大工程

小／大工程的分流已在進場時做完（見前面「小工程直通」——那條不限走哪條路，小工程根本不會走到本節）；會走到這裡的都是大工程。

### 進場問一次：這次 UI 走哪條路

大工程進場、且確認路徑一此刻用得上時，照本檔同目錄 `phase-grill.md` 的提問格式問使用者一次（Claude Code 端走 AskUserQuestion 彈窗；Codex 端沒有彈窗，比照該檔的 Codex 降級規則改用文字點列。一次一題、2–4 個選項、每個選項用白話寫清楚後果與代價）：

- **路徑一：Claude Design**——它自己設計，你在 canvas 上看、留評論、轉旋鈕調到滿意，再拉回 repo 落成正式 code。代價是要等雲端來回幾趟。
- **路徑二：執行端自己寫**——直接改專案的正式 code、起本地 server，執行端點過、截圖給你看圖拍板（瀏覽器工具或 Artifact 缺才改給網址讓你自己點），要改哪裡用文字講就好，不必進 canvas。代價是下面這句。

**這次要講的代價（照實寫進選項說明）**：**執行端自己寫的那幾個版本，是同一個判斷的幾種寫法，不等於真的比較過不同方案**——看起來像「有比較過方案」，實際上可能只是同一個想法換幾種排法。

**這句誠實話是「選它之前該知道的代價」，不是「別走這條」的理由**：講清楚之後使用者仍選路徑二，那就是他要的路——照做，不再勸一次，也不把路徑二辦得比較潦草。兩個選項的推薦順序照這次任務的實情排，不是固定把路徑一排前面：`grill-close.md`「是否需要 UI」欄值是 `是（架構有得選）` 就推路徑一——這次本來就要比不同方向，讓它自己設計出幾個方向正是路徑一給得出、路徑二給不了的東西；欄值是 `是（照既有架構做）` 就推路徑二——資訊架構已經定了，這次只有一種合理排法，付雲端來回的成本換不到東西。**改造既有畫面（rework）不論欄值一律推路徑二**——改造型的落地硬規則本來就是改現有 code 的增量修改、絕不整頁重畫，繞一趟雲端拿回來的稿最後還是只能當參考。

### 路徑一此刻不可用時：只剩路徑二，一樣要開口講

**判斷依據是「工具此刻在不在、通不通」，不是「現在跑在哪個執行環境」**（出處：母本 DESIGN.md §9 降級表，部署後 runtime 不需讀取）。只要下面任一種成立，路徑一這次就走不了：沒網路、額度用完、當前執行環境裡沒有這個工具、工具掛在那裡但登入不通（例如以標準 MCP 方式掛載卻沒有走得完的登入方式——它不會自動繼承 claude.ai 的登入憑證）。

**不要按執行環境的品牌判斷「哪邊有、哪邊沒有」**：Claude Code 端離線、額度用完一樣用不上；反過來另一邊哪天掛上可用的工具、登入也通了，就用得上。按品牌判斷兩邊都會判錯，所以一律以「這次實際確認的結果」為準。

這種時候進場提問就不是兩條擇一、而是**只剩路徑二**，但仍然要開口，**不默默改成自己寫**：

1. **照實講路徑一這次為什麼走不了**——是哪一種（沒網路／額度／這個環境沒有這個工具／登入不通），不要含糊帶過。
2. **照實講路徑二的代價**——就是上面那句「同一個判斷的幾種寫法，不等於真的比較過不同方案」。
3. **給他一個真的還有得選的選項**（一次一題、2–4 個選項、白話寫清楚後果與代價；Codex 端改文字點列）：**換到有這個服務可用的環境**把這一步做完再回來——代價是要換環境、要等；換來的是真的由設計服務自己設計、在 canvas 上調到滿意。或者**就走路徑二**。這一題把「換環境」排第一並標推薦，因為只有那條真的補得回落差。

不要自己替使用者決定哪一條，也不要一聲不響就開始自己寫。

### 路徑二實際怎麼做

**預設先做一版，再用文字來回迭代出不同方向**，不要一次生 3 個版本擺出來讓人挑——理由就是上面那句：同一個判斷的幾種寫法不是真的比較，一次攤一堆只是把假選項攤開來。`grill-close.md` 記著 `是（架構有得選）` 也一樣先做一版，之後靠來回追問長出不同方向（「再給我一版側邊欄式的」「這次改成逐步精靈那種流程」）；記著 `是（照既有架構做）` 就更明確只有一版。**只有使用者明確說想一次看幾個不同方向**才做多版（上限 5），並在呈交時據實講明「這幾版是同一個判斷的不同寫法，不是真的比較過不同方案」。

1. 在專案裡直接改／寫真元件真 code（能跑能點，不是靜態圖），**照本檔同目錄 `design-taste.md` 做**——動筆前先判定這次的畫面屬於哪一類（該份的適用範圍那一段），再照它的量化規則排版面。真的要做多版時，各版的**結構要真的不同**——資訊架構／導覽模式／互動流程本身不同（卡片網格總覽／側邊欄列表＋詳情面板／逐步式精靈），不是換顏色字體交差。
2. **共用同一個視覺基底**：repo 已經有既有 UI 就沿用既有 code 的設計語言；一片空地就照 `design-taste.md` 的紀律**現場定出一組 tokens**（主色／背景／文字／邊框／狀態色、字級階層、間距節奏、圓角與陰影），**自己定、不問使用者**，定了什麼、為什麼這樣定寫進定稿記錄——除非使用者主動點名要某種調性，那就照他講的做。做多版時各版一起換掉配色，會讓「哪個結構好」被「哪個配色好」污染，所以基底一定要共用。
3. **優先掛在既有頁面**——空白路由是真空環境，脫離真實使用情境會讓每個版本都顯得好看。這個功能沒有對應的既有頁面（全新頁面）才退而求其次開一個新路由。做多版時用 `?variant=a`／`b`／`c` 參數切換；只有一版就不必加切換器。
4. **照步驟 5b 走，一字不減**：自己先預檢（**先照 `design-taste.md` 的機械自檢掃一遍**；沒有瀏覽器工具時照該步的降級做並誠實講明）→ **起本地 dev server（一樣經 `gates/serve.mjs` 起，它會先查該埠殘留）、照逐區塊元件清單逐一點過每個互動、整頁截圖，發私人 Artifact 請他看圖拍板**（瀏覽器工具或 Artifact 任一缺，才改給網址請他自己點）→ 他用文字講「要哪個、想改哪裡」→ 依回饋改 code → 反覆到滿意 → **他拍板才算定稿，拍完照樣 `stop` 並講明釋放了哪個埠**；「已改未重截」不算定稿。挑哪一版、改哪裡仍是使用者親自拍板的設計決策，不代為決定。路徑二少的只有「拉回雲端稿」那一步，**定版點兩條路一模一樣，一點都沒有放寬**。
5. 滿意即定稿——東西本來就在 repo 裡，**沒有拉回、也沒有轉譯這兩步**。做過多版的話清掉 `?variant=` 切換器與沒被選中的版本檔案，收尾時 repo 裡只留一份正式版本，沒有殘留的開關或死檔案。
6. 一樣照步驟 7 寫定稿記錄、一樣凍結。記錄裡照步驟 7 的第一項寫明「這次走的是哪條路、為什麼」（使用者選的，或路徑一此刻不可用是哪一種原因；小工程沒問使用者的就寫「小工程，直接改 code 給使用者看」），其餘照寫（基底是哪一套與為什麼／做了幾版與為什麼／使用者選了哪個／改了什麼）；**不為此新增任何欄位或檔案**。
- 「是否滿意、是否還要再調」這類封閉確認一次一題、2–4 個選項、白話寫清楚後果與代價：Claude Code 端用 AskUserQuestion 彈窗；Codex 端沒有彈窗，改用文字點列確認。
