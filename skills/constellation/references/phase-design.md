# Phase ② UI 定稿（design）

一句話：把這個專案的設計基底同步上 Claude Design → 讓 Claude Design 自己設計出這次要的畫面 → 使用者在它的 canvas 上調到滿意 → 拉回 repo、**直接改專案的正式頁面 code** → **開本地 dev server 請使用者親自點過拍板** → 才算定稿，定稿即凍結。

解決的根本問題是 mockup 與成品不符（出處：母本 DESIGN.md §3，部署後 runtime 不需讀取）。**定稿物＝專案裡真的改好、能用瀏覽器打開點完的正式畫面**——「canvas 上的稿」與「元件檔案存在於 repo」**兩者都不算定稿**；**沒有使用者在本地跑起來的畫面上點過並拍板，這一步就沒有完成**。落地手段仍是一次性轉譯（把它的檔案格式換成專案自己的元件格式），不是看著圖重畫；不可以宣稱「原封落地」（格式不同，一定要轉一次），但仍然遠勝「看著 mockup 重畫」。

> **這是 2026-08-13 使用者拍板收緊的條文，收緊原因請讀一次**（母本 DESIGN.md §3 有完整案例）：曾經有一輪寫完定稿記錄、宣稱已定稿，但**轉譯落地與凍結兩步根本沒做**（`_v2/` 只留空資料夾、那一輪連 `design-frozen.json` 都沒有），weave 只驗「有沒有定稿決議這筆檔」就放行，於是四個子分頁改由 build 照決議散文重畫——與談好的稿差了 12 個區塊，八天後才被使用者走查抓到。**病根是舊條文本身**：定版簽名簽在 canvas 的稿上，轉譯與凍結發生在使用者視野之外，做沒做他看不到。所以現在的定版點在**本地跑起來的正式畫面**上（步驟 5b），不在 canvas。

**方向感（這階段最容易走反的地方）**：Claude Design 的價值在於**它自己會設計**——官方定位是「你講你要什麼，它先做一版給你反應，你再一路改到它變成你的」。所以**不要**在本地先做好幾個版本再推上去讓使用者挑：那等於白繞一趟雲端，也浪費了它自己會設計這件事。大工程要自己寫畫面 code，只在「這次用不上 Claude Design」時才走（見最後的「降級路徑」）；小工程則一律直接改 code、不進產線（見「小工程直通」）。

## 進場 / 離場

- **進場條件**：本檔同目錄的 `phase-grill.md` 收尾時判定這次任務**需要 UI**（不是純後端／無 UI 任務），frontier 已清空、使用者已拍板。`decisions/grill-close.md` 的「是否需要 UI」欄值是 `是（架構有得選）` 或 `是（照既有架構做）`，**兩者都進場**——差別只在步驟 2 要不要請 Claude Design 生成多個方向讓使用者比較；同步基底、確認調整、拉回、轉譯、寫定稿記錄、凍結一律照跑。
- **進場後第一件事**：先分流小／大工程（見下方「小工程直通」）——小工程不論 Claude Design 可不可用都直接改 code、不進產線；大工程才確認這次到底用不用得上 Claude Design（見步驟 1 之前的前置判斷）。用得上就照步驟 1～7 走主線；用不上就走最後的「降級路徑」。
- **離場條件（五項全中才准離場，缺一項就是這一步沒做完）**：
  1. 使用者已在 canvas 上挑定並調到滿意（只生成一版的路徑沒有「挑」這個動作，改為看過這一版、講完要改哪裡並調到滿意）——**這一項只是設計方向確認，不等於定版**；
  2. 已**直接改專案的正式頁面 code**（步驟 5）——不是產一份放在旁邊的元件檔，也不是掛在暫時網址上的預覽版；
  3. **已開本地 dev server、使用者親自點過並拍板**（步驟 5b，唯一的定版點）；
  4. 定稿記錄已寫，且**附了逐區塊元件清單**（步驟 7）；
  5. 凍結名單已寫：`design-frozen.json` 的 `frozen` **非空**、且**每個路徑都真的存在於 repo**。
  才交給本檔同目錄的 `phase-weave.md`（它進場會用機器把第 4、5 項再驗一次）。
- **走降級路徑的離場條件**：沒有 canvas、沒有「拉回」這一步（東西本來就長在 repo 裡），**其餘五項一字不減**——尤其第 3 項（使用者在本地跑起來的畫面上親自點過拍板）在降級路徑同樣必須發生；定稿記錄另含「這次沒用上 Claude Design、原因是什麼、使用者選了哪條路」。
- **無 UI 任務**：本檔同目錄的 `phase-grill.md` 判定不需要 UI 時，本階段完全不運行，也不會去建立或動任何 Claude Design 專案，直接由 grill 交給 weave。

## 小工程直通（先於一切工具判斷，不限降級情境）

**不是所有跟畫面有關的工作都需要設計服務。**只改一個按鈕、修一個小地方、加一個欄位、在既有設計語言底下做單一元件、修畫面的 bug——這類**不論 Claude Design 此刻可不可用，一律直接改 code 給使用者看**（改完起本地 server、給他網址請他點；小工程的改動小到用截圖說得清時可以附截圖輔助，但**只要動到互動就要給網址讓他點**），不動用設計產線、也不必問要不要換環境；工具可用時把小工程推上產線，同樣違反「流程本身不得成為工作量」（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取；決議 012）。改完照「降級路徑」一節「使用者選『你自己寫』時怎麼做」的第 4 點往後走（給他看、依文字回饋改、滿意即定稿、寫記錄、凍結——定稿記錄寫「小工程，直接改 code 給使用者看」）。

**要走產線（或降級判斷）的是這幾種大工程**：新產品、全新頁面、資訊架構要重新決定、複雜的操作流程。（`grill-close.md` 記著 `是（照既有架構做）` 的需求多半落在小工程那一側，但「照既有架構做的全新頁面」或複雜流程仍算大工程——判斷依據是這次要決定的東西有多大，不是那一欄的值。）

## 這階段誰動手：多數步驟自己代操，只有一步非使用者親自不可

Claude Design **沒有可以程式呼叫的「生成」介面**——DesignSync 工具只有讀檔、寫檔、建專案那幾個方法，「生成畫面」與「在 canvas 上編輯」都只存在於網頁上。所以這階段會真的去操作瀏覽器好幾次，要分清楚哪幾次自己做完就好、哪一次一定要停下來等使用者（下面這張表講的是用得上 Claude Design 的主線；用不上時的分工見最後的「降級路徑」，但「哪一版、改哪裡由使用者親自拍板」這條在兩條路上都一樣）：

| 步驟 | 誰動手 |
|---|---|
| 1　推基底上去 | 自己（DesignSync 寫檔） |
| 1d 觸發編譯 | **自己代開瀏覽器**載入專案頁面（不載入就不會編譯），使用者不必在場 |
| 2　丟需求生成 | **自己代開瀏覽器**輸入需求、送出、等它畫完，使用者不必在場 |
| 3　方向確認與調整 | **⚠ 使用者親自**——挑哪一版、調哪裡是設計決策，不可代為拍板。**但這一步不算定版** |
| 4　拉回 repo | 自己（`get_file`） |
| 5　直接改專案的正式頁面 code | 自己 |
| **5b　開本地 dev server、使用者親自點過拍板** | **⚠ 使用者親自——這是唯一的定版點**。不可代為拍板、不可用截圖替代、不可跳過去寫定稿記錄 |
| 6／7　單向門、定稿記錄與凍結 | 自己（**前置：5b 的拍板已經發生**） |

所以實際節奏是：**先把基底推上去、把畫面生成好，然後才把使用者叫來**——給他 canvas 網址、告訴他手上有哪些工具（見步驟 3），請他看、調、或直接用文字講要改什麼（用文字講的話由自己動手改，不必逼他去拖拉）。方向定了之後**自己把正式頁面 code 改完、把本地 server 起好**，才第二次把使用者叫來——這次給的是**本地網址**，請他真的點（步驟 5b）。不要在步驟 1、2 進行中就把網址丟給使用者要他等；不要跳過步驟 3 自己覺得哪一版好看就往下走；**更不要跳過 5b 直接寫定稿記錄**——那正是 2026-08-03 那輪出事的位置。

**使用者要被叫來兩次，這是刻意的**：第一次確認「設計方向」（canvas），第二次確認「真的做出來的東西」（本地畫面）。少了第二次，「定稿」兩個字就沒有任何人驗過。

## 開工前先分清兩件事：基底哪裡來、要不要多個方向

這兩件事互不相干，各自有各自的決定方式，不要混成一題：

- **基底哪裡來＝事實，自己讀 repo 就知道，絕對不問使用者**（鐵律「事實不問人」，出處：母本 DESIGN.md §2，部署後 runtime 不需讀取）：repo 裡已經有能跑的畫面（既有頁面／元件／樣式）→ 基底就是既有 code 本身，把它真正的 tokens／可重用元件／全域 CSS／字型推上去；repo 是一片空地（全新專案、還沒有任何畫面）→ 才挑一套設計系統當起點。做法見步驟 1。
- **要不要多個方向＝真決策，使用者在訪談收尾已經拍板**：讀 `decisions/grill-close.md`「是否需要 UI」欄的值——`是（架構有得選）` 就在步驟 2 請 Claude Design 生成多個方向，`是（照既有架構做）` 就只生成一版。**這裡不重問**，值已經在檔案裡了。

兩件事交叉出四條路，實際走法：

| repo 有沒有既有 UI（自己探測） | grill-close.md 記的值 | 這階段怎麼走 |
|---|---|---|
| 沒有（空地） | `是（架構有得選）` | 挑一套設計系統推上去當基底 ＋ 請 Claude Design 生成多個方向讓使用者比較 |
| 沒有（空地） | `是（照既有架構做）` | 挑一套設計系統推上去當基底 ＋ 只生成一版 |
| 有 | `是（架構有得選）` | 把既有 tokens／元件／全域 CSS／字型推上去當基底 ＋ 生成多個方向 |
| 有 | `是（照既有架構做）` | 同上基底 ＋ 只生成一版，需求描述裡明講沿用既有的資訊架構 |

**這次是改造某個既有畫面時**（改版、重排、換互動方式）：把現況那幾個元件也一起推進設計系統當基底就好——生成時它會先讀設計系統再設計，自然會參考到現況長什麼樣。**不另外做「現況對照組」這種機制**；使用者真的想拿新舊並排看，就在 canvas 上跟現況畫面對照著看，或請 Claude Design 再生成一版貼近現況的版本。

## 步驟 1：把專案的設計基底同步上 Claude Design

這步的目的只有一個：**讓 Claude Design 設計的時候，用的是這個專案真正的東西，不是它自己想像的近似值**（官方原話是「用你真正的元件，不是近似品」）。做完這步，之後每一次生成都會先讀它、再設計。

> **這整步是手工做法**：官方的 `/design-sync` skill **目前在本機取不到**（實查：Claude Code 2.1.220 已是 npm 最新版本，安裝檔裡搜不到 `design-sync` 字串、官方 marketplace 沒有這個 skill、官方 changelog 從未提及）。所以下面的檔案結構與哨兵都是從 app 端行為反推出來的手工做法。**哪天官方 skill 真的可用了，本步驟應該直接改成呼叫它**，不要繼續維護手工版。

**動手推檔案之前，先確認這次到底用不用得上 Claude Design**：實際確認一次能不能把基底推上去、能不能開它的 canvas。**看的是「工具此刻在不在、通不通」，不是「現在跑在哪個執行環境」**——用不上的原因很多種（沒網路、額度用完、這個環境裡沒有這個工具、工具在但登入不通），任何一種成立就一律走最後的「降級路徑」，先告知使用者落差、讓他拍板，**不默默改成自己寫**。確認得出「用得上」才往下做 1a。

### 1a. 先確認要推的是「設計系統專案」

- 用 `list_projects` 找這個專案有沒有既有的 design system 專案；沒有就 `create_project` 新建（用它建出來的就是設計系統型別）。
- 推之前用 `get_project` 驗一下 `type` 是不是 `PROJECT_TYPE_DESIGN_SYSTEM`。
- **型別在建立時就固定、之後不能改**：不能拿一個普通專案（`PROJECT_TYPE_PROJECT`）充當設計系統，把檔案推上去它也不會變成設計系統，只是白推。

### 1b. 基底的內容從哪來

**A. repo 是一片空地（全新專案／還沒有任何畫面）** → 挑一套當起點：

- 若 `CONTEXT.md`／`decisions/` 裡訪談階段已經記錄使用者的風格偏好，直接沿用，不重問。
- 沒有既定偏好：兩種來源都可以，**挑哪一套是有取捨的真決策**，照本檔同目錄 `phase-grill.md` 的提問格式問使用者（走 AskUserQuestion 彈窗，2–4 個選項、推薦排第一、每個候選附一句「適合什麼調性」）：
  - 同目錄的 `design-systems/index.md`（150 套品牌設計系統資產庫）—— **lazy 只讀索引**，依這次任務的調性／受眾抓 2–3 個候選；使用者選定後才讀那一套的 `design-systems/<slug>/DESIGN.md`（9 段規範）＋ `tokens.css`（CSS 變數），其餘 149 套不讀。
  - Claude Design 內建的六套（Modernist／Classical／Nocturne／Organic／Broadsheet／Industry）——想要快、不想先攤一套完整 tokens 時用這條。
- 選定後把那套的 tokens 照下面 1c 的形狀寫成檔案推上去，做客製化延伸，不是套用預設樣式了事。

**B. repo 已經有既有 UI** → 基底就是既有 code 本身：

推上去的是**既有的 tokens、可重用元件、全域 CSS、字型**——**不是推做好的頁面**。不必反推、不必猜近似值，直接給真的東西最保真。實務上就是把 repo 裡的設計變數檔、共用元件、全域樣式、字型宣告整理成 1c 的形狀推上去；專案裡沒有集中的 tokens 檔就現場從既有樣式抽出那幾組值（主色／背景／文字／邊框／狀態色、字級階層、間距節奏、圓角與陰影、互動狀態的表現方式），寫成 `tokens.css` 推上去。

**不要為此在 repo 裡新增任何檔案**——設計系統的檔案活在 Claude Design 專案那邊，repo 這邊不留快照（快照會過期，既有 code 才是唯一真相，而且不新增檔案就不用維護它；流程本身不得成為工作量，出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。

**⚠ 基底用 code，需求不用 code——這是兩個不同的真相**：上面那句「既有 code 才是唯一真相」只適用於**視覺語言**（tokens、元件、全域樣式）。改造既有畫面時，現況 code 是**改版前**的狀態；「這一輪欄位要改成什麼、哪些欄位要拿掉」一律以**本輪決議**為準，兩者衝突時**決議勝出**。

把 code 裡的欄位清單（型別定義、表單狀態、驗證規則）直接餵給設計服務，等於把改版前的規格當成需求送出去——而且它會照著做、做得很像真的，事後看不出哪裡不對。

> 實例：某輪任務的決議已把表單第 1 組的「活動名稱／簡稱」兩個自由文字欄整個移除、改成兩個結構化必填欄位，也把另一組的欄位搬走大半；執行端卻在使用者反映「這組是幻想的」之後，去讀既有 `types.ts` 抄欄位餵過去，於是整組被做成**改版前**的樣子。使用者一眼看出：「我們不是討論了活動名稱不要……討論的你都忘光了嗎」。錯的不是設計服務，是餵進去的需求來源選錯了。

### 1c–1f. 檔案形狀、哨兵、驗證與呼叫坑（動手推檔前必讀）

**動手寫任何要推上去的檔案之前，先 Read 本檔同目錄的 `design-sync-details.md`**——app 端只認特定檔案形狀，形狀不對不會報錯、只會完全隱形；哨兵缺了前面全部白做。那份檔案是實測反編譯拿到的字面規則全集（樣式入口鏈、token 宣告位置、元件三件套、哨兵與編譯驗證、DesignSync 呼叫坑），照它逐條做完再回來走步驟 2。

## 步驟 2：把需求丟給 Claude Design 生成

- **動筆寫需求之前，先對每一張要設計的畫面做一次「決議覆蓋檢查」**——這是本步驟唯一能自己抓到「漏讀決議」的機制，不可跳過（憑印象挑決議一定會漏，而漏掉的那幾筆往往正是改動最大的那幾筆）：
  1. 列出 `.constellation/decisions/` 的**全部檔名**。檔名是英文 slug、語意可讀，例如 `079-activity-identity-without-name` 一眼就看得出跟「活動識別不用名稱」有關。
  2. **逐一判斷每個檔名與這張畫面有沒有關係**——判斷的依據是檔名，不是憑印象回想自己讀過什麼。
  3. 判定相關的**全部讀完**再動筆。交接檔（`HANDOFF.md`）點名的那幾筆只是起點，不是全集。
  4. 把「這張畫面對應哪幾筆決議」記下來；**後續每一輪修正都照同一份清單複查**，不要重新憑印象挑。
  漏讀的代價在本階段特別高：設計服務**不會空著讓你發現漏了**，它會補一個看起來完全合理的東西（抽查比例、二審流程、假的地區狀態…），不去查決議根本看不出是編的。
- 在 `https://claude.ai/design` 的輸入框描述這次要做的東西——內容來自訪談定版的決議（`CONTEXT.md`＋`decisions/*.md`），不是憑印象重寫一遍需求。`Design system` 欄選步驟 1 那個專案。
- 它會**先讀設計系統再設計**（實測畫面會顯示「I'll start by exploring the design system.」、「Listing files ×2, Reading ×3」這類動作）。
- **`grill-close.md` 記的是 `是（架構有得選）` → 要多個方向，就用它自己的迭代追問**（「再給我一版側邊欄式的」「這次改成逐步精靈那種流程」）。**不要回頭在本地手工做幾個變體**——那是舊流程，等於白繞一趟雲端。
- **記的是 `是（照既有架構做）` → 只生成一版**，並在需求描述裡明講沿用既有的資訊架構（例如「照現有的列表頁排法，只多一個狀態篩選器」）。需求本來只有一種合理排法時（列表加個篩選器、表格多一欄、表單多一個欄位），硬要多個方向只會生出沒人要的假選項，那是流程自己在製造工作量（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。
- 產出的檔名形如 `<Name>.dc.html`，住在它新建的一個**普通專案**（`PROJECT_TYPE_PROJECT`）裡，不是住在步驟 1 那個設計系統專案裡。
- **成本／效果的實測參考**（拿來設定預期，不是拿來吹）：一句需求描述換到的產出，比本地手工做三個變體完整得多——它自己補上了鍵盤快捷鍵、批次勾選、佇列分類與計數、作者歷史、垃圾自動篩選統計、三組快速回覆模板，並自己跑了一輪自檢把問題修掉。

## 步驟 3：使用者在 canvas 上確認設計方向（**這一步不算定版**）

請使用者去 canvas 上看，並講清楚他手上有哪些工具（多數人不知道 `Tweaks` 是什麼）：

- **`Comment`**：對特定元素留 inline 評論。
- **`Tweaks`**：**語意化的參數旋鈕**，來自設計稿裡宣告的 `data-props`——例如 `density: comfortable|compact`、`autoAdvance`、`showShortcuts`。它不是拖拉像素，是「這個畫面本來就設計成可以切換的那幾個選項」。
- **`Edit`**：圖層樹 ＋ 選取／文字／框線工具，有 `Simple`／`Pro`／`Code`／`Tweaks` 四種模式。
- **`Present`**／**`Share`**：全螢幕呈現與分享。

- **它自己生成的 `.dc.html` 支援直接編輯**；反過來說，**本地推上去的純 `.html` 卡片會顯示「This file does not support automatic edits. You can edit the preview; we will describe changes to Claude to apply on exit.」**——那條翻譯裂縫只存在於「本地推上去的檔」，不存在於「它自己生成的設計」。這正是新流程比「本地做好再推上去讓人挑」好的地方之一。
- 可以多輪來回，調到使用者滿意為止。滿意與否這類封閉確認照本檔同目錄 `phase-grill.md` 的規則走彈窗（Codex 端改文字點列）。
- **⚠ 這一步的點頭是「方向對了」，不是「定稿了」**：問法與回報用語都要照這個講（例如「這個方向可以往下做嗎」，不要問「這樣可以定稿嗎」）。真正的定版在步驟 5b——**專案 code 改完、本地跑起來、他點過**之後。這裡拿到點頭就直接寫定稿記錄，是本階段最容易犯、也最貴的一個錯（2026-08-03 實際犯過，代價是整輪 UI 與稿差 12 個區塊）。

## 步驟 4：拉回 repo

- 用 DesignSync 的 `get_file` 直接讀 `<Name>.dc.html`——**不需要任何匯出功能**。（`list_files` 對這種普通專案同樣有效，用來先看有哪些檔。）
- 一併拉 `_ds/<namespace>/_ds_manifest.json` 回來，當轉譯時的 token 對照表（設計稿裡用到的變數名對得回你的 tokens）。
- **`get_file` 單檔上限 256 KiB**；設計稿大到超過就分次拉相關檔案，不要以為是工具壞了。
- 拉回來的 `.dc.html` **轉譯完就不留在 repo 裡**（用暫存目錄接它，轉完刪掉）。不是因為它佔空間，是因為一份躺在 repo 裡的設計稿會讓人想「改設計稿再同步一次」——那正是步驟 6 要防的事。真的需要回頭看當初定稿長什麼樣，有兩層軌跡夠用了：定稿記錄寫了關鍵判斷，Claude Design 那個雲端專案原檔也還在。它不是工作流要追蹤的檔案，也不進凍結名單。

## 步驟 5：直接改專案的正式頁面 code（轉譯是手段，交付物是能跑的畫面）

**動手位置的四條硬規則**（2026-08-13 使用者拍板，原話：「你就要直接動手改了，改完以後開本地給我確認畫面，我同意之後你就接 API 這樣，反正我們不是有 git 版控，不行再復原」）：

1. **改的是正式檔案、正式路由**——不掛暫時網址、不開 `?variant=`、不做 `/preview/` 預覽區、不留新舊兩份並存。**保險是 git**，不行就復原。（理由：暫時位置永遠要多一次「扶正」，而扶正那一步一旦被跳過或做半套，就會出現「兩種品質的畫面並存」；某專案現在就是三塊 1:1 的元件與四頁重畫的舊面板並存。）
2. **不另建假資料檔層**（`mock-data.ts` 這種獨立假資料檔）。要假值就把最小範例值寫死在元件裡，build 接真 API 時整段刪掉——獨立假資料檔會被寫進凍結名單，事後刪它還得先走解凍流程，多一道純手續。
3. **資料來源看後端有沒有**：**後端已經存在 → 直接接真 API**（省掉「先假資料、再換真的」那一圈白工）；**後端還沒有 → UI 先做**、範例值寫死，並在定稿記錄記明哪幾處是寫死的、由哪張票換掉。順序是使用者定的：**先把 UI 做對，後端後接**。
4. **改完要能真的跑**：`pnpm dev`（或該專案的等效指令）起得來、頁面打得開、點得動。**留著「按了沒反應」的示意 stub 就不算改完**——那是 mockup 的行為，不是這一步的交付物。

`.dc.html` 是 Claude Design 專屬的 runtime 格式，**不能直接當專案元件用**，所以這一步的技術動作仍是轉譯。它長這樣：

```html
<x-dc>
  <helmet><script src="_ds/…/_ds_bundle.js"></script><style>…全域 CSS…</style></helmet>
  …template：純 HTML ＋ inline style 字串，用 {{ expr }} 綁值…
</x-dc>
<script type="text/x-dc" data-dc-script data-props="{…語意化參數定義…}">
  const DATA = [...];                    // Claude Design 產的假資料
  class Component extends DCLogic { state = {…}; renderVals() { return {…} } }
</script>
```

執行時它需要 `support.js`（dc-runtime）＋ `window.React`／`window.ReactDOM`——專案端不需要這些，轉譯就是把它換成專案自己的寫法。

**動手轉譯前，先 Read 本檔同目錄的 `design-translate-details.md`**——完整轉譯對應表（多數語法機械對應；唯一真正機械化不了的是動態 inline style 拼接字串要拆成 class modifier）、兩個必踩陷阱（inline style 打敗 `:hover`、假資料要換真 API）與成本實測都在那份，照表逐項轉。

改完**自己先預檢一次**再交件——不要只憑「我照表轉完了」就宣告完成：

- **手上有瀏覽器工具時**（Claude Code 端多數情況）：自己把頁面打開，對照設計稿逐區塊看一眼、點幾個互動，確認長得一樣、點得動。
- **手上沒有瀏覽器工具時**（Codex 端裸 CLI 沒有內建瀏覽器，見母本 §9 降級表與 §11.5）：降級為「打 HTTP 確認頁面回 200 ＋ 關鍵區塊的標記真的出現在回傳的 HTML 裡」＋跑既有的元件 render 測試；**交件那句話必須誠實講明「我沒有親眼看過渲染結果，破圖請直接說」**。不得因為看不到就跳過預檢，也不得假稱看過。

**預檢是給自己抓破圖用的，不能取代步驟 5b**——5b 那次是**使用者親自點**，兩件事不可互相頂替。

## 步驟 5b：開本地 dev server，請使用者親自點過拍板（**唯一的定版點**）

這一步的存在理由：**「定稿」這兩個字必須有人在真的畫面上驗過**。舊條文把使用者的拍板放在 canvas（步驟 3），轉譯與凍結全發生在他視野之外——做沒做他都看不到，於是出現過「定稿記錄寫好了、`_v2/` 只有一個空資料夾」這種事。

怎麼做：

1. **起本地 server**：用該專案自己的指令（`pnpm dev`／`npm run dev`／等效），背景執行，拿到本機網址。起不來就先修到起得來——**這一步不能用「我改好了但跑不起來」交件**。
2. **自己先預檢**（見步驟 5 末尾那兩條，含無瀏覽器時的降級）。
3. **把網址交給使用者，明確請他點**，並列出**這次要請他看的清單**：哪幾個頁面、哪幾個子分頁、哪幾個互動（按鈕、彈窗、切換、空狀態）。清單要照著步驟 7 的逐區塊元件清單列——**他點過的範圍就是被定版的範圍**，沒列到的區塊等於沒人驗過。
4. **等他拍板**（Claude Code 端 AskUserQuestion 彈窗；Codex 端照母本 §9 降級為文字點列）。他要改就改完再請他看一次，多輪來回都可以。
5. **拍板通過，才准往步驟 6、7 走**。

硬規定：

- **不可代為拍板**——執行端自己覺得「跟稿長得一樣」不算數。
- **不可用截圖替代**：截圖點不動，看不出互動有沒有真的接上；使用者要抓的正是「按了沒反應」這種事。手上沒有瀏覽器工具時也一樣——那影響的是**執行端的預檢**，不影響使用者拿自己的瀏覽器點（這一步跟 runtime 無關，兩邊一模一樣，不降級）。
- **不可跳過去寫定稿記錄或凍結**。沒有這次拍板，`decisions/` 的定稿記錄與 `design-frozen.json` 都不准動；weave 進場另有機器三驗兜底（見 `phase-weave.md` 進場條件），跳過會在那裡被擋下並退回本階段。
- **代價要誠實記著**：這一步讓每輪 design 多一次「等使用者有空點」的來回，流程會變慢。這個錢是刻意付的（母本 §11.5 有記），不要為了省它而自己拍板。

## 步驟 6：這是單向門（本階段最重要的一條紀律）

轉譯完成後，**專案裡的元件 code 就是唯一真相**，`.dc.html` 降為參考資料。**不建立任何「回頭同步」機制。**

理由要講明白：設計稿第二次改動時，轉換器的輸出會覆蓋掉手工命名的 class 樹與 modifier 結構，**第二次以後比第一次更貴**，不是更便宜。要再改 UI 就走這兩條路：

- **解凍既有元件、直接改 code**（改動不大時；解凍流程見本檔同目錄的 `phase-build.md`「撞到凍結怎麼辦」）。
- **重跑一次本階段，產一份新的一次性設計稿**（整體結構要換時）。

不做雙向同步——那正是母本 §0 反教訓要防的機制膨脹。

## 步驟 7：收尾——寫定稿記錄、定稿即凍結（**前置：步驟 5b 的使用者拍板已經發生**）

- 收尾寫一筆 `decisions/NNN-slug.md`（**定稿記錄是 decisions 的特例格式**——不套「背景＋決定＋原因＋證據」四要素，用下列自己的欄位；定稿脈絡本身就是拍板證據，不必重複填），記這幾件事：**這次有沒有用上 Claude Design、為什麼**（用上就一句話帶過；用不上就照實寫是哪種原因——沒網路／額度／這個環境沒有這個工具／登入不通——以及使用者選了哪條路；屬於「小工程直接做、沒問使用者」的就照實寫「小工程，直接改 code 給使用者看」）、**用了哪一套設計系統當基底**（既有 code 的 tokens／元件，或資產庫／內建的哪一套）、**需求是怎麼描述給 Claude Design 的**、**生成了幾個方向**、**使用者選了哪一版**、**在 canvas 上調了什麼**、**轉譯時做了哪些判斷**（動態 style 怎麼拆、class 怎麼命名、哪些 Tweaks 參數在專案端沒有對應物、哪裡還接著寫死的範例值與由哪張票換掉）、**使用者是在哪個本地網址上點過拍板的、當時請他看了哪些頁面與互動**（步驟 5b 那份清單照抄）、以及下面這項——

  **⚠ 必附：逐區塊元件清單**（這一輪新增的必記項，不是可選）。格式是三層：**畫面 → 區塊 → 區塊內部元素與互動**，從剛改好的 code 機械抽出（元件函式名＋JSX 結構就是清單，不要憑印象重寫）。例如：

  ```
  單一活動／數據分析
    ├ 身份別子分頁（全部／小黃／多元／多元試跑／未知，各帶人數）
    ├ KPI 五卡（參加者數・成長人數・成長趟數・成長承接率・成長上線時數；無「整體判斷」）
    ├ 活動條件與獎金結構（每日達標三條 AND ＋ 保底級距表 ＋ 超越級距表，依類型增減）
    ├ 逐日成效表（14 欄，表頭換行）
    ├ 指標趨勢（圖表卡隨類型與啟用條件增減）
    ├ 獎勵發放（總額大字 ＋ 保底／超越兩欄「逐日發放表」：日期・長條・金額・占比%）   ← 這一層就是關鍵
    └ 參加隊員清單（搜尋・可排序・分頁・兩個徽章 legend・點列進司機頁）
  ```

  **為什麼非附不可**：散文顆粒度只到「有哪幾個區塊」，區塊**內部**（上例的「兩欄逐日發放表」）會在下游拆票時整段蒸發，而下游看不出它蒸發了——2026-08-03 那輪的定稿記錄把七個區塊名字寫得很完整，於是完全合規地漏掉了「獎勵發放裡面長什麼樣」，拆票時那一段連一條驗收條件都沒有。這份清單同時是三件事的分母：weave 拆驗收條件的分母、ship 的 Spec 軸逐條對照的分母、以及下一輪比對「上一輪定案過、這一輪不見了什麼」的基準。只生成一版的路徑，「生成了幾個方向」就照實寫「一版——照既有架構做，經使用者拍板不比方向」，其餘照寫。
  **走了哪條路就寫在這段文字裡，這樣就夠了**——不為了追溯在 `.constellation/` 的任何檔案裡多開欄位（哪條路徑、哪個環境、工具版本、來源檔的雜湊、轉譯警告、誰核准的，一律不加）。那些欄位一加就得永遠餵它、永遠對賬，正是「流程本身不得成為工作量」要防的事（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。
  **這筆記錄在四條路徑上都一定要寫**——它同時是下游 weave 判斷「UI 已定稿」的依據（見本檔同目錄的 `phase-weave.md` 進場條件），少寫這筆會讓 weave 判定 UI 沒定稿、把任務又轉回本階段。它也是 `ticket-template.md`「目標」段落唯一例外提到的「design 定稿記錄」的來源——後續票要引用定稿的視覺／互動細節時，指到這筆決議即可。
- **定稿即凍結**（出處：母本 DESIGN.md §3「定稿即凍結」，部署後 runtime 不需讀取）：把全部定稿元件的檔案路徑（repo 相對路徑）寫入 `.constellation/design-frozen.json` 的 `frozen` 陣列，並在同檔的 `log` 陣列裡逐一補一筆：
  ```json
  { "path": "src/components/LoginForm.tsx", "action": "freeze", "at": "<ISO 時間戳>", "reason": "design 定稿" }
  ```
  **`frozen` 不得為空、且每個路徑都必須真的存在於 repo**——空名單或指到不存在的檔案，等於步驟 5 沒真的做，weave 進場的機器三驗會擋下並退回本階段（session 開場的哨兵也會印警示）。
  另外在同一個檔案記一個 **`source` 欄**，存這次定稿的取稿座標：Claude Design 的 `projectId` ＋ 實際取用的檔名清單（走降級路徑、沒有雲端稿時寫 `null` 並註明是自己寫的）。日後走查照它取稿，不憑記憶找專案——曾經因為憑記憶找錯專案而誤判「當初的設計稿已被覆蓋、看不到了」，實際上稿一直都在，害得那次走查用錯的前提結案：
  ```json
  { "source": { "projectId": "<uuid>", "files": ["tab-detail.jsx", "tab-all.jsx"], "at": "<ISO 時間戳>" }, "frozen": ["…"], "log": ["…"] }
  ```

## 降級路徑：這次用不上 Claude Design

**觸發條件是「工具此刻在不在、通不通」，不是「現在跑在哪個執行環境」**（降級表出處：母本 DESIGN.md §9，部署後 runtime 不需讀取）。只要下面任一種成立，就算「這次用不上」，一律走本節：沒網路、額度用完、當前執行環境裡沒有這個工具、工具掛在那裡但登入不通（例如以標準 MCP 方式掛載卻沒有走得完的登入方式——它不會自動繼承 claude.ai 的登入憑證）。

**不要按執行環境的品牌判斷「哪邊有、哪邊沒有」**：用不上的情況不是只發生在某一邊——Claude Code 端離線、額度用完一樣用不上；反過來另一邊哪天掛上可用的工具、登入也通了，就用得上。按品牌判斷兩邊都會判錯，所以一律以「這次實際確認的結果」為準。

**這是降級路徑，不是主線**——真的用得上就不要走這條，因為這條等於放棄「讓它自己設計」這件事。

### 大工程又用不上時：先告知落差、讓使用者選，不默默降級

用白話講清楚三件事，然後請使用者拍板：

1. **這次用不上 Claude Design，以及為什麼**——照實講是哪一種（沒網路／額度／這個環境沒有這個工具／登入不通），不要含糊帶過。
2. **落差在哪，而且必須誠實講出這一句**：**執行端自己寫幾個版本給人挑，那幾個版本是同一個判斷的幾種寫法**——看起來像「有比較過方案」，實際上可能只是同一個想法的幾種寫法，不等於真的探索過不同方案。所以**不可以把「自己寫」包裝成與 Claude Design 對等的替代方案**。
3. **兩個選項讓他選**（Claude Code 端走 AskUserQuestion 彈窗；Codex 端沒有彈窗，比照本檔同目錄 `phase-grill.md` 的 Codex 降級規則改用文字點列。照該檔的提問格式：一次一題、選項附白話後果、把「換環境」排第一並標推薦，因為只有那條真的補得回落差）：
   - **換到有這個服務可用的環境**，把這一步做完再回來——代價是要換環境、要等；換來的是真的由設計服務自己設計、使用者在 canvas 上調到滿意。
   - **不換，由執行端自己寫畫面 code**，用文字來回修到滿意——代價就是第 2 點那句話：不等於真的比較過不同方案。

不要自己替使用者決定哪一條，也不要一聲不響就開始自己寫。

### 使用者選「你自己寫」時怎麼做

**預設先做一版，再用文字來回迭代出不同方向**，不要一次生 3 個版本擺出來讓人挑——理由就是上面那句：同一個判斷的幾種寫法不是真的比較，一次攤一堆只是把假選項攤開來。`grill-close.md` 記著 `是（架構有得選）` 也一樣先做一版，之後靠來回追問長出不同方向（「再給我一版側邊欄式的」「這次改成逐步精靈那種流程」）；記著 `是（照既有架構做）` 就更明確只有一版。**只有使用者明確說想一次看幾個不同方向**才做多版（上限 5），並在呈交時據實講明「這幾版是同一個判斷的不同寫法，不是真的比較過不同方案」。

1. 在專案裡直接改／寫真元件真 code（能跑能點，不是靜態圖）。真的要做多版時，各版的**結構要真的不同**——資訊架構／導覽模式／互動流程本身不同（卡片網格總覽／側邊欄列表＋詳情面板／逐步式精靈），不是換顏色字體交差。
2. **共用同一個視覺基底**（既有 code 的設計語言，或挑定的那一套）——一起換掉配色會讓「哪個結構好」被「哪個配色好」污染。
3. **優先掛在既有頁面**——空白路由是真空環境，脫離真實使用情境會讓每個版本都顯得好看。這個功能沒有對應的既有頁面（全新頁面）才退而求其次開一個新路由。做多版時用 `?variant=a`／`b`／`c` 參數切換；只有一版就不必加切換器。
4. **照步驟 5b 走，一字不減**：自己先預檢（沒有瀏覽器工具時照該步的降級做並誠實講明）→ **起本地 dev server、把網址交給使用者、列出請他看的頁面與互動清單、請他親自點** → 他用文字講「要哪個、想改哪裡」→ 依回饋改 code → 反覆到滿意 → **他拍板才算定稿**。**不可只給截圖**（點不動，驗不到互動有沒有接上）；挑哪一版、改哪裡仍是使用者親自拍板的設計決策，不代為決定。降級路徑少的只有「拉回雲端稿」那一步，**定版點一點都沒有降級**。
5. 滿意即定稿——東西本來就在 repo 裡，**沒有拉回、也沒有轉譯這兩步**。做過多版的話清掉 `?variant=` 切換器與沒被選中的版本檔案，收尾時 repo 裡只留一份正式版本，沒有殘留的開關或死檔案。
6. 一樣照步驟 7 寫定稿記錄、一樣凍結。記錄裡照步驟 7 的第一項寫明「這次沒用上 Claude Design、原因是什麼、使用者選了哪條路」（小工程沒問使用者的就寫「小工程，直接改 code 給使用者看」），其餘照寫（用了哪套基底／做了幾版與為什麼／使用者選了哪個／改了什麼）；**不為此新增任何欄位或檔案**。
- 「是否滿意、是否還要再調」這類封閉確認，Claude Code 端用 AskUserQuestion 彈窗；Codex 端沒有彈窗，比照本檔同目錄 `phase-grill.md` 的 Codex 降級規則改用文字點列確認。
