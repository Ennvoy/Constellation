# Phase ⑤ 出貨（ship）

一句話：全量真跑一次，再用兩個互不參考的視角各審一次跨票與整體，所有發現當場結案才出貨。

## 進場 / 離場

- **進場條件**：所有票（或小流程單一任務卡；`next-round/` 有票併入時，這些票各自獨立，也要算進「所有票」一起 `status: done`）。
- **離場條件**：全量驗證綠燈 ＋ 本輪啟用的各審查軸都沒有阻擋級發現（或發現已修完、複驗綠燈）＋ **本輪所有發現都已結案**（修掉／丟掉並寫了理由／使用者當場決定，見下方「發現的處理」；build 期各批審查的發現也算）→ 出貨報告產出，流程結束。出貨報告裡唯一允許的延後項，是使用者在彈窗親口選了「下輪做」的那幾件。
- **不等別批上線**：進行中的別批不是本輪開跑或推送的前提，誰先驗完誰先上；推送前確認正式站基底、主線有別批未上線 commit 時另開工作區、併入對方後重跑全量，照總控 `SKILL.md`「不等進行中的批次」（決議 032）。

## 步驟 1：全量真鏈路驗證

- 跑法：驗證 runner 絕對路徑由 session 開場注入提供（閘門 3 開場會印出這個路徑）；session 沒印出注入路徑時，用 install 部署的母本路徑 `<母本>\gates\verify-runner.mjs`。執行 `node <runner 絕對路徑> --scope ship`——一次跑齊 `.constellation/config.json` 裡登記的**全部** `commands.journey`，加上 `commands.test` 的完整回歸——不是只挑被改到的部份。
- **機器鎖／排隊（跨 session 共用一台機器時）**：`--scope ship` 開跑前 runner 自動向 `gates/lease.mjs`（與 runner 同目錄，登記檔在 `~/.constellation/leases/`）取 `machine` 資源鎖；機器被別的 session 的全量佔用時自動排隊等待，輪到自己就自動開跑，跑完照常觸發背景完成通知——不必等對方傳訊息才手動開跑。**runner 只能由主 session 用背景執行（`run_in_background`）起**：不放進 Workflow 子代理（子代理交卷會把它一起結束，通知也跟著沒了），也不用 `Start-Process` 之類脫離終端機的做法（脫離的行程收不到背景完成通知）。排隊中（尚未印出「開跑」那一行）可以先停掉，把手上的修正落地後再重新排一次；一旦印出「開跑」，就進入下方「一開跑就不准中途砍」的規則，不再分排隊或已跑。**起了 runner 之後**看一次 `node <lease.mjs 絕對路徑> list`，在正文講明目前是被誰持有（專案／用途）、依它的預估結束時間大約幾點輪到——**沒有排隊目錄，查不到、也不必講「目前排第幾」**（誰先 poll 到誰先接手，不是先到先贏的隊伍），只寫「排隊中」同樣不算講清楚，至少要點名持有者與大約幾點輪到。**逾時（代碼 3）**：等到 `--max-wait`（預設 4 小時）都還被佔用時 runner 會以代碼 3 結束——這不是紅燈、不計入斷路器、也不寫任何失敗紀錄，回報「等太久，先處理別的，稍後重新排一次」即可，不當成出貨驗證失敗處理。鎖本身怎麼登記、失效怎麼判定，是 `lease.mjs` 的程式行為，這裡不重複（見母本 DESIGN.md §5／§7，案例見決議 026）。
- 跟逐票驗證的差異：逐票只驗那張票驗收條件涉及的部份，範圍窄；這裡是全量。
- 一樣走真鏈路：真點擊（Playwright）、真 API、真 DB 讀回，不能用 mock。
- **證據落點**：`--scope ship` 這次跑出的全量證據，由 runner 簽章寫入 `.constellation/ship-evidence.md`（跟逐票證據寫進各票檔不同，全量證據集中這一份）——下面「出貨報告」的「證據在哪」就是指向這份檔案，不是要求審查者自己東拼西湊。跑紅的輪次也會寫進同一份檔案（指令、紅在哪、耗時），但標記「未簽章」；最終出貨依據的證據，只認同一次完整全綠的簽章那一筆。
- **預期超過 10 分鐘就背景跑、且一開跑就不中途砍**：全量驗證預期（或上輪實測）超過約 10 分鐘時，以背景執行方式跑，期間先平行開步驟 2 的兩軸審查——兩軸互不參考、也不依賴驗證結果，天然可與驗證平行；證據照常由 runner 簽章落檔。**runner 沒有優雅中止的路，背景全量一旦開跑就不准中途砍**（砍了收尾不會跑，正式庫可能留下殘留、還會白吃一次斷路器失敗次數；排隊等鎖的階段不算「開跑」，見上一點）。審查若在全量跑完前就先抓到阻擋級發現，也讓全量跑完再處理——等待期間可以定位根因、擬修法，但改動要等全量結束才落到工作樹，期間也不跑會寫 DB 的測試；紅燈的收尾走下一條的書擋節奏。
- **有任何一條紅——全量只當書擋，不當除錯迴圈**：**runner 遇到第一條紅就停，後面排隊的指令不會執行**，清單只涵蓋這一條——不是「一次紅燈跑完就等於拿到所有壞掉項目的完整清單」；這條紅若不是資料保險或環境類警報、且其餘 journey 彼此獨立，才值得另外用測試框架把還沒跑到的那幾個 journey 跑一次換一份較完整的清單，runner 失敗時也會多印一行「以下指令因前一條紅燈未執行：…」。**紅了先單跑紅的那幾支**（指名檔案或 `--last-failed`）：單跑就綠的視為假紅燈（冷站、並行互撞、計時型斷言、資源或記憶體不足、資料保險誤報或殘留這類），不拿整套重跑來確認它是假的——記成一條發現，照下方「發現的處理」結案：本輪造成的當輪修；既有的照「既有問題」問使用者現在修或記進 MAP。最終那趟要同一次完整全綠才能簽章，留著它最終那趟可能再紅，所以預設當輪修。單跑仍紅的才進修復（決議 032）。修復期間只用秒級迴圈驗單點——測試框架的「只重跑上次失敗」（如 Playwright `--last-failed`）或指名失敗的那幾個檔案，修一條驗一條，修法本身走本檔同目錄的 `phase-build.md` 節奏；**不得每修一個問題就重跑一次全量**——全量整合套件動輒數十分鐘，N 個問題會付 N 次全價；整套只跑開頭與最終各一趟。全部單點轉綠後，回來重跑一次全量拿正式證據。**不得「沿用上次的綠燈、重跑時跳過已綠的套件」**——為修 A 動的 code 可能弄壞 B，最終證據必須來自同一次完整全綠。也不要帶著已知的紅燈去做下一步的審查——審查是相對貴的動作，值得先確認能全部跑過再花時間審。

## 步驟 2：獨立各軸審查

- 另開乾淨 context 進行審查，不沿用 build 期累積的對話記憶——避免「這是我剛寫的，看起來沒問題」這種確認偏誤。
- **Standards 軸審查定錨——只審本輪 diff**：基準自動取上輪出貨歸檔那個 commit（`git log -1 --format=%H -- .constellation/ship-report.md ':(glob).constellation/archive/*/ship-report.md'`；首輪沒有就全 repo）——流程外改 `HISTORY.md` 不會讓它後移（決議 032），審查範圍＝`git diff <基準>...HEAD`。**開審前先在主線驗兩件事**——基準能解析、diff 非空；任一不成立先停下查清楚（歸檔異常或真的沒改動），不把壞基準帶進獨立審查 context 空燒一輪。Spec 軸不受此限（它以本輪決議逐款為圈）。
- **只看跨票與整體層面**：單張票、單批的程式品質與驗收條件，已經在 build 每批整合完成後審過（見本檔同目錄 `phase-build.md`「每批整合後的獨立審查」），這裡不重審一遍；出貨審的是只有整輪串起來才看得到的東西。**例外：小流程**（單一任務卡，build 期不跑批次審查）的輕量⑤，兩軸照舊涵蓋任務卡與併入票本身的程式品質與逐條驗收。
- **只回報寫得出具體後果的發現（兩軸與條件觸發軸皆適用）**：每條發現都要寫得出「在什麼情況下會出什麼錯」（例如「兩張票各自存一份金額換算，其中一份沒四捨五入，月報加總會差 1 元」）；寫不出具體後果的純異味、註解、用詞、「可以寫得更好」一律不回報——這條隨審查指派原文帶給審查員。
- 兩軸**平行**跑、**分開報告**，禁止合併排名選出一個「總贏家」——這兩軸問的問題本質不同，硬湊成一個分數沒有意義：
  - **Standards 軸**：只看 code 品質，範圍鎖定上面定錨的本輪 diff，重點放在跨票層面——同一形狀的邏輯在不同票各寫一份、票與票之間的共用介面或資料格式對不上、整體結構因這輪變得難改。優先套用這個 repo 自己既有的規範（lint 設定、既有 style、命名慣例）；repo 規範沒覆蓋到的地方，才退回 baseline——即下方「固定 12 條 smell 清單」，**隨審查指派把清單原文帶給 Standards 軸**（獨立 context 沒有其他管道拿到它）。三條判定規則：①repo 已文件化／lint 化的規範永遠壓過 baseline，衝突時以 repo 為準；②typecheck／lint 等工具已強制的不重複報；③baseline **命中且寫得出具體後果才報**，報了一律標「judgement call」（與 repo 規範硬違規分開列）。另掃本檔同目錄 `verification-playbook.md`「真鏈路也要快」的效率鐵則，違反且寫得出具體後果（例如「每支測試各自重登入，全量多花約 N 分鐘」）才報。**報告紀律（兩軸皆適用）**：每軸以 400 字為度、結尾一行摘要（發現數＋該軸內最嚴重一條）；依舊分開報告、不合併排名。
  - **Spec 軸**：整體對照，拿原始來源比、不拿票比（逐票的驗收條件已在 build 每批審過；票是決議的轉譯，轉譯時漏掉或走樣的款，對照票抓不到，決議 032）。**分母**：本輪決議原文逐款（`grill-close.md` 之後落的 `decisions/NNN-slug.md`，含 `decisions/engineering-defaults.md` 逐條）、定稿記錄的逐區塊元件清單（有 UI 時）、本輪需求的源頭原文（使用者原話、需求單）——源頭原文只認有落檔的（決議證據欄的使用者原話、repo 裡的需求單），與後來的決議不同時以決議為準、不算對不到；票只當找 code 的索引。每款寫出哪段 code 或哪個畫面做到、用什麼確認（逐款對照表附在該軸報告後，不計入 400 字）；對不到、或做出來的意思與原文字面不同，即阻擋級。另看跨票的使用流程從頭走到尾接不接得上；身分路徑只確認決議提到的每種身分都有走查紀錄，不新增走查活動。不管 code 寫得好不好看。另外核對 `.constellation/design-frozen.json` 的 `log`——每筆 `unfreeze` 都應有對應的使用者同意脈絡可查（例如某張票的決議記錄提到這次解凍、或彈窗確認的紀錄）；有 `unfreeze` 卻找不到對應同意脈絡的，列為阻擋級發現（出處：母本 DESIGN.md §3「定稿即凍結」，部署後 runtime 不需讀取）。**核對範圍就是本輪的 `log`**——這份名單隨輪歸檔（見步驟 3），現存檔案裡看到的 `unfreeze` 一定是本輪發生的、對應的票也一定還在 `tickets/` 裡找得到；不必也不該跑去 `archive/` 翻上一輪的紀錄來核對。
- 兩軸各自輸出自己的 findings 清單，不互相參考、不互相調整對方的結論。
- **第三、四軸（條件觸發）**：讀 `decisions/grill-close.md` 的高風險標記，命中對應標記才加開對應軸，與前兩軸同樣平行跑、分開報告；一般任務不加開：
  - **security 紅軍**（標記「有」，涉權限／金流／個資）：另一個獨立 context 以攻擊者視角**實測**攻擊面（越權存取、參數竄改、注入、金額運算邊界、個資外洩路徑），不是看 code 推測——能實際打 API／操作 UI 重現的才算 confirmed。
  - **效能實測**（標記含「大量資料」）：以接近票面寫的 N 筆量級的資料（測試活動、匯入真資料快照、或正式庫唯讀量測）實測每張標了量級門檻的票的「在 N 筆下 < X 秒」，量不過關列阻擋級。

### Standards 軸 baseline：固定 12 條 smell（症狀 → 修法方向）

出自 Fowler《Refactoring》ch.3 選集，逐條「是什麼→怎麼修」；對照 diff 判讀，**命中且寫得出具體後果（在什麼情況下會出什麼錯、或下一次改動會被卡在哪）才報**，只是「看起來有這個味道」不報；報了一律是 judgement call。build 每批審查與這裡共用同一份清單：

- **Mysterious Name（名不副實）**：函式／變數／型別的名字看不出它做什麼、裝什麼 → 改名；取不出誠實的名字代表設計本身混濁。
- **Duplicated Code（複製貼上）**：同一形狀的邏輯出現在改動的多個 hunk／檔案 → 抽出共用形狀，兩邊呼叫它。
- **Feature Envy（戀慕他物）**：方法伸手拿別的物件的資料多過用自己的 → 把方法搬去它戀慕的資料那邊。
- **Data Clumps（資料結伴）**：同幾個欄位／參數總是結伴出現 → 收成一個型別，傳它。
- **Primitive Obsession（原始型別硬撐）**：字串／數字硬代一個該有自己型別的領域概念 → 給概念立一個小型別。
- **Repeated Switches（重複分支）**：對同一型別的 switch／if 串在改動中反覆出現 → 多型，或共用一張對照表。
- **Shotgun Surgery（散彈手術）**：一個邏輯改動迫使 diff 散落多檔零碎修改 → 把會一起變的聚進同一模組。
- **Divergent Change（理由發散）**：同一檔／模組因多個不相干理由被改 → 拆開，讓每個模組只因一種理由變。
- **Speculative Generality（投機通用化）**：為 spec 沒有的需求加抽象／參數／hook → 刪掉；真需求出現前先內聯回去。
- **Message Chains（連環呼叫）**：呼叫端依賴 a.b().c().d() 的長鏈導覽 → 首物件上包一個方法藏起這段路。
- **Middle Man（中間人）**：類別／函式幾乎只是轉手委派 → 砍掉，直接呼叫真目標。
- **Refused Bequest（拒絕遺產）**：子類忽略或覆寫大部分繼承物 → 放棄繼承，改用組合。

## 發現的處理

照總控 `SKILL.md` 紀律「發現當場結案，不往後丟」（決議 031），每條 finding 先分**誰該決定**，再照下表結案——不限這兩軸審查，出貨階段（含全量紅燈、推送後正式站檢查、上線日觀察）看到的任何事都照這張表走：

- **執行端能決定的**（程式品質、小 bug、測試、註解、用詞）：
  - **阻擋級**（不修就會出貨出問題：驗收條件沒做到、明顯 bug、安全或資料風險）——只能修，不能丟；修完、針對受影響範圍複驗綠燈，才能出貨。
  - 其餘——當場修掉（併入下面的批次修復一起複驗）；或判斷不值得修就丟掉，在出貨報告「驗了什麼」段寫一句理由。**不開票**。
- **要使用者決定的**（方向、權限／個資範圍、新功能、使用者看得到的行為改變）：當下用 AskUserQuestion 問，一次一題，選項含「現在做／不做／下輪做」（推薦的排第一），選項說明寫清楚各自的後果。選「現在做」就併入批次修復；選「不做」就在出貨報告寫一句；選「下輪做」才開票——開在 `.constellation/next-round/`（格式同一般票、`status: open`，目標段附當時彈窗題目與所選選項原文；不放 `tickets/`；票號依 `ticket-template.md`「命名規則」接續 `tickets/`、`next-round/`、`archive/` 三處已用過的最大號，開票前先掃這三處取當下最大號，撞號時以先落檔者為準、後者重新取號）。屬取捨型拍板就照 `SKILL.md`「拍板即落檔」寫一筆決議。
- **既有問題**（不是本輪造成的，例如推送後檢查看到的舊毛病）：當下問使用者「現在修／記進 MAP 已知缺口」；選記進 MAP 的，在步驟 3 校對 `MAP.md` 時寫進第三段、條目開頭標「（待選）」，下一輪訪談開工前盤點會端給使用者選。
- **執行端、審查員、指揮官都不得自行開下輪票**——`next-round/` 唯一入口是使用者在彈窗親口選「下輪做」。

要修的發現（阻擋級、執行端決定修掉的、使用者選「現在做」的）**走批次，不逐條各跑一輪**（決議 012）：等所有審查軸都出完報告→先去重、合併同根因的發現→一批修完→一次跑受影響範圍的複驗，不必整個全量重跑——除非改動範圍大到說不清楚受影響範圍（修復動到共用契約、schema、權限、全域設定就屬此類，回頭重跑 ship 全量）。複驗綠燈之外，還要**複審**——請原提出這些 finding 的審查軸（獨立 context）在同一次回合逐條標示 resolved／unresolved，確認修法真的解決了問題本身，而不是只讓測試變綠；複審範圍只限這批發現，不重跑全量審查。

## 出貨報告

固定落檔 `.constellation/ship-report.md`，固定三段，白話寫清楚，不堆術語：

- **做了什麼**：第一行列本輪全部票號；接著這輪出貨包含哪些票，每張票一句話說做了什麼。
- **驗了什麼**：全量驗證跑了哪些 test／journey、結果如何；兩軸審查各自看了什麼範圍。接著寫**發現怎麼結案**（本輪全部發現，含 build 期各批審查）：修掉幾條、丟掉的每條各一句理由、使用者當場決定的各一句；最後列**「使用者選擇下輪做」清單**——本輪新開進 `next-round/` 的每張票附票號與當時彈窗原文，沒有就寫「無」。這份清單以外不得有任何「待辦／候選／之後再看」的延後項。
- **證據在哪**：全量驗證的證據指向 `.constellation/ship-evidence.md`（步驟 1 由 runner 簽章寫入）；逐票驗證與審查發現另外存在各票檔的對應欄位——讓人可以自己回去核對，不能只靠這份報告的文字斷言。

`HISTORY.md` 的輪次摘要直接取這份報告的「做了什麼」那一段，不另外寫。

## 步驟 3：出貨後歸檔

離場條件（全量驗證綠燈＋本輪啟用的各審查軸都沒有阻擋級發現＋本輪所有發現都已結案＋出貨報告已產出）滿足後，才做這一步——讓下一輪任務從乾淨狀態開始，新舊輪不混淆：

- 把本輪 `tickets/`、`decisions/grill-close.md`、`decisions/engineering-defaults.md`（若存在）、`.constellation/ship-evidence.md`、`.constellation/design-frozen.json`、`.constellation/design-baseline.json`、`.constellation/ship-report.md` 整批移入 `.constellation/archive/<日期>-<摘要>/`（`<日期>` 用 `yyyy-mm-dd`，`<摘要>` 取 `decisions/grill-close.md` 記錄的一句話任務摘要轉成 kebab-case slug）。
- **把 `.constellation/config.json` 的 `approved` 重設為 `false`**：核准狀態跟著這輪歸零，下一輪 weave 重新核准時再寫回 `true`，避免下一輪誤讀到上一輪留下的核准痕跡。
- **同步在 `.constellation/HISTORY.md` 最上方補一段本輪摘要**（沒有這個檔就建立）：`## <日期> <任務摘要>` 起頭，內文直接取 `ship-report.md`「做了什麼」那一段，不另外寫。**最新一輪永遠在檔案最上方**（session 開場注入取檔案開頭當最近輪次）。票歸檔後明面上就查不到「上一輪做了什麼」，全靠這段摘要接棒——寫完才算歸檔完成。
- **校對專案現況地圖 `.constellation/MAP.md`**（母本 DESIGN.md §4）：build 期的結構變動記在各票決議記錄，這裡逐票收攏一次更新地圖。本輪如果新增／搬移了模組、新增或刪除了資料表，把對應行更新；同時把本輪查出來的**新的資料缺口與地雷**補進第三段（那一段是「看程式碼看不出來的不存在」，正是下一輪開工前盤點最省時間的地方）；本輪途中看到、使用者選了「記進 MAP 已知缺口」的既有問題（記在各票決議記錄或出貨報告），寫進第三段時條目開頭標「（待選）」，下一輪訪談開工前盤點靠這個標記把它們端給使用者選。**不必手動標記同步點**——閘門 3 直接拿「`MAP.md` 最後一次被 commit 的那個 commit」當過期基準自己算（母本 DESIGN.md §4），所以地圖跟著票一起 commit，基準就自動跟上。**語意三段要逐條複驗**（資料表口徑、已知缺口、地雷）：這三段機器測不出對錯，只有人看得出來。不必每次從頭掃兩百行——開場閘門第③道會點名「來源在地圖更新後動過」的行，先複驗那幾行，再加上本輪自己動過的模組相關條目。**缺口補上了就刪那條、地雷拆了就刪那條**：留著已經不成立的缺口比沒寫還糟，下一輪會照著它繞路、或重做一次已經做完的事。**地圖不存在就順手建一份**（grill 階段的開工前盤點應該已經產出，沒有代表那一步被跳過了）。**順手把超長條目壓回去**：地圖第三段（缺口與地雷）與 `CONTEXT.md` 的詞條，若 session 開場注入標了「已超出預算，下次 ship 先壓縮」（數字門檻見母本 DESIGN.md §4，部署後 runtime 不需讀取），這次校對一併壓回——地圖條目壓成至多 2 句、保留行內來源路徑、其餘指向決議或來源檔；CONTEXT 詞條壓成 1–2 句、規格內文移出另立文件；壓縮不是刪除。這一步只花幾分鐘：地圖只記路徑不記內容，本輪沒有新增或搬移檔案時通常一行都不用改。
- **凍結名單跟票同生命週期**：`design-frozen.json` 隨這輪票一起歸零、下一輪 design 從空名單重建，理由是避免跨輪累積的 `unfreeze` 紀錄讓下一輪 Spec 軸查不到已歸檔的同意脈絡而誤報阻擋級發現；代價是上一輪定稿、這輪不打算動的畫面在下一輪失去閘門 5 的機器保護，退而靠 weave 劃 `zone` 與出貨 Spec 軸逐款對照原文兜住，真要繼續保護就在那一輪 design 重新寫進 `frozen`（母本 DESIGN.md §4／§11.5）。
- `CONTEXT.md` 與其餘 `decisions/NNN-slug.md`（`grill-close.md` 除外）**留在原位、不歸檔**——這些是跨輪累積的專案領域知識，不是單輪產物。design 階段的定稿記錄（`decisions/NNN-slug.md`）也留在原位，凍結名單走了它還在，下一輪要沿用上輪的視覺語言時查得到。`.constellation/next-round/` 同樣**不歸檔**——它裝的是使用者選了「下輪做」的票，本質是跨輪累積的待辦，跟 `tickets/` 是分開的資料夾，這一步不動它（決議 027）。
- **本輪若在獨立工作區動工，歸檔最後一步把它收掉**：合併回主線並推送後，先確認工作區沒有未 commit 的改動、沒有登記中的 server（有就停下回報）；再照 `phase-build.md`「保護三」的順序——`cmd /c rmdir <工作區>\node_modules` 拆 junction（`Remove-Item -Recurse` 會刪穿主專案套件）→ `git worktree remove <工作區>` → `git branch -d <分支>`（`--detach` 開的沒有分支，略過這步）。工作區裡是整份真套件、`worktree remove` 撞到路徑過長而中斷時，改用 `cmd /c rmdir /s /q "\\?\<工作區>"` 刪目錄，再 `git worktree prune`。收完跑 `git worktree list`、`git branch`，確認只剩主工作樹與主分支。（起因：0915 輪出貨只刪了分支，工作區目錄留到下一輪才被發現。）
- 歸檔完成後，`.constellation/` 底下不再有任何 `tickets/*.md`，也沒有 `decisions/grill-close.md`，也沒有 `decisions/engineering-defaults.md`，也沒有 `design-frozen.json`、也沒有 `design-baseline.json`（兩者都隨凍結名單一起歸零；閘門 5 讀不到 `design-frozen.json` 時一律放行，不會擋到下一輪的正常編輯）——這是刻意的：下次總控（`skills/constellation/SKILL.md` Step 0）讀到這個狀態，會依「`tickets/` 空＋`grill-close.md` 不存在」判定「訪談尚未完成」，Lazy Read `references/phase-grill.md` 走增量重訪。**`next-round/` 這時可能還有票，屬預期**——總控 Step 0 本來就不看這個資料夾（見 `SKILL.md` Step 0 開頭），有票留著不代表歸檔沒做完。這正是要的效果——`CONTEXT.md` 與其餘 `decisions/*.md` 還留著跨輪知識，新一輪需求接上既有背景繼續問新的 frontier，不會被上一輪的舊票或舊決議誤判成「還在做上一輪」。
