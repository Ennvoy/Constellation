# 真鏈路驗證手冊

> 驗證 runner（閘門 4）與關票刷卡機（閘門 5）的判斷依據；build 逐票驗證、ship 全量驗證都照此手冊。核心規則（出處：母本 DESIGN.md §6，部署後 runtime 不需讀取）。

## 核心命題

**完成 = 實跑綠燈，不是 code 看起來對。** 讀完程式碼覺得邏輯應該沒問題，不算驗證通過——AI 的嘴不算數（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。每一條驗收條件都要有一次真實執行留下的證據，才准打勾。

## 依產出物型別，走真鏈路

| 涉及 | 驗證方式 | 禁止 |
|---|---|---|
| UI | **用當前環境可用的瀏覽器自動化工具（如 Playwright）真點擊**（navigate／click／type／snapshot／take_screenshot 這類操作）跑過使用者實際會走的路徑 | 讀 component 程式碼推斷「應該會動」 |
| API | **真打**（curl，或專案既有 http client）打進真的執行中服務，看實際 status／body | 讀 route handler 程式碼推斷回應長相 |
| 資料 | **真查 DB**（專案既有 DB client，如 `psql`／`sqlite3`／ORM script）直接讀資料表 | 讀 migration／model 檔推斷資料有沒有寫進去 |

三者都涉及時（多數功能票都是）——三段全跑，不是挑一段做代表。

## 資料類驗證鏈（涉資料的票，固定走這四段）

```
假資料 → 真 create API（seed）→ 真 DB（落地）→ UI 操作 / 真 API 呼叫 → 真 DB 讀回（核對最終狀態）
```

假資料只用在「餵給誰」這一步，之後每一步都是真依賴：不能自己直接寫 SQL insert 繞過 create API（繞過了 API 層的驗證邏輯，就測不到票要驗的東西）；也不能查 DB 這步用 mock 回傳代替，DB 讀回必須是真的一次查詢。

## 測試資料衛生（安全鐵則——與正式資料同庫時，清理範圍就是資料安全）

真鏈路測試打的是真 DB，而真 DB 裡可能同時住著正式資料——清理手段因此是安全問題，不只是整潔問題：

1. **測試資料必須可識別**：測試建立的資料一律帶明顯記號（固定前綴如 `test-`／專用測試帳號／專用網域的 email），肉眼與查詢都能一眼跟正式資料區分，不混淆。
2. **清理只清自己產生的資料**：測試收尾只刪「本次測試建立、帶測試記號」的資料（能用交易回滾就用回滾）；不得順手清別的測試或來路不明的資料。
3. **禁止全庫／全表清除當清理手段**：DROP／TRUNCATE／無條件 DELETE 不得出現在測試的 setup／teardown／清理程式碼——與正式資料同庫時，這等於拿正式資料賭測試不會跑錯環境。專用隔離測試庫（與正式資料完全分離，如本機測試實例）內的 reset 不在此限。
4. **平行 worker 版**：多個 worker 同時打同一顆測試庫時規則不變，只是「自己的」範圍要更精確——用**票專屬前綴**（例如 `test-T012-`）而不是共用的 `test-` 前綴，清理與核對都只比對自己前綴的範圍，**禁止整表前後快照比對**（快照會被別的 worker 同時寫入的資料污染，比對不出誰改了什麼）；平行時跑出的紅先單獨重跑一次，再判定是不是真的產品回歸（先假設是撞車，不是真的壞）。本質上沒辦法這樣隔離的操作（套 migration／改 schema、整庫快照型資料保險、量級壓測）在票頭標 `exclusive:`，改走「單獨時段」（機制見本檔同目錄 `phase-build.md`「保護二」）。
5. **起站埠要真的傳進測試框架**：weave 逐票指定的埠號不是寫在票裡就自動生效——指令帶環境變數（例如 `PORT=<埠> pnpm test:e2e`）或框架設定檔讀同一個環境變數；用 Playwright 之類有內建 `webServer` 的框架時，順手把 `reuseExistingServer` 設 `false`（平行時才不會誤用別的 worker 剛好占著的那個埠上的舊 server，蓋出一份跑在別人 build 上的假證據）。**票省略「驗證指令」段時，runner fallback 跑 `config.json` 的固定指令、固定埠**——這種票不能跟其他也用固定埠的票同批平行，抓不準 zone／指令時就把這張票放進下一批單獨跑，不要賭「應該不會撞」。

## 臨時 server 的起與收

驗證指令或除錯要用到「自己起的 server」（dev server、預覽 server、測試用後端）時，**一律經 `gates/serve.mjs` 起**（開場注入已直接印出它的絕對路徑；沒有注入時，例如 worker，與驗證 runner 同目錄），收工 `stop`、確認那個埠真的空出來。**這不是整潔問題，是正確性問題**：殘留的舊 server 會被測試框架的「既有 server 就沿用」設定當成自己人——它只探測那個網址通不通、不驗是誰起的——於是整輪 e2e 跑在舊 build 上，蓋出一份看起來完全正常的合格證據。

runner 自己起的那棵進程樹它會收乾淨（殺 shell 連坐子孫，外殼已退出的孤兒再用埠差集補刀），但 **agent 手動起的 server 完全在它視野外**——那正是殘留的主因，只有記帳管得到。記帳的意思是 `start` 當下就把 PID／埠／啟動時間登記起來，`stop` 與 SessionEnd **只殺登記過的那幾個、殺之前比對啟動時間**；不去掃全機的埠猜哪個該死（那會殺掉使用者自己正開著看的畫面，也會誤傷平行 session）。

**只有 Claude Code 端的 SessionEnd 真的收得到**：Codex 端 SessionEnd 上限 3 秒，登記真有得收時常跑不完（失效方向安全——不殺也不刪），得靠手動 `serve.mjs stop --port <p>` 收（見母本 DESIGN.md §9 降級表）。**worker 在 worktree 裡起的 server，登記寫進 worktree 自己的 `.servers.json`**——worktree 一移除，登記就跟著消失，主 session 的 SessionEnd 收不到，所以 worker 收工前、移除 worktree 前必須自己 `stop`。

**收工要殺的行程，歸屬只認三種證據**：①`serve.mjs` 登記過的 server，用 `stop` 收；②自己開的背景任務，用 `TaskStop` 收；③**自己這個 agent** 起的那支腳本——認的是起它時取的專屬檔名或當下記下的 PID，不是整個 session 共用的暫存路徑：同一個 session 裡平行派工的多個 worker 共用同一個 scratchpad（決議 023），只認到路徑分不出「哪個 agent」，會連平行 worker 正在跑的驗證一起殺掉。Claude Code 端腳本照樣放自己的 scratchpad，但檔名或 PID 才是憑證；**Codex 端因為沒有 scratchpad，自寫的驗證腳本一律放 `%TEMP%\codex-<CODEX_SESSION_ID>\`，背景起的自己記下 PID**（`CODEX_SESSION_ID` 在 `gates/serve.mjs` 已經在用，天然帶 session id、不會跟別的 session 撞名，但仍要靠檔名或 PID 分出是哪個 agent）。**殺之前先列候選清單，逐一核對三件事**：命令列含那支腳本的專屬檔名；建立時間晚於自己起它的時間；不是自己正在執行、用來下殺指令的那個 shell 本身（純子字串比對連自己都可能命中，決議 020 補記記錄過這種失手）——三者都對得上才殺，只有 session 暫存路徑、沒有專屬檔名或 PID 佐證的，不算充分證據。**程式名相同（例如 `chrome-headless-shell.exe`）、`ms-playwright` 這類共用路徑片段、命令列字串巧合相同、啟動時間早晚、記憶體高低，全部不算證據**——本機實測：Node 在 Windows 上開瀏覽器用的是非 detached 子行程，但系統連坐只管**直接**父子關係，隔一層 cmd 或 bash 就斷鏈（`node → cmd → node`、`node → Git Bash → node` 這兩種形狀下，殺最上層之後，中間層與底層的 node 連同它開的瀏覽器都還活著）；Playwright 起瀏覽器正是控制端 node 的直接子行程、沒有另外包殼，所以瀏覽器會跟著**直接控制它的那支 node**一起死，但那支 node 本身可能是隔著 cmd／bash 掛上去的孤兒（例如 Claude Code 的 Bash 工具就是 node → bash → node 這個形狀，session 異常結束會留下這樣的孤兒），連坐鏈在更上層就已經斷了。所以看得到活著的 headless 瀏覽器，只代表**那支直接控制它的 node** 還活著——那支 node 是自己的還是別人的，還是要照上面三種證據查，不能單憑「看得到瀏覽器」就假設有人在用。**瀏覽器本身不要直接殺**，要收就殺直接控制它的那支腳本，瀏覽器自然被系統連坐收掉。**認不出是自己的就不殺**——不符合上面三種證據的行程（另一個 session 的驗證、另一個平行 worker 的驗證、使用者自己開的瀏覽器、瀏覽器 MCP 起的有頭 Chrome），一律彈窗問使用者，不得因為程式名或路徑相同就當孤兒清掉（案例見決議 025）。

## 跨 session 共用這台機器

同一台機器上可能同時有好幾個 session（不同專案，或同一專案的不同 worktree）在跑。全量驗證怎麼排隊、怎麼看誰佔著、什麼時候能停，`phase-ship.md` 步驟 1 已經講清楚，這裡不重複；這節只管兩件事——殺行程時的歸屬判斷、跟什麼時候才需要開口。

- **只殺自己起的行程**：判準跟決議 020／025 的三種歸屬證據一致（`serve.mjs` 登記過的 server、自己開的背景任務、自己這個 agent 起的那支腳本），這裡指過去即可，不重複列。另一個 session 的全量驗證——不論是不是自己專案的——一律不算「自己的」，看起來像孤兒也不動手。
- **閘門會擋別人全量的 PID**：`gates/kill-guard.mjs` 掛在 `gates/pre-tool-use.mjs` 上，會比對指令裡的 PID 是不是別的 session 在出貨鎖裡登記的持有者（所有專案的登記都比對，不只你自己這個專案的那一份），命中就擋下並講明是哪個專案的全量、幾點起跑——擋下來的訊息本身就是「這不是你的」的證據，不必自己先判斷再手動放過。真的要停對方的全量，走下面的 SendMessage，不要想辦法繞過守門。
- **SendMessage 只用來講燈表達不了的事**：誰在跑、大約幾點輪到，出貨鎖與 `lease list`（列所有專案的登記）都看得到，不必再用訊息確認一次——**沒有排隊目錄，「排到第幾」查不到**，誰先 poll 到誰先接手，不是先到先贏的隊伍；SendMessage 留給出貨鎖表達不了的事——外部時段限制（例如正式庫有固定的上傳窗不能碰）、事故（對方需要真的中止、要換人接手）。

## 反模式清單（出現任一項＝這張票不算驗證通過）

1. **Tautological test（自我循環的測試）**：測試的期望值跟實作用同一套算法算出來的，於是必然綠。例如實作用某公式算利息，測試也用同一個公式現算期望值去比對——這種測試改壞實作也會一起綠，等於沒測到東西。期望值要來自需求本身（票的驗收條件描述的具體數字／行為），不是抄實作邏輯。
2. **Mock 冒充真依賴**：真依賴（真實 API、真實 DB、真實第三方服務）還沒 ready 時，用 mock／stub 頂著讓測試先綠，再把票標完成。正確做法：**這張票標 `blocked`**，寫清楚卡在哪個依賴，不是用假的東西騙過驗證。
3. **只看 code 目測宣稱完成**：讀過一遍程式碼、覺得邏輯合理，沒有實際跑，就在驗證證據欄寫「已確認無誤」。驗證證據欄只能填「真的執行了一次」留下的紀錄，不是審閱心得。
4. **清理範圍越界**：測試的 setup／teardown 用全庫／全表清除（DROP／TRUNCATE／無條件 DELETE），或刪到非本次測試建立的資料——與正式資料同庫時這是資料事故的預備動作，不是整潔習慣（隔離測試庫例外，見「測試資料衛生」）。

## 證據遮密（落檔前的衛生）

驗證證據（票的「驗證證據」欄、`ship-evidence.md`）、決議記錄與報告裡引用的指令與輸出，**落檔前一律遮密**——這些檔案全部進 git，寫進去就是永久留底：

1. 金鑰／token／密碼／可識別個資改寫成 `<REDACTED>`；指令本身用環境變數引用（如 `$env:SUPABASE_KEY`），明文憑證不落檔。
2. **遮值不遮形**：status code、筆數、表名、耗時這些診斷需要的資訊照留；擷取的回應只引載有訊號的那幾行，不整包貼。
3. 遮完仍不足以佐證時，照實說明並請使用者看現場輸出，不為了留證據而落敏感內容。

閘門 2 的 secrets 掃描是最後一道；這條是第一道——一開始就不寫進去，比被攔下來重寫便宜。

## 真鏈路也要快（效率鐵則）

真鏈路要求的是「真依賴」，不是「最貴的跑法」——unit 與整合測試單條成本可差數十倍，寫測試當下就選最省的形態，套件才不會隨專案變大而失控。違反下列鐵則**不影響該票驗證判定**（正確性不為速度讓路，速度也不反過來變成新閘門），由 build 每批審查與 ship 的 Standards 軸在寫得出具體後果時回報（例如「每支測試各自重登入，全量多花約 N 分鐘」），執行端當場修掉或寫理由丟掉，不開票（決議 031）：

1. **最低層原則**：每條測試寫在能抓到該 bug 的最低層（unit→整合/db→e2e）；e2e 只驗「使用者流程走得通」的跨層縫合，不重複斷言低層已驗過的邏輯分支。真鏈路四段鏈是每個驗收條件走一次的鏈，不是每個分支各走一次全鏈。新增 e2e 測試的票，在決議記錄留一句「為什麼低層測不到」。**下推不是降級許可證**——「禁 mock 冒充真依賴」「每個驗收條件至少走一次真鏈路」兩條優先於下推，拿不準就留在原層。
2. **本地同引擎隔離庫＝真依賴**：「禁 mock」禁的是假引擎假行為，不是要求付跨區網路延遲——同引擎、同版本、同 migration 的本地實例就是真依賴。平常照專案現有連線寫、**不預先建基建**；要不要改用本機庫由使用者自行決定，工作流不主動提案。已本機化的專案，ship journey 仍保留至少一組打真雲端環境的檢查當漂移保險。不論本機或雲端，**少往返**是預設紀律：清理與 seed 合併成單次呼叫、斷言批次讀回，不逐句序列 SQL 疊網路往返。
3. **登入態一次取得、全套件重用**：用測試框架的 setup 機制（如 Playwright setup project＋storageState）登一次、全套件共用；不讓每支測試各自重走登入 UI。
4. **資料隔離用輕量手法**：API／DB 層測試用交易回滾，e2e 層用最小範圍清理；不每測 truncate 全表、不在 beforeEach 逐句清理疊固定成本。
5. **追蹤產物只留失敗**：trace／video／screenshot 設「失敗才保留」級別；不分成敗全程錄影會拖慢執行並塞爆磁碟。
6. **執行平行度拉滿**：測試 runner 的並行度按機器核心數設定（Playwright `workers`、vitest／jest 的 thread 數等），不留在框架的保守預設。測試互撞（搶同一張表、共用固定帳號）時改用第 4 條的資料隔離解決，不靠全域調回單工——那是拿整個套件的時間補少數幾支測試的耦合。

## 關票前的測試整理

TDD 過程中，「測試先行」（步驟 2）常常會為了把實作往前推、驅動出正確的中間結構，順手寫出一批只服務當下這一刻的測試——這些是**草稿題**，幫忙把字寫工整，但改完考卷不會收進成績單。關票前要把草稿題跟**期末考題**分開，只留後者。

- **草稿題（關票前刪掉或併入）**：測內部函式的中間值、mock 掉內部模組、斷言呼叫次數（「這個 function 有沒有被呼叫 3 次」）、測 private helper——這些測的是「這一刻程式碼怎麼切」，不是這張票對外承諾的行為。重構把內部切法換掉時，這些測試理應跟著壞，留著只會變成重構的絆腳石，不是保護網。
- **期末考題（留到最後）**：每條驗收條件對應一支行為測試——「給輸入看輸出」「打 API 看回應」「查 DB 看結果」，測的是對外可觀察的結果，不管內部怎麼實作都不該壞。這才是這張票真正要留給下一個人看的證據。
- **判準**：問「這支測試斷言的是使用者／呼叫方看得到的結果，還是我這一刻選的內部切法」——前者留，後者關票前清。拿不準就想像半年後重構了內部實作，這支測試理論上該不該壞：不該壞的才留。
- **數量以驗收條件數為準**：留下的行為測試數量跟票的驗收條件數同一個量級，不無限累積——一條驗收條件對應一支測試是常態，不是每次修過的中間版本都各留一支。

跟前面兩條銜接、不重複：「真鏈路也要快」管**怎麼寫測試最省**（單條成本），這節管**寫完之後留哪些**（套件總量）——草稿題留著不清，套件會隨專案變大持續變慢，是效率鐵則要防的失控的另一個來源。「禁 tautological test」是測試本身壞掉（期望值抄實作邏輯算出來）；草稿題是測試本身沒壞，只是測的是不該長期保留的內部細節——兩者是不同層次的問題。

## 分級規則

驗證 runner（絕對路徑取得方式見本檔同目錄的 `phase-build.md`／`phase-ship.md`）用 `--scope ticket|ship` 區分兩級，各自讀 `.constellation/config.json` 對應的指令陣列：

- **逐票（build 階段）**：`node <runner 絕對路徑> --ticket <票號> --scope ticket`——票內有「## 驗證指令」縮圈清單（weave 寫定，見 `ticket-template.md`）就跑該清單，省略則跑 `commands.test`（快速套件）全量；外加**這張票驗收條件對應的實跑檢查**（驗收條件列了哪些操作，就跑哪些操作，例如對應的 Playwright 點擊、真打 API），**不跑** `commands.journey`；不必每次都跑全量回歸。跑完後 runner 把指令、結果摘要、時間戳與簽章寫進票的「驗證證據」欄，這欄人不手填（格式見本檔同目錄 `ticket-template.md`「驗證證據」）。
- **出貨（ship 階段）**：`node <runner 絕對路徑> --scope ship`——`commands.test` 完整回歸 ＋ `commands.journey` 全量一次跑齊，涵蓋所有已關票的驗收條件加總，抓票與票之間可能互相打壞的地方。這是（出處：母本 DESIGN.md §6，部署後 runtime 不需讀取）兩軸獨立審查之外、屬於「有沒有真的動起來」的那一半驗證，兩者互補、缺一不可。這一輪的全量證據由 runner 簽章寫入 `.constellation/ship-evidence.md`（見本檔同目錄的 `phase-ship.md` 步驟 1），是 ship 級「證據在哪」的唯一落點，不是散落在各票檔裡自己拼湊。

## 真依賴沒 ready 時怎麼辦

不降級成 mock、不跳過、也不用「之後補」含糊帶過——這張票直接標 `blocked`，在票的決議記錄寫明卡在哪個依賴（哪個服務／哪張票／哪個外部帳號），等依賴解除再繼續。平行 fan-out 時其餘不受影響的票照常推進（出處：母本 DESIGN.md §8，部署後 runtime 不需讀取）。
