# 真鏈路驗證手冊

> 驗證 runner（閘門 4）與關票刷卡機（閘門 5）的判斷依據；build 逐票驗證、ship 全量驗證都照此手冊。核心規則（出處：母本 DESIGN.md §6，部署後 runtime 不需讀取）。

## 核心命題

**完成 = 實跑綠燈，不是 code 看起來對。** 讀完程式碼覺得邏輯應該沒問題，不算驗證通過——AI 的嘴不算數（出處：母本 DESIGN.md §0，部署後 runtime 不需讀取）。每一條驗收條件都要有一次真實執行留下的證據，才准打勾。

## 依產出物型別，走真鏈路

| 涉及 | 驗證方式 | 禁止 |
|---|---|---|
| UI | **用當前環境可用的瀏覽器自動化工具（如 Playwright）真點擊**（navigate／click／type／snapshot／take_screenshot 這類操作）跑過使用者實際會走的路徑 | 讀 component 程式碼推斷「應該會動」 |
| API | **真打**（curl，或專案既有 http client）打進真的執行中服務，看實際 status／body | 讀 route handler 程式碼推斷回應長相 |
| 資料 | **真查 DB**（專案既有 DB client，如 `psql`／`sqlite3`／ORM script）直接讀資料表 | 讀 migration／model 檔推斷資料有沒有寫進去 |

三者都涉及時（多數功能票都是）——三段全跑，不是挑一段做代表。

## 資料類驗證鏈（涉資料的票，固定走這四段）

```
假資料 → 真 create API（seed）→ 真 DB（落地）→ UI 操作 / 真 API 呼叫 → 真 DB 讀回（核對最終狀態）
```

假資料只用在「餵給誰」這一步，之後每一步都是真依賴：不能自己直接寫 SQL insert 繞過 create API（繞過了 API 層的驗證邏輯，就測不到票要驗的東西）；也不能查 DB 這步用 mock 回傳代替，DB 讀回必須是真的一次查詢。

## 反模式清單（出現任一項＝這張票不算驗證通過）

1. **Tautological test（自我循環的測試）**：測試的期望值跟實作用同一套算法算出來的，於是必然綠。例如實作用某公式算利息，測試也用同一個公式現算期望值去比對——這種測試改壞實作也會一起綠，等於沒測到東西。期望值要來自需求本身（票的驗收條件描述的具體數字／行為），不是抄實作邏輯。
2. **Mock 冒充真依賴**：真依賴（真實 API、真實 DB、真實第三方服務）還沒 ready 時，用 mock／stub 頂著讓測試先綠，再把票標完成。正確做法：**這張票標 `blocked`**，寫清楚卡在哪個依賴，不是用假的東西騙過驗證。
3. **只看 code 目測宣稱完成**：讀過一遍程式碼、覺得邏輯合理，沒有實際跑，就在驗證證據欄寫「已確認無誤」。驗證證據欄只能填「真的執行了一次」留下的紀錄，不是審閱心得。

## 真鏈路也要快（效率鐵則）

真鏈路要求的是「真依賴」，不是「最貴的跑法」——unit 與整合測試單條成本可差數十倍，寫測試當下就選最省的形態，套件才不會隨專案變大而失控。違反下列鐵則**不影響該票驗證判定**（正確性不為速度讓路，速度也不反過來變成新閘門），由 ship 的 Standards 軸列建議級發現：

1. **最低層原則**：每條測試寫在能抓到該 bug 的最低層（unit→整合/db→e2e）；e2e 只驗「使用者流程走得通」的跨層縫合，不重複斷言低層已驗過的邏輯分支。真鏈路四段鏈是每個驗收條件走一次的鏈，不是每個分支各走一次全鏈。新增 e2e 測試的票，在決議記錄留一句「為什麼低層測不到」。**下推不是降級許可證**——「禁 mock 冒充真依賴」「每個驗收條件至少走一次真鏈路」兩條優先於下推，拿不準就留在原層。
2. **本地同引擎隔離庫＝真依賴**：「禁 mock」禁的是假引擎假行為，不是要求付跨區網路延遲——同引擎、同版本、同 migration 的本地實例就是真依賴。導入採**觸發式**：平常照專案現有連線寫、不預先建基建；當 ship 證據的耗時行顯示 db 層驗證持續超過 10 分鐘，才提本機化方案（共用本地實例／內嵌實例）彈窗讓使用者針對該專案拍板、落 decisions/；本機化後 ship journey 仍保留至少一組打真雲端環境的檢查當漂移保險。不論本機或雲端，**少往返**是預設紀律：清理與 seed 合併成單次呼叫、斷言批次讀回，不逐句序列 SQL 疊網路往返。
3. **登入態一次取得、全套件重用**：用測試框架的 setup 機制（如 Playwright setup project＋storageState）登一次、全套件共用；不讓每支測試各自重走登入 UI。
4. **資料隔離用輕量手法**：API／DB 層測試用交易回滾，e2e 層用最小範圍清理；不每測 truncate 全表、不在 beforeEach 逐句清理疊固定成本。
5. **追蹤產物只留失敗**：trace／video／screenshot 設「失敗才保留」級別；不分成敗全程錄影會拖慢執行並塞爆磁碟。

## 分級規則

驗證 runner（絕對路徑取得方式見本檔同目錄的 `phase-build.md`／`phase-ship.md`）用 `--scope ticket|ship` 區分兩級，各自讀 `.constellation/config.json` 對應的指令陣列：

- **逐票（build 階段）**：`node <runner 絕對路徑> --ticket <票號> --scope ticket`——票內有「## 驗證指令」縮圈清單（weave 寫定，見 `ticket-template.md`）就跑該清單，省略則跑 `commands.test`（快速套件）全量；外加**這張票驗收條件對應的實跑檢查**（驗收條件列了哪些操作，就跑哪些操作，例如對應的 Playwright 點擊、真打 API），**不跑** `commands.journey`；不必每次都跑全量回歸。
- **出貨（ship 階段）**：`node <runner 絕對路徑> --scope ship`——`commands.test` 完整回歸 ＋ `commands.journey` 全量一次跑齊，涵蓋所有已關票的驗收條件加總，抓票與票之間可能互相打壞的地方。這是（出處：母本 DESIGN.md §6，部署後 runtime 不需讀取）兩軸獨立審查之外、屬於「有沒有真的動起來」的那一半驗證，兩者互補、缺一不可。這一輪的全量證據由 runner 簽章寫入 `.constellation/ship-evidence.md`（見本檔同目錄的 `phase-ship.md` 步驟 1），是 ship 級「證據在哪」的唯一落點，不是散落在各票檔裡自己拼湊。

## 真依賴沒 ready 時怎麼辦

不降級成 mock、不跳過、也不用「之後補」含糊帶過——這張票直接標 `blocked`，在票的決議記錄寫明卡在哪個依賴（哪個服務／哪張票／哪個外部帳號），等依賴解除再繼續。平行 fan-out 時其餘不受影響的票照常推進（出處：母本 DESIGN.md §8，部署後 runtime 不需讀取）。
