# Phase ① 訪談（grill）

一句話：把待釐清範圍問到 frontier 清空、決議即時落檔；frontier 沒清空前不動手實作，事實不問人。

## 進場 / 離場

- **進場條件**：任何時刻都能進場——全新任務（`.constellation/` 不存在）、既有任務要補問（增量重訪，見下）、或使用者透過獨立入口 `/grill` 對任何想法拷問（不限開發任務）。
- **離場條件**：frontier 清空 ＋ 收尾盲點掃描零新發現 ＋ 使用者對大小分岔與是否需要 UI 定稿一次拍板確認，才算離場：
  - 這次任務**需要 UI** → 交給本檔同目錄的 `phase-design.md`（design 定稿拉回 repo、轉譯成專案元件後才轉交本檔同目錄的 `phase-weave.md`）。使用者答「照既有架構做」（不用看多個方向）**也算需要 UI、也照樣轉交 design**——定稿本身還是要的（要讓使用者看過、要凍結），design 階段內部只生成一版就好，這裡不另分岔。
  - **純後端／無 UI 任務** → 直接交給本檔同目錄的 `phase-weave.md`。
  - 兩種情況都要先把「大小流程／是否需要 UI」寫成一筆決議（見「訪談收尾」），讓接手的階段不必回頭重問。
  - 大流程另有獨立盲點審（見「完整性四保險」第 3 點），它決定轉交時機：一律跑到收斂才轉交下一階段——需要 UI 時轉交 design，不需要 UI 時轉交 weave，兩個 runtime 做法相同。

## 開場先讀使用者預設

建設計樹**之前**，先 Read 本檔同目錄的 `user-defaults.md`——使用者的既有技術棧（部署平台、後端）
與 web 系統必備模組都在裡面。這些項目**不進設計樹當問題問**（已有答案的不叫開放問題），
直接當預設推薦帶入；只有當次任務性質明顯不適用、或使用者主動提起要換時，才變回要問的題。

## 開工前盤點（repo 已有 code 時必跑，先於建設計樹）

**這一步不是為了寫文件，是因為改造型任務的 frontier 有一大半根本不在使用者腦子裡**——它藏在
「已經拍板的決議，跟系統實際做到的事對不上」那道縫隙裡。使用者記得住業務規則，但記不住哪條規則系統其實沒做；
agent 也不會憑空想到。**這種洞只能主動掃，掃不出來就會變成邊問邊挖，讓使用者替你做盤點。**

**先看有沒有 `.constellation/MAP.md`**（專案現況地圖，母本 DESIGN.md §4）：
- **有**：照它定位，只補掃這次要動到的部分；掃完把新發現補回地圖對應段落。
- **沒有**：整份掃出來，順手落檔成 `MAP.md`（格式見 DESIGN.md §4：模組索引／資料表／已知缺口與地雷）。
  盤點本來就要跑，落檔是零額外成本——**下一個 session 就不必再掃一次**，這正是它存在的唯一理由。

**掃四個角度**（fan-out 平行，屬母本 §7 允許的「研究／盤點」場景之一；盤點類派中階模型、**審查性質的不得降級**）：

1. **決議 vs 實作**：與本次範圍相關的決議逐條對照程式碼，找「拍板了但應用層沒做」。
   已知會反覆出現的五種形態——資料表建好了卻沒有寫入路徑／算出來了卻沒有任何畫面在顯示／
   欄位存的是「文字說明」而不是可計算的值／函式簽名根本沒有那個參數／只有測試在用、正式路徑沒接。
2. **本次改動會打斷什麼**：唯一鍵與索引、排序、搜尋、深連結、匯出檔、API 契約、既有測試、定案快照。
   （典型：要移除某個欄位，而它正好是資料表唯一鍵的一部分。）
3. **依賴的資料源到底存不存在**：要用的維度／欄位／資料表是不是真的有資料——空表、被 fail-closed 擋著、
   保留窗外會靜默回 0，都算「沒有」。
4. **錯誤路徑／權限／資料生命週期**有沒有被定義過。

**順手動作（盤點時一併做，不算四角度之一）**：專案有資料庫時，用一句查詢列出各表的估算筆數
（Postgres 用 `pg_class.reltuples`；其他引擎用等效的統計值，不做精確 `COUNT(*)`），結果補進 `MAP.md`
資料表段的粒度旁——這是「大量資料」判定的訊號之一（見「訪談收尾」高風險標記）。

**掃出來的落差逐條分流**：需要使用者取捨的 → 轉成 frontier 節點依序問（照下面的提問格式）；
純技術實作細節 → 自己決定，記入決議或票，不佔使用者的判斷力。

**`MAP.md` 第三段標「（待選）」的條目，盤點時端給使用者選**（決議 031）：那是上一輪途中看到的既有問題、使用者當時選了「記進 MAP 已知缺口」而不是當場修。有這類條目時，在建設計樹前逐條彈窗問（一次一題）「併入這輪／繼續留在地圖／不修了」，跟本次範圍重疊的排前面並推薦併入；超過 5 條時先用一窗問「只看跟這輪範圍重疊的幾條（推薦）／全部逐條看」。選併入的轉成 frontier 節點照常問細節；選繼續留著的原樣不動（下一輪再問）；選不修了的拿掉「（待選）」標記、條目照留當已知缺口（它仍是事實），之後不再問。純流程外輪次不問這一題，條目原樣留著。

**先掃完再開始問**。掃描與提問可以平行（掃在背景跑、同時問不依賴它的題），但不得「問到一半才開始掃」。

## 設計樹與 Frontier

- 把待釐清的範圍想成一棵**設計樹**：每個決策節點可能有前置依賴（父節點），父節點就是「答了這題才問得下去」的那一題。樹不必一開始就建完整——隨著使用者回答，會解鎖新的子節點，也可能把整條子樹剪掉（父節點答案讓那些子問題根本不成立）。
- **Frontier** ＝目前所有前置已拍板、可以問的節點。它決定出題順序：先問沒有前置依賴的根節點，答案解鎖新節點後重算 frontier，繼續往下問。
- **「batch」指的是內部運算，不是介面呈現**：frontier 是一次算出「現在能問的一批」，但呈現給使用者時仍是**一則訊息一題**依序問完這一批，不把多題塞進同一則訊息（見下方提問格式）。
- 依賴未拍板的題必須遞延，不能因為「反正之後會問到」就先問子節點、之後再倒回頭補父節點的答案。

> 例：使用者想加「留言功能」。根節點「留言要不要能編輯」無前置，直接進 frontier。答「要」後，解鎖子節點「編輯要不要留編輯紀錄」「編輯時間窗口多長」——這兩題現在才進 frontier。若答「不要」，這兩個子節點直接從樹上剪掉，不問。

## 先分流：事實不問人

拿到一個待問節點，先判斷它是「真決策」還是「事實」：

- **事實**（讀檔、跑工具、查官方文件就能拿到答案的）：agent 自己查，不排進使用者要回答的 frontier。查證動作**非阻塞**——發起查證的同時，若還有其他不依賴這個事實的 frontier 節點，照常繼續問使用者，不枯等查證結果。
- 只有**以這個事實節點為父節點的下游題**會被卡住，等查證完成才解鎖；其餘節點不受影響。
- 查證完成後，若發現這其實沒有唯一答案（官方文件也沒寫死、或有多個可行方案要權衡）——代表它其實是決策，這時才把它升級成正常 frontier 節點問使用者，並附上查到的背景資訊當推薦理由的依據。
- **真決策**（沒有客觀對錯、要使用者的取捨判斷）：才進 frontier，用下面的格式問。

## 提問格式

**開放問題與封閉確認一律用 AskUserQuestion 彈窗，一次一題。**

- **一次一題**：frontier 是一次算出「現在能問的一批」，但仍是一則訊息一個彈窗、依序問完，不把多題塞進同一次彈窗。選項真的可複選才開 `multiSelect`。
- **2–4 個選項**，推薦的排第一、label 標「（推薦）」。每題**必附推薦答案**，不是丟一堆選項了事。
- 每個選項的 `description` 用**白話**寫「選了會怎樣、代價是什麼」，代價據實寫、不淡化。
- **白話是硬要求**：使用者曾直接回「看不懂」——問題堆內部術語（模組名、函式名、內部代號）會讓人無從判斷。先講「什麼情況、會發生什麼事」，技術名詞留到括號裡補充。
- **彈窗本身必須能獨立看懂**：已知顯示 bug 會讓同回合彈窗前的文字整段不渲染，使用者當下只看得到彈窗。背景與取捨要塞進 question 或選項描述裡，不能只寫在正文就當使用者看得到。
- 使用者選「Other」自由作答時，**其內容優先於任何選項**——跟選項都不符就照他打的走，不用套回某個選項硬解讀。

> 要再改「一律彈窗」時，本節與母本 `DESIGN.md` §2、`phase-design.md`、`phase-weave.md`、`phase-build.md`、`SKILL.md` 降級表、使用者全域 `CLAUDE.md` 的對應條款須同步。

### 封閉確認（同樣走彈窗，選項更精簡）

答案固定二三選一、點一下最快的場合，選項寫得更精簡即可，格式與開放問題相同。訪談階段內會用到的場合：

- 收尾時「frontier 真的清空、可以往下走了嗎」的確認。
- 收尾時「大小流程／是否需要 UI（需要 UI 才追問這次畫面架構有沒有得選）」的最終拍板（見「訪談收尾」，可以跟上一項合併成同一次彈窗的連續幾小題）。
- 增量重訪時「這輪新增的決議要不要覆蓋掉舊的」這類是非題。

## 鐵律

1. 每題附推薦答案（含理由與代價，白話、不用術語轟人）。
2. 事實不問人：能查到答案的不進 frontier，只有真決策才問。
3. frontier 清空前禁止動手實作；清空後仍須使用者明確確認才進下一步——不能自己覺得問夠了就直接開始做。
4. **詞彙挑戰**：使用者的用詞與 `CONTEXT.md` 既有定義衝突、或一詞多義（同一個詞在講兩件事）時，當場點出並問清——「詞彙表定義『X』是＜既有定義＞，你這裡指的是不是另一回事？」；模糊詞當場提議一個定案說法、其餘列 avoid。與程式現況矛盾時照實擺出對質（開工前盤點抓的是存量落差，這條抓的是對話進行中的增量）。

## 邏輯原型繞道（談不攏的題先做樣品）

frontier 題**同時滿足兩條件**才動用：①文字選項講不清——典型是狀態機／資料模型題（狀態流程「先 A 再 B」該如何、資料形狀裝不裝得下某案例），要動手玩過才判斷得了；②選錯的返工代價高（拍板後拆票實作整段重來那種）。兩條件都中時：

- Read 本檔同目錄的 `logic-prototype.md` 照做——產一個單檔 HTML 拋棄式樣品給使用者玩（雙擊就能開、按按鈕看狀態變化）。
- 玩過後照常彈窗拍板；結論落 decisions/，證據欄寫「原型結論」＋一句樣品驗出了什麼。
- 樣品放暫存目錄、閱後即焚、不進 repo。
- 不是每題都做——彈窗講得清的照常彈窗；這是繞道，不是主線。

## 決議落檔

答案一拍板就**立刻**寫進檔案，不等訪談結束才批次補：

- **用詞定義**：這題定義或選定了一個本專案特有的詞彙 → 寫進 `.constellation/CONTEXT.md`。只收本專案特有詞（通用程式概念不收），每詞 1–2 句；遇到同義詞，選一個定案，其餘列為 avoid，不刪除舊說法只是標記別再用。
- **經拍板的取捨**：使用者對這題做了取捨型拍板（不是純事實確認）→ 寫一筆 `.constellation/decisions/NNN-slug.md`，四要素各 1–2 句：背景＋決定＋原因＋**證據**——證據記拍板脈絡（彈窗題目與所選選項原文，或使用者原話一句）與當時依據（實測數據、官方文件連結；沒有就寫「無」）。編號遞增，用過的編號永久保留給那筆決議，即便決議之後被推翻也只標 `superseded by NNN`，不刪除、不重複使用號碼。
- **其餘答案**（沒定義新詞、也沒經拍板的細節，例如純事實確認）：屬於合成拆票階段會自己判斷的「小事」材料，不用另外開檔案存——同一場訪談若直接接續到 design／weave，沿用對話上下文即可；真的中途中斷、之後才重開 `/grill` 增量重訪，這類答案視為沒發生過，需要的話重問一次也無妨。
- **指揮官自決的工程預設**（獨立盲點審時，見下方「完整性四保險」第 3 點）：審查員標了阻擋級但指揮官判斷屬於自己能定的、或指揮官直接處理的其餘發現，不算「經拍板的取捨」——純簿記類（交叉引用沒對上、措辭、格式這類不改語意的）直接修回原決議檔，不進工程預設清單；會改變行為或結果的發現才寫進固定檔案 `.constellation/decisions/engineering-defaults.md`（工程預設清單），不是 `NNN-slug.md`；處置紀錄（誰提了什麼、處置了沒）不放進這份清單、也不放進其他 `decisions/`。

## 完整性四保險

1. **Frontier 清空才算完成**：設計樹每個分支走到底，沒有任何東西被默默假設；清空後仍須使用者明確確認才進下一步（見封閉確認）。
2. **收尾盲點掃描**：frontier 清空後，agent 切到獨立視角，對照下面五個角度重新掃一遍已落檔的決議，任一角度有漏，就對照那個漏洞生成新的 frontier 問題再問一輪；直到掃過一整輪零新發現才算過關。
   - **邊界情況**：極值、空值、超出預期量級的輸入，決議裡有沒有講清楚這些情況下的行為。
   - **錯誤路徑**：操作失敗、網路中斷、驗證不過時，使用者會看到什麼、系統怎麼處理。
   - **權限**：誰能做這個操作、誰不能，決議裡有沒有漏掉「未登入」「權限不足」這類分支。
   - **資料生命週期**：資料建立後會不會被更新／刪除／過期，刪除是軟刪除還是硬刪除，決議裡有沒有講。
   - **相依故障**：這個功能依賴的外部服務或其他票的產出，若不可用／慢／回傳異常，決議裡有沒有講清楚要怎麼辦。
3. **獨立盲點審（大流程必跑，每一輪、每個視角都換新審查員）**：訪談收尾拍板、寫完 `grill-close.md` 後啟動，把落檔決議全集（`CONTEXT.md`＋`decisions/`＋`decisions/engineering-defaults.md`，若已有）交給一位**沒有參與過這個案子**的新審查員——它只看送審清單本身的檔案，看不到訪談對話，也看不到上一輪的發現、變動清單或處置說明（工程預設清單裡改判那一行的理由除外）——避免被討論過程或前一輪處置說明的思維慣性污染，這正是它能抓到「使用者沒想到＋訪談者也沒問到」結構性盲區的原因，任務：假設這份決議明天直接開工，找出矛盾、未定義概念、缺席的異常路徑、該問而沒人問的問題——**找的範圍不縮小**（決議 022② 否決的「縮小審查範圍」不變）。
   - **審查員起法（每一輪、每個視角都適用）**：以能開獨立 context 的方式起——Claude Code 用 Agent 工具或 Workflow 起皆可（每個呼叫顯式帶 `model`，不得省略而讓其默默繼承主線模型）；Codex 用其原生做法起獨立 context。**主線不得兼任審查員**——即使當下缺可用的起法工具，也要換一種能開出獨立 context 的方式，不能由主線自己讀過送審清單後自己判定。首輪不設發現條數上限，並列出情境推演角度（時序情境、migration 順序、各角色的 UI 路徑），讓既有的洞在第一輪就被掃到；之後每一輪同樣不設條數上限。若同時派出多位不同視角的審查員，各自建立獨立 identity，一輪一位、每輪都是全新審查員。
   - **阻擋級只有三種「要問使用者的題」**（其餘一律不算阻擋級）：(a) 要使用者選、選項會帶來使用者或同仁看得到的不同結果，而既有拍板推不出答案；(b) 兩條使用者拍板過的決議互相打架；(c) 指揮官的工程預設擴大或收窄了使用者拍板的範圍，需要使用者追認。審查員拿不準一律標阻擋級——寧可多問一句，不要漏掉真正該問使用者的題。阻擋級轉成新 frontier 題目問使用者→答案照常落檔→**再送審一輪**。
   - **其餘發現不讓這一輪重來**：會出事但指揮官補得了的、實作細節、補丁之間的縫，由指揮官直接修，**不為它另送一輪**。純簿記類（交叉引用沒對上、措辭、格式這類不改語意的）直接修回原決議檔，不進工程預設清單；會改變行為或結果的發現，指揮官自己補的，一律寫進固定檔案 `.constellation/decisions/engineering-defaults.md`（工程預設清單，檔名固定、不是編號遞增的 `NNN-slug.md`，同 `grill-close.md` 手法）——**就地改寫，不加「修正 by」**：每條只寫要保證的結果，不寫做法（做法留給拆票決定）；要寫程式現況事實必須附可重跑的出處（檔案:行號或查詢句），沒查過的不寫。**處置紀錄（誰提了什麼、處置了沒）不放進這份清單、也不放進其他 decisions/**——那是流水帳（見上方「決議落檔」）。
   - **指揮官可以把審查員標的阻擋改判成自己的工程預設**：審查員標了阻擋級，但指揮官判斷其實是自己能定的工程預設，可以直接改判並寫進工程預設清單，條件是那一條要附一句理由（例如「依 NNN 推得出」，NNN＝推得出這個答案的那條使用者拍板決議），**且這一輪不算乾淨輪**（不計入下面「連續兩位」的收斂計數）——下一位新審查員照樣要看這份清單，順便檢查指揮官的改判有沒有越權（其實是第 c 類、該問使用者卻被指揮官自己拍板了）。**同一條被下一位新審查員再標一次阻擋，指揮官不得再改判**，一律照阻擋級規則問使用者——避免反覆改判讓收斂條件永遠湊不齊。
   - **收斂＝每個視角連續兩位新審查員都沒挑出阻擋級**：不設輪數上限——每一輪本來就是全新審查員，收斂本身就是「連續兩個獨立視角都看不出該問使用者的題」。在 `grill-close.md` 檔尾補一行「盲點審：已收斂（第 N 輪）」（N＝累計輪數）——design 進場、weave 進場與總控 Step 0 都靠這一行判定盲點審跑完了。使用者明示喊停時照實改寫「盲點審：使用者喊停（第 N 輪）」，效力同收斂行。收斂後又經增量重訪落了新的訪談決議，就刪掉這一行、照本保險重跑到收斂。
   - **多視角並行**：同時派出多位不同視角的審查員時，每個視角各自獨立累計連續零阻擋輪數、各自收斂——某個視角這輪有阻擋不影響其他視角。`grill-close.md` 檔尾的收斂行要等**所有視角都各自收斂**才能寫，寫一行即可（不必逐視角各寫一行）。
   - **與下一階段的時機**：大流程一律跑到收斂才轉交下一階段——需要 UI 時轉交 `phase-design.md`，不需要 UI 時轉交 `phase-weave.md`，不與拆票並行；**Claude Code 與 Codex 規則一致，不再需要降級**（每輪本來就是換新審查員起，兩邊做法天生相同）。送審的決議集就是訪談決議＋盲點題答案＋工程預設清單，每輪由指揮官列出送審清單（`CONTEXT.md`＋`decisions/`＋`decisions/engineering-defaults.md`）交給審查員——**不附上一輪的發現、變動清單或處置說明**（工程預設清單裡改判那一行的理由除外）。
   - **換 session 接回**：`grill-close.md` 記著大流程、檔尾卻沒有收斂行，就是盲點審還沒跑完——先接回本保險，收斂後才轉交 design 或 weave；連續零阻擋的輪數從零重算（本來每輪就是新審查員，接回就是再起一位新人）。例外：舊規則下寫的 `grill-close.md`（當時規則是收斂才轉交、沒有收斂行），若它或決議裡已記載盲點審跑完，照實告知使用者，同意後補上收斂行即可，不必重跑。

   若審出的內容動搖了 grill-close.md 的既有判斷（大小流程／UI／高風險標記），更新該檔並跟使用者確認一句。小流程可省略本保險（決議集小，前兩道保險已足）。
4. **增量重訪**：訪談決議全落檔（`CONTEXT.md`＋`decisions/`），任何時候可重開 `/grill`——既有決議視為已拍板節點，不重問；重建 frontier 時只納入「這輪使用者新提出的內容」與「收尾盲點掃描／獨立盲點審才發現的缺口」兩類，其餘照舊。

## 訪談收尾：大小分岔與 UI 需求

Frontier 清空、收尾盲點掃描零新發現後，依改動範圍估算並提議：

- 估算依據：能否一個連貫改動做完、有沒有新資料結構（新表／新欄位／新 API 資源）、跨不跨模組。
- 估算後用一次 AskUserQuestion 彈窗（拆成連續幾小題，一次一題）向使用者提以下幾件事，各附推薦與理由：
  - **`.constellation/next-round/` 有票時，先問併不併入**（排在本節所有題目最前面問，僅這一題、不逐張各開一窗；`next-round/` 空的輪次不問，直接跳到下一小題）：彈窗固定三個選項——「併入推薦的那幾張（推薦）」（推薦依據：動到的模組與本輪重疊，或屬於安全類）、「全部留著」、「全部併入」；使用者也可以在其他欄位直接打票號指名要併入哪幾張，或寫「T-xxx 不做了」代表放棄那張。**這題排最前面問是因為答案要先算進下面幾題的估算**：「大／小流程」「是否需要 UI」「高風險標記」都要把併入票的範圍算進去，不能先估完、拍板完才回頭發現漏算（例如併入一張動到權限的票，高風險標記卻還寫「無」）。**只要選了併入（不論幾張），下面「大／小流程」那題就不再提供「流程外」這個選項**——流程外定義上不拆票、不建 `tickets/`，沒有地方承接併入的票。**這一輪本身就只會走流程外捷徑（不經過本節這輪彈窗，直接照本檔同目錄 `SKILL.md`「流程外小改動」紀律辦）時，不問這一題**——`next-round/` 的票原樣留著，等下一輪再問。使用者的選擇記進 `grill-close.md` 檔尾一行固定格式的「下輪待辦」狀態註記（比照下面盲點審的收斂行，是狀態註記、不算新增欄位，寫法見「訪談收尾」段落最後一句）：`下輪待辦：併入 T-541、T-542；放棄 T-540`（併入與放棄各自可能是空的，空的那半句連同分號一起省略；兩邊都空就整行不寫）——**不塞進「一句話任務摘要」**（那句之後會被拿去當歸檔目錄名稱與 `HISTORY.md` 標題，塞票號會污染兩者）。`phase-weave.md` 收尾時讀這一行：併入的搬去 `tickets/`，放棄的搬去 `archive/next-round-closed/`；這裡只負責問並落檔，不負責搬檔案。
  - **大／小流程／流程外**：大流程完整走②③④⑤；小流程只在③（weave）不拆多票——直接產**單一任務卡**（本質是一張票，含驗收條件與 `config.json` 驗證設定），之後單線程做完＋實跑驗證，再走**輕量⑤**（驗證範圍即該卡全部驗收條件，兩軸審查照做；`next-round/` 有票併入時，這些票各自獨立、不併進任務卡，輕量⑤的驗證範圍要一併涵蓋它們的驗收條件）。**流程外**——一個連貫改動、主線或單一工作流可以做完，且不動資料結構、不動權限、不碰定稿凍結名單內的檔案（動 migration 或權限一律走小流程），三條安全條件同時成立才適用（**上一題已併入 `next-round/` 待辦票時，這個選項不提供**——流程外沒有 `tickets/` 可以承接併入的票）：這一輪到此為止，不寫 `grill-close.md`、不進②③④⑤——落一筆決議（背景＋決定＋原因＋證據）到 `decisions/NNN-slug.md`，直接改、直接 commit，`HISTORY.md` 最上方記一行「`## <日期> <摘要>（流程外，無票）獨立審查：<有/無>；全量測試：<結果>`」，判定依據與理由寫進這行讓使用者看得到；不拆票、不出貨審查、不建 archive。
  - **是否需要 UI 定稿**：這次改動有沒有使用者看得到、要操作的介面；純後端／API／資料層改動不需要，直接跳過②。這一題與大小流程**正交**、分開判斷，不是「小流程就一定不需要 UI」。
  - **需要 UI 時才追問：這次畫面的架構有沒有得選**（答不需要 UI 就不問這題，也不佔題數）。白話問法：這個功能是「同一件事可以有好幾種完全不同的排法，值得先各看一版再挑」，還是「照現有頁面的排法照做就好，只是多一個篩選器／表格多一欄／表單多一個欄位」？
    - **有得選** → design 階段會給好幾個不同方向讓使用者比較、挑一個再往下調；**這裡不要承諾「會由 Claude Design 生成」**——走路徑一（Claude Design 生成）還是路徑二（執行端自己寫）要到 design 階段進場才拍板，細節見本檔同目錄 `phase-design.md`。若這次是改造某個既有畫面，選項說明要講明：現況那幾個畫面會一起當成基底送上去，使用者看得出「改了到底有沒有變好」。
    - **照既有架構做** → design 階段照樣跑（一樣要讓使用者看過定稿、一樣凍結），只是只生成一版、不看多個方向。選項說明要據實寫代價：少了「幾個方向擺出來比」這一輪，好處是不用為了湊數看兩個沒人要的假選項（需求本來只有一種合理排法時硬湊版本，就是流程自己在製造工作量），代價是這次不會意外發現「其實換個排法更好用」。
- **給人讀的產出，先給使用者看真資料樣本（流程外／小流程）**：改動主體是給人讀的產出（週報、推播、報表文字、口徑數字），而且改的是呈現方式或口徑時，盡量在動工前用拋棄式腳本（不進 repo）套真資料做一份樣本（私人 Artifact 或本地檔），請使用者看一次；動工前做不出來（要先寫出新的計算才有東西可套）最晚也要在審查與上線前。使用者要改就改完重做樣本；看樣本不會自動升級流程，要不要升級照上面的條件判斷（動資料結構或權限才升）。代價約 10–20 分鐘＋1 題。
- **不要問使用者「基底風格要沿用既有的、還是挑一套新的」**：這是**事實**（design 階段自己讀 code 就知道，鐵律 2「事實不問人」），不佔用使用者要回答的題數；規則細節在本檔同目錄的 `phase-design.md` 步驟 1，本階段不重複判斷、也不預先讀那份檔案。
- 彈窗前的正文也完整寫出同一份估算與提議理由，不只靠彈窗內容。
- 估算時同時判斷本次任務是否**涉權限／金流／個資**（登入授權、角色權限、收付款、可識別個人的資料）——這決定出貨審查是否自動加開 security 紅軍軸，判斷結果一併寫進收尾決議。
- 估算時同時判斷本次任務是否**大量資料**：判定不靠感覺、靠三個查得到的訊號，任一命中即標：
  1. 這次會讀寫的表估算筆數超過門檻（預設 10 萬筆；`config.json` 可用 `largeDataRows` 調整）——對照「開工前盤點」補進 `MAP.md` 的估算筆數。
  2. `MAP.md` 資料表段記的粒度是「每日／每筆／每次事件」這類會隨時間長大的。
  3. 使用者用詞出現「幾千人、名單、匯入、報表、重算、歷史、全站」。

  標了就必問固定三題並落決議：現在大概幾筆、一年後大約幾筆、這頁或這個動作多久算可接受。標記會讓 weave 階段的相關票必寫量級門檻、ship 階段加開效能實測軸。

  **附則：蓋新機制繞開某個限制前，先實測那個前提對這次的真實量還成不成立**——新機制是為了繞開某個既有前提或外部限制（單次上限、單次成本、量級）而建、且預計拆 3 張票以上時（不論有沒有標大量資料），最晚在訪談收尾（事實分流允許 frontier 期間就先量），用拋棄式腳本（不進 repo）在真實環境量一次：這次的真實量級離上限多遠、單次成本隨什麼變——限制本身還在不代表前提成立，要量的是這次會不會真的碰到它。量到的數字帶進收尾彈窗；舊決議記下的限制與前提一樣要重量，不直接沿用。量測限唯讀、最小樣本；會寫入、會計費或會對正式站造成重負載的量測，先問使用者。不另設檢查點，也不併進邏輯原型（那個不接真 DB）。
- 使用者拍板後（走的是大／小流程，非流程外——流程外已在上一步直接完成，不會走到這裡），把「大小流程：大/小、是否需要 UI：否／是（架構有得選）／是（照既有架構做）、高風險標記：無／有（權限/金流/個資/大量資料，有則列出哪類）、必備模組排除：無／有（web 任務時，使用者明示不要哪些必備模組就列哪些）、一句話任務摘要」寫入**固定決議檔** `decisions/grill-close.md`（檔名固定，不是編號遞增的 `NNN-slug.md`）。**欄位仍是這五欄、不新增欄位**（大流程盲點審收斂後補在檔尾的收斂行「盲點審：已收斂（第 N 輪）」與 `next-round/` 有票時補的「下輪待辦：併入 T-xxx；放棄 T-yyy」行都是狀態註記、不算欄位，見「完整性四保險」第 3 點與上面「先問併不併入」那一題）——「是否需要 UI」這一欄只是把可寫的值從兩種擴成三種，三種值的含義是：`否`＝不需要 UI，跳過 design；`是（架構有得選）`＝走 design，且要請 Claude Design 生成多個方向讓使用者比較；`是（照既有架構做）`＝走 design，但只生成一版、沿用既有的資訊架構。後面兩種值都代表「需要 UI、要走 design」，差別只在 design 階段內部要不要看多個方向。這份檔案同時是**機讀的「訪談已完成」標記**：總控（`skills/constellation/SKILL.md` Step 0）靠它判斷訪談是否完成並決定路由——沒有這份檔案就一律視為訪談未完成、退回本階段增量重訪，不論 `CONTEXT.md` 或其他 `decisions/*.md` 是否已有內容——「拍板即落檔」通則下 decisions/ 可能只有流程外落的既有決議、訪談根本沒開過，也可能是訪談中途中斷，兩種都不得被誤判為已完成。寫完後再依上面「進場/離場」的規則轉交下一階段。

## 獨立入口（非開發任務）

`/grill` 可以脫離 Constellation 開發流程單獨呼叫，對任何想法或決定做拷問。這種情境下：

- frontier、事實分流、提問格式、推薦答案、完整性四保險（第 3 點只適用於有 `grill-close.md` 的大流程），規則完全不變。
- 若當下確實在某個專案的 `.constellation/` 工作目錄脈絡下（不論是被 Constellation 主流程呼叫、還是使用者在該專案裡手動呼叫），決議照樣落檔進該目錄的 `CONTEXT.md`／`decisions/`。
- 若當下不在任何專案脈絡（純粹拷問一個想法，不是開發任務），沒有 `.constellation/` 可落檔——不用為了落檔硬生出一個工作目錄，frontier 清空後直接把最終決議整理成一份總結回覆給使用者即可。

## Codex 端降級

Codex 沒有 AskUserQuestion 彈窗（出處：母本 DESIGN.md §9 降級表，部署後 runtime 不需讀取），**所有提問**（開放問題與封閉確認）一律降級為純文字點列格式：

```
Q：<問題本身，白話，禁術語轟人>
```
