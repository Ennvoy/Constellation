# Phase ① 訪談（grill）

一句話：把待釐清範圍問到 frontier 清空、決議即時落檔；frontier 沒清空前不動手實作，事實不問人。

## 進場 / 離場

- **進場條件**：任何時刻都能進場——全新任務（`.constellation/` 不存在）、既有任務要補問（增量重訪，見下）、或使用者透過獨立入口 `/grill` 對任何想法拷問（不限開發任務）。
- **離場條件**：frontier 清空 ＋ 收尾盲點掃描零新發現 ＋ 使用者對大小分岔與是否需要 UI 定稿一次拍板確認，才算離場：
  - 這次任務**需要 UI** → 交給本檔同目錄的 `phase-design.md`（design 定稿拉回 repo、轉譯成專案元件後才轉交本檔同目錄的 `phase-weave.md`）。使用者答「照既有架構做」（不用看多個方向）**也算需要 UI、也照樣轉交 design**——定稿本身還是要的（要讓使用者看過、要凍結），design 階段內部只生成一版就好，這裡不另分岔。
  - **純後端／無 UI 任務** → 直接交給本檔同目錄的 `phase-weave.md`。
  - 兩種情況都要先把「大小流程／是否需要 UI」寫成一筆決議（見「訪談收尾」），讓接手的階段不必回頭重問。

## 開場先讀使用者預設

建設計樹**之前**，先 Read 本檔同目錄的 `user-defaults.md`——使用者的既有技術棧（部署平台、後端）
與 web 系統必備模組都在裡面。這些項目**不進設計樹當問題問**（已有答案的不叫開放問題），
直接當預設推薦帶入；只有當次任務性質明顯不適用、或使用者主動提起要換時，才變回要問的題。

## 開工前盤點（repo 已有 code 時必跑，先於建設計樹）

**這一步不是為了寫文件，是因為改造型任務的 frontier 有一大半根本不在使用者腦子裡**——它藏在
「已經拍板的決議，跟系統實際做到的事對不上」那道縫隙裡。使用者記得住業務規則，但記不住哪條規則系統其實沒做；
agent 也不會憑空想到。**這種洞只能主動掃，掃不出來就會變成邊問邊挖，讓使用者替你做盤點。**

（2026-08-04 實際翻車：使用者反問「名單範本應該有基準趟數吧？你確認一下」，一查才發現決議早已定案
「基準趟數每人一個值、隨名單上傳」、資料表也建好了，但應用層**從來沒有寫入路徑**——新建活動的基準趟數
全是 0、超越獎金會爆掉。使用者當場說：「為什麼我每次都要自己提醒你」。這一節就是那次的產物。）

**先看有沒有 `.constellation/MAP.md`**（專案現況地圖，母本 DESIGN.md §4）：
- **有**：照它定位，只補掃這次要動到的部分；掃完把新發現補回地圖對應段落。
- **沒有**：整份掃出來，順手落檔成 `MAP.md`（格式見 DESIGN.md §4：模組索引／資料表／已知缺口與地雷）。
  盤點本來就要跑，落檔是零額外成本——**下一個 session 就不必再掃一次**，這正是它存在的唯一理由。

**掃四個角度**（fan-out 平行，屬母本 §7 允許的「研究／盤點」場景之一；盤點類派中階模型、**審查性質的不得降級**）：

1. **決議 vs 實作**：與本次範圍相關的決議逐條對照程式碼，找「拍板了但應用層沒做」。
   已知會反覆出現的五種形態——資料表建好了卻沒有寫入路徑／算出來了卻沒有任何畫面在顯示／
   欄位存的是「文字說明」而不是可計算的值／函式簽名根本沒有那個參數／只有測試在用、正式路徑沒接。
2. **本次改動會打斷什麼**：唯一鍵與索引、排序、搜尋、深連結、匯出檔、API 契約、既有測試、定案快照。
   （典型：要移除某個欄位，而它正好是資料表唯一鍵的一部分。）
3. **依賴的資料源到底存不存在**：要用的維度／欄位／資料表是不是真的有資料——空表、被 fail-closed 擋著、
   保留窗外會靜默回 0，都算「沒有」。
4. **錯誤路徑／權限／資料生命週期**有沒有被定義過。

**掃出來的落差逐條分流**：需要使用者取捨的 → 轉成 frontier 節點依序問（照下面的提問格式）；
純技術實作細節 → 自己決定，記入決議或票，不佔使用者的判斷力。

**先掃完再開始問**。掃描與提問可以平行（掃在背景跑、同時問不依賴它的題），但不得「問到一半才開始掃」。

## 設計樹與 Frontier

- 把待釐清的範圍想成一棵**設計樹**：每個決策節點可能有前置依賴（父節點），父節點就是「答了這題才問得下去」的那一題。樹不必一開始就建完整——隨著使用者回答，會解鎖新的子節點，也可能把整條子樹剪掉（父節點答案讓那些子問題根本不成立）。
- **Frontier** ＝目前所有前置已拍板、可以問的節點。它決定出題順序：先問沒有前置依賴的根節點，答案解鎖新節點後重算 frontier，繼續往下問。
- **「batch」指的是內部運算，不是介面呈現**：frontier 是一次算出「現在能問的一批」，但呈現給使用者時仍是**一則訊息一題**依序問完這一批，不把多題塞進同一則訊息（見下方提問格式）。
- 依賴未拍板的題必須遞延，不能因為「反正之後會問到」就先問子節點、之後再倒回頭補父節點的答案。

> 例：使用者想加「留言功能」。根節點「留言要不要能編輯」無前置，直接進 frontier。答「要」後，解鎖子節點「編輯要不要留編輯紀錄」「編輯時間窗口多長」——這兩題現在才進 frontier。若答「不要」，這兩個子節點直接從樹上剪掉，不問。

## 先分流：事實不問人

拿到一個待問節點，先判斷它是「真決策」還是「事實」：

- **事實**（讀檔、跑工具、查官方文件就能拿到答案的）：agent 自己查，不排進使用者要回答的 frontier。查證動作**非阻塞**——發起查證的同時，若還有其他不依賴這個事實的 frontier 節點，照常繼續問使用者，不枯等查證結果。
- 只有**以這個事實節點為父節點的下游題**會被卡住，等查證完成才解鎖；其餘節點不受影響。
- 查證完成後，若發現這其實沒有唯一答案（官方文件也沒寫死、或有多個可行方案要權衡）——代表它其實是決策，這時才把它升級成正常 frontier 節點問使用者，並附上查到的背景資訊當推薦理由的依據。
- **真決策**（沒有客觀對錯、要使用者的取捨判斷）：才進 frontier，用下面的格式問。

## 提問格式

**開放問題與封閉確認一律用 AskUserQuestion 彈窗，一次一題。**

- **一次一題**：frontier 是一次算出「現在能問的一批」，但仍是一則訊息一個彈窗、依序問完，不把多題塞進同一次彈窗。選項真的可複選才開 `multiSelect`。
- **2–4 個選項**，推薦的排第一、label 標「（推薦）」。每題**必附推薦答案**，不是丟一堆選項了事。
- 每個選項的 `description` 用**白話**寫「選了會怎樣、代價是什麼」，代價據實寫、不淡化。
- **白話是硬要求**：使用者曾直接回「看不懂」——問題堆內部術語（模組名、函式名、內部代號）會讓人無從判斷。先講「什麼情況、會發生什麼事」，技術名詞留到括號裡補充。
- **彈窗本身必須能獨立看懂**：已知顯示 bug 會讓同回合彈窗前的文字整段不渲染，使用者當下只看得到彈窗。背景與取捨要塞進 question 或選項描述裡，不能只寫在正文就當使用者看得到。
- 使用者選「Other」自由作答時，**其內容優先於任何選項**——跟選項都不符就照他打的走，不用套回某個選項硬解讀。

> 2026-07-27 反覆試用後定案為一律彈窗。要再改時，本節與母本 `DESIGN.md` §2、`phase-design.md`、`phase-weave.md`、`phase-build.md`、`SKILL.md` 降級表、使用者全域 `CLAUDE.md` 的對應條款須同步。

### 封閉確認（同樣走彈窗，選項更精簡）

答案固定二三選一、點一下最快的場合，選項寫得更精簡即可，格式與開放問題相同。訪談階段內會用到的場合：

- 收尾時「frontier 真的清空、可以往下走了嗎」的確認。
- 收尾時「大小流程／是否需要 UI（需要 UI 才追問這次畫面架構有沒有得選）」的最終拍板（見「訪談收尾」，可以跟上一項合併成同一次彈窗的連續幾小題）。
- 增量重訪時「這輪新增的決議要不要覆蓋掉舊的」這類是非題。

## 鐵律

1. 每題附推薦答案（含理由與代價，白話、不用術語轟人）。
2. 事實不問人：能查到答案的不進 frontier，只有真決策才問。
3. frontier 清空前禁止動手實作；清空後仍須使用者明確確認才進下一步——不能自己覺得問夠了就直接開始做。

## 決議落檔

答案一拍板就**立刻**寫進檔案，不等訪談結束才批次補：

- **用詞定義**：這題定義或選定了一個本專案特有的詞彙 → 寫進 `.constellation/CONTEXT.md`。只收本專案特有詞（通用程式概念不收），每詞 1–2 句；遇到同義詞，選一個定案，其餘列為 avoid，不刪除舊說法只是標記別再用。
- **經拍板的取捨**：使用者對這題做了取捨型拍板（不是純事實確認）→ 寫一筆 `.constellation/decisions/NNN-slug.md`，四要素各 1–2 句：背景＋決定＋原因＋**證據**——證據記拍板脈絡（彈窗題目與所選選項原文，或使用者原話一句）與當時依據（實測數據、官方文件連結；沒有就寫「無」）。編號遞增，用過的編號永久保留給那筆決議，即便決議之後被推翻也只標 `superseded by NNN`，不刪除、不重複使用號碼。（2026-08-04 門檻放寬：原「難以逆轉＋沒背景會驚訝＋真的經過權衡」三條件同時成立才記——實測發現使用者被迫反覆重提醒的，正是沒過三關就蒸發的中型決議。）
- **其餘答案**（沒定義新詞、也沒經拍板的細節，例如純事實確認）：屬於合成拆票階段會自己判斷的「小事」材料，不用另外開檔案存——同一場訪談若直接接續到 design／weave，沿用對話上下文即可；真的中途中斷、之後才重開 `/grill` 增量重訪，這類答案視為沒發生過，需要的話重問一次也無妨。

## 完整性四保險

1. **Frontier 清空才算完成**：設計樹每個分支走到底，沒有任何東西被默默假設；清空後仍須使用者明確確認才進下一步（見封閉確認）。
2. **收尾盲點掃描**：frontier 清空後，agent 切到獨立視角，對照下面五個角度重新掃一遍已落檔的決議，任一角度有漏，就對照那個漏洞生成新的 frontier 問題再問一輪；直到掃過一整輪零新發現才算過關。
   - **邊界情況**：極值、空值、超出預期量級的輸入，決議裡有沒有講清楚這些情況下的行為。
   - **錯誤路徑**：操作失敗、網路中斷、驗證不過時，使用者會看到什麼、系統怎麼處理。
   - **權限**：誰能做這個操作、誰不能，決議裡有沒有漏掉「未登入」「權限不足」這類分支。
   - **資料生命週期**：資料建立後會不會被更新／刪除／過期，刪除是軟刪除還是硬刪除，決議裡有沒有講。
   - **相依故障**：這個功能依賴的外部服務或其他票的產出，若不可用／慢／回傳異常，決議裡有沒有講清楚要怎麼辦。
3. **獨立盲點審（大流程必跑，交替迴圈到收斂）**：訪談收尾拍板、寫完 `grill-close.md` 後、轉交下一階段**前**，把落檔決議全集（`CONTEXT.md`＋`decisions/`）交給一個**獨立 context 的審查 agent**——它看不到訪談對話、只看檔案（避免被討論過程的思維慣性污染，這正是它能抓到「使用者沒想到＋訪談者也沒問到」結構性盲區的原因），任務：假設這份決議明天直接開工，找出矛盾、未定義概念、缺席的異常路徑、該問而沒人問的問題。它的發現轉成新 frontier 題目問使用者→答案照常落檔→**再送審一輪**，交替迴圈直到**連續一輪零新發現**才轉交（使用者已拍板：能兌現保真的審查迴圈成本值得付，不設輪數上限）。若審出的內容動搖了 grill-close.md 的既有判斷（大小流程／UI／高風險標記），更新該檔並跟使用者確認一句。小流程可省略本保險（決議集小，前兩道保險已足）。
4. **增量重訪**：訪談決議全落檔（`CONTEXT.md`＋`decisions/`），任何時候可重開 `/grill`——既有決議視為已拍板節點，不重問；重建 frontier 時只納入「這輪使用者新提出的內容」與「收尾盲點掃描／獨立盲點審才發現的缺口」兩類，其餘照舊。

## 訪談收尾：大小分岔與 UI 需求

Frontier 清空、收尾盲點掃描零新發現後，依改動範圍估算並提議：

- 估算依據：預計動幾個檔、有沒有新資料結構（新表／新欄位／新 API 資源）、跨不跨模組。
- 估算後用一次 AskUserQuestion 彈窗（拆成連續幾小題，一次一題）向使用者提以下幾件事，各附推薦與理由：
  - **大／小流程**：大流程完整走②③④⑤；小流程只在③（weave）不拆多票——直接產**單一任務卡**（本質是一張票，含驗收條件與 `config.json` 驗證設定），之後單線程做完＋實跑驗證，再走**輕量⑤**（驗證範圍即該卡全部驗收條件，兩軸審查照做）。
  - **是否需要 UI 定稿**：這次改動有沒有使用者看得到、要操作的介面；純後端／API／資料層改動不需要，直接跳過②。這一題與大小流程**正交**、分開判斷，不是「小流程就一定不需要 UI」。
  - **需要 UI 時才追問：這次畫面的架構有沒有得選**（答不需要 UI 就不問這題，也不佔題數）。白話問法：這個功能是「同一件事可以有好幾種完全不同的排法，值得先各看一版再挑」，還是「照現有頁面的排法照做就好，只是多一個篩選器／表格多一欄／表單多一個欄位」？
    - **有得選** → design 階段會給好幾個不同方向讓使用者比較、挑一個再往下調。**這裡不要承諾「會由 Claude Design 生成」**——訪談當下還不知道屆時那個服務用不用得上；用得上就由它生成多個方向，用不上就改成先做一版、再用文字來回迭代出不同方向（見本檔同目錄 `phase-design.md` 的降級路徑）。若這次是**改造某個既有畫面**（不是全新畫面），選項說明要講明：現況那幾個畫面會一起當成基底送上去，所以生成出來的版本本來就會參考現況長什麼樣，使用者看得出「改了到底有沒有變好」。
    - **照既有架構做** → design 階段照樣跑（一樣要讓使用者看過定稿、一樣凍結），只是只生成一版、不看多個方向。選項說明要據實寫代價：少了「幾個方向擺出來比」這一輪，好處是不用為了湊數看兩個沒人要的假選項（需求本來只有一種合理排法時硬湊版本，就是流程自己在製造工作量），代價是這次不會意外發現「其實換個排法更好用」。
- **不要問使用者「基底風格要沿用既有的、還是挑一套新的」**：repo 裡到底有沒有既有 UI 是**事實**，design 階段自己讀 code 就知道（鐵律 2「事實不問人」），不佔用使用者要回答的題數——探到有既有 UI，就把既有的設計變數／可重用元件／全域樣式／字型直接送上去當基底；探到是一片空地，才挑一套現成的設計系統當起點（150 套品牌資產庫或 Claude Design 內建那幾套），那才是要問使用者的真決策。規則細節在本檔同目錄的 `phase-design.md` 步驟 1，本階段不重複判斷、也不預先讀那份檔案。
- 彈窗前的正文也完整寫出同一份估算與提議理由，不只靠彈窗內容。
- 估算時同時判斷本次任務是否**涉權限／金流／個資**（登入授權、角色權限、收付款、可識別個人的資料）——這決定出貨審查是否自動加開 security 紅軍軸，判斷結果一併寫進收尾決議。
- 使用者拍板後，把「大小流程：大/小、是否需要 UI：否／是（架構有得選）／是（照既有架構做）、高風險標記：無／有（權限/金流/個資，有則列出哪類）、必備模組排除：無／有（web 任務時，使用者明示不要哪些必備模組就列哪些）、一句話任務摘要」寫入**固定決議檔** `decisions/grill-close.md`（檔名固定，不是編號遞增的 `NNN-slug.md`）。**欄位仍是這五欄、不新增欄位**——「是否需要 UI」這一欄只是把可寫的值從兩種擴成三種，三種值的含義是：`否`＝不需要 UI，跳過 design；`是（架構有得選）`＝走 design，且要請 Claude Design 生成多個方向讓使用者比較；`是（照既有架構做）`＝走 design，但只生成一版、沿用既有的資訊架構。後面兩種值都代表「需要 UI、要走 design」，差別只在 design 階段內部要不要看多個方向。這份檔案同時是**機讀的「訪談已完成」標記**：總控（`skills/constellation/SKILL.md` Step 0）靠它判斷訪談是否完成並決定路由——沒有這份檔案就一律視為訪談未完成、退回本階段增量重訪，不論 `CONTEXT.md` 或其他 `decisions/*.md` 是否已有內容——「拍板即落檔」通則下 decisions/ 可能只有流程外落的既有決議、訪談根本沒開過，也可能是訪談中途中斷，兩種都不得被誤判為已完成。寫完後再依上面「進場/離場」的規則轉交下一階段。

## 獨立入口（非開發任務）

`/grill` 可以脫離 Constellation 開發流程單獨呼叫，對任何想法或決定做拷問。這種情境下：

- frontier、事實分流、提問格式、推薦答案、完整性三保險，規則完全不變。
- 若當下確實在某個專案的 `.constellation/` 工作目錄脈絡下（不論是被 Constellation 主流程呼叫、還是使用者在該專案裡手動呼叫），決議照樣落檔進該目錄的 `CONTEXT.md`／`decisions/`。
- 若當下不在任何專案脈絡（純粹拷問一個想法，不是開發任務），沒有 `.constellation/` 可落檔——不用為了落檔硬生出一個工作目錄，frontier 清空後直接把最終決議整理成一份總結回覆給使用者即可。

## Codex 端降級

Codex 沒有 AskUserQuestion 彈窗（出處：母本 DESIGN.md §9 降級表，部署後 runtime 不需讀取），**所有提問**（開放問題與封閉確認）一律降級為純文字點列格式：

```
Q：<問題本身，白話，禁術語轟人>
1. <選項 A>（推薦）— <一句話講後果與取捨>
2. <選項 B> — <一句話講後果與取捨>
回數字選擇；回「ok」＝採推薦；或直接打自己的想法。
```

一則訊息只放一題、置於結尾醒目處；封閉確認的選項通常更精簡（一句講清楚哪個是預設即可）。frontier 運作、事實分流、決議落檔、完整性四保險等規則不因降級而改變——降級只影響「問題長什麼樣子」這一層。
