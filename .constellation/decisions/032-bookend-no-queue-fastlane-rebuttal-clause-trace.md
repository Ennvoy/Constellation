# 032 提速四件：整套測試只在頭尾跑、不排隊等前批上線＋流程外快速通道、盲點審阻擋級先過反駁員、出貨 Spec 軸改拿原文逐款對照

> 第 2(a) 點末句「機器鎖（出貨全量排隊）不動」已 **superseded by 033**：改為同專案的出貨鎖照舊、跨專案不排隊。其餘各項仍有效。

背景：
- **整套測試**：14 輪出貨期整套測試共跑 111 趟、約 54 小時（runner 全量 92 趟、另 19 趟是自組的整套指令）；照 `phase-ship.md` 既有「全量只當書擋」條文，runner 只需 28 趟（每輪頭尾各一），多出 64 趟、約 2,127 分，其中約七成由假紅燈推著整套重跑（e2e 冷站與並行、計時型斷言、資源或記憶體不足、資料保險誤報與殘留、vitest Unhandled Error），其餘是修完一處就整套重跑確認；修復期間幾乎沒走 `--last-failed` 或指名檔案。
- **排隊**：執行端會以「同時改主線的話，那批的全量驗證和推送會把還沒給使用者看過的畫面一起送上線」為由，讓新工作等進行中的批次跑完全量與部署，實例等了 141 到 448 分。盤點 `SKILL.md`、`DESIGN.md`、`phase-*.md`，條文沒有任何一句要求等進行中的批次——等待是執行端自己推出來的，所以補一句紀律寫明不等。
- **小改動**：流程外原本要先跑完訪談的開工前盤點與設計樹，到訪談收尾才提出；`HISTORY.md` 那一行要求寫「獨立審查／全量測試」。
- **盲點審**：決議 029 允許指揮官把審查員標的阻擋級改判成自己的工程預設——判「這題要不要問使用者」的，正是寫那份工程預設的人。
- **出貨 Spec 軸**：拿票對照；票是決議的轉譯，轉譯時漏掉或意思走樣的款，對照票抓不到。
- **出貨 Standards 軸起點（既有缺口，本次對抗審查發現）**：起點原取 `HISTORY.md` 最後一次被 commit 的 commit；輪次進行中若有流程外改動寫了 `HISTORY.md`（或併入它時改了 `HISTORY.md`），起點就往後移，這輪更早的 commit 不會被審到。不排隊之後中途插件會更常見。

決定（使用者拍板四件都做；第 5 項是對抗審查補上的既有缺口，使用者在存檔確認彈窗一併拍板，原文見「證據」）：

1. **整套測試只在頭尾跑**（`phase-ship.md` 步驟 1 書擋條文補寫）：整套紅燈後先單跑紅的那幾支；單跑就綠的視為假紅燈，不拿整套重跑來確認，記成一條發現照「發現的處理」結案——本輪造成的當輪修；既有的照「既有問題」問使用者現在修或記進 MAP；最終那趟要同一次完整全綠才能簽章，留著它最終那趟可能再紅，所以預設當輪修。修復期間只用 `--last-failed` 或指名檔案；整套只跑開頭與最終各一趟。不新增機制或欄位；各專案假紅燈的測試修正本身不在本決議範圍。
2. **不排隊＋流程外快速通道**：
   - (a) **任何工作都不等進行中的批次**：誰先驗完誰先上，上線只推自己驗過的那個版本。推送前兩件事都要成立、不靠記憶：①正式站回報的 commit（git 部署的專案看健康檢查端點；查不到就以 `git ls-remote <remote> <主線>` 為準並在正文講明）必須是 HEAD 的祖先；②`git log --oneline <正式站 commit>..HEAD` 列出來的只能是自己這批驗過的 commit（含併入用的 merge commit）；任一不成立就停下查，不硬推。非 git 部署的專案，部署前先推遠端主線。主線上有別批尚未上線的 commit、或主工作樹有不是自己的未 commit 改動（例如進行中輪次訪談、定稿期的決議與畫面改動）時，從最後上線的版本另開工作區來做：開之前先 `git fetch`；優先 `git worktree add --detach`，不建分支（git 守門只攔 `worktree add -b/-B`，另攔 `checkout`、`switch`；要開或切分支先彈窗問使用者）；`.env` 自己複製進去、不 commit；取號同時看主工作樹 `.constellation/decisions/`（含未 commit）與 `git ls-tree` 兩處的最大號。自己上線後由另一批併進去；併入後，那批自己當初那套驗證要在新的 HEAD 上重跑才能推（簽過全量全綠的重跑全量、拿同一次完整全綠；流程外重跑同一組靜態檢查與子集）；推送被 git 以非 fast-forward 拒絕時同此處理；零機制檢查（只適用簽過全量的批次）：推送前若 `git log --merges -1 --format=%cI` 晚於最後一筆簽章時間（`ship-evidence.md`，已歸檔就看 `archive/` 裡那份），代表簽章後併入過別批，就要重跑。機器鎖（出貨全量排隊）不動。
   - (b) **流程外入口就判定**：先讀要改到的檔案再判，不跑開工前盤點、筆數查詢、設計樹，保留一個「這件走流程外」的確認彈窗；進行中輪次自己的修正（審查或紅燈的發現、使用者選「現在做」的事、這輪票範圍內的調整）不算流程外。不算流程外的條件（對著 diff 判，碰到任一項就不是）：資料結構（migration、資料庫 schema 或 ORM 模型、會被存下來或跨模組傳遞的資料格式、共用型別與 API 契約）；RLS、policy 或權限判斷；金流計算、個資的讀取範圍或輸出；新增或升級套件；全域設定（建置、框架、middleware、全域樣式）；部署、連線、環境變數、憑證設定；這次動作本身要寫入或回補正式資料（一次性腳本、回補、手動改資料）；Constellation 的閘門程式行為或 hooks 設定（只改註解不算）；凍結名單內的檔案（另開工作區時看主工作樹那份 `design-frozen.json`）；改到的查詢或寫入碰到 `MAP.md` 記為超過大量資料門檻或會隨時間長大的表。另在入口看使用者這次的話判斷：做法有兩種以上、會讓使用者看到不同結果、而使用者還沒選定，也不算。做到一半發現碰到了，當場升成小流程。驗證＝全域靜態檢查（typecheck、lint、build；build 在另開的工作區跑，或確認沒有別人的站在用同一個建置目錄時才在主工作樹跑）＋改到的檔案所屬的測試子集（寫法同票級驗證指令縮圈），不跑出貨全量；子集含 e2e 或資料庫測試時照決議 026 退讓（用自己的站、不跑整套）。先給使用者看結果再審、再上線（看得見的改動截圖發私人 Artifact；給人讀的產出套真資料做樣本，照測試資料衛生）。一位對抗驗證員（獨立 context、顯式帶 model）拿使用者這次的原話與相關決議原文比 diff，另查框架執行期陷阱、會不會寫到正式資料、會不會改到別的畫面；邏輯改動在本地站把改到的路徑真跑一次；只回報寫得出具體後果的阻擋級、當場修；純文案，或只動單一頁面自己的樣式（不動共用元件與全域樣式、不動邏輯與資料）可省。只有取捨型拍板才落決議。`HISTORY.md` 那一行改為 `## <日期> <摘要>（流程外，無票）驗證：<相關測試＋結果>；使用者看過：<是／不適用（純後端、無可看產出）>；對抗驗證：<有（N 條）／無（純文案或單頁樣式）>`，「（流程外，無票）」要原樣連在一起寫。
3. **盲點審阻擋級先過反駁員，駁不倒才問使用者**：審查員拿不準照樣標阻擋級。每條阻擋級交一位沒參與過的反駁員（獨立 context、顯式帶 model、審查性質不降級；同輪阻擋級一次全派、平行、一條一位）試著推翻：屬使用者決定或判斷類的題，只能引使用者拍板的決議款號原文推翻；檔案行號或查詢結果只能推翻事實前提；附不出出處不算推翻。引文要逐字附款號，後面一句寫出它怎麼直接回答審查員那一題；引的是工程預設清單、已被取代的條款，或引文答不到這一題，都算推不翻——指揮官不得替反駁員補理由。推不翻的才轉成新題問使用者；被推翻的照「其餘發現」處理，不讓該輪重來。刪除「指揮官可把審查員標的阻擋改判成自己的工程預設」。保留決議 029 的保險：被推翻過的同一條，下一位新審查員再標一次就一律問使用者。收斂改為「每個視角連續兩位新審查員都沒挑出推不翻的阻擋級」；不設輪數上限（決議 022② 否決過，不動）。
4. **出貨對照改拿原始來源比，拆票對照表逐款列**：出貨 Spec 軸的分母改為本輪決議原文逐款（含工程預設逐條）、定稿記錄逐區塊元件清單（有 UI 時）、本輪需求的源頭原文（使用者原話、需求單），票只當找 code 的索引；源頭原文只認有落檔的（決議證據欄的使用者原話、repo 裡的需求單），與後來的決議不同時以決議為準、不算對不到。每款寫出哪段 code 或哪個畫面做到、用什麼確認，對不到或意思與原文字面不同即阻擋級；身分路徑只確認決議提到的每種身分都有走查紀錄，不新增走查活動；凍結日誌核對照留。build 每批審查的 Spec 維持決議 031 的逐票驗收，不改。weave 的決議承接對照表一筆決議有幾款就列幾列（工程預設逐條、定稿逐區塊），有 UI 時多一欄「定稿畫面跟這款有沒有衝突」，標不適用要寫一句理由；核准彈窗本體帶一份壓縮版「款 → 票號」對照，全表照常寫在正文；此表不得變成任何閘門的檢查欄位。
5. **出貨 Standards 軸審查起點改用上輪出貨歸檔 commit**：基準改取 `git log -1 --format=%H -- ':(glob,icase).constellation/**/ship-report*.md'`（`.constellation/` 根與歸檔目錄裡的報告一起找，報告與歸檔落在同一個 commit 的專案才取得到；首輪沒有就全 repo）——流程外改 `HISTORY.md` 不會讓它後移。審查員已用暫存 repo 實測三種情況皆完整涵蓋（前提是取到上輪歸檔 commit）。初版指令只認小寫、無後綴的 `ship-report.md`，在 crm-system 回空（歸檔檔名是 `SHIP-REPORT.md`、`ship-report-2026-09-25.md` 這類大小寫與日期後綴變體），照條文會退回審整個 repo，故改用 `icase` 加萬用後綴；改後在四個應用專案實測都落在最近一次歸檔 commit（crm-system `be1710f`、AI_project_hub `6384a7f`、活動計算 `8bfa21e`、polydesk-dev `545cd86`）。

原因：
- ①：條文早就說全量只當書擋，多付的 64 趟約七成花在「拿整套重跑確認紅燈是不是真的」——把「先單跑、單跑就綠算假紅燈」寫明，這條路就不再是預設出口。
- ②：等前批上線的代價是實打實的 141–448 分，而它要防的「把別批沒給使用者看過的東西一起推上去」，用「推送前核對正式站 commit 與待推清單＋另開工作區」就防得住，不必靠排隊。小改動走完整訪談盤點、跑出貨全量，成本與風險不成比例；改成入口判定＋對著 diff 判的排除清單＋一位對抗驗證員，把力氣集中在小改動真正會出事的地方（框架執行期陷阱、寫到正式資料、改到別的畫面）。
- ③：判「這題要不要問使用者」的權力，從寫工程預設的指揮官移到沒參與過的反駁員，且推翻必須逐字引使用者拍板原文——「不問使用者」從此有出處可查。
- ④：拿原文逐款比，才抓得到轉譯成票時漏掉或走樣的款；逐款列表讓使用者在核准拆票時就看得到每款落在哪張票。
- ⑤：出貨歸檔只在出貨時發生，起點不會被流程外的 `HISTORY.md` 改動往後推，這輪的 commit 不會漏審。

與既有決議的關係：
- **取代決議 029 第 1 點的「指揮官可以改判、那一輪不算乾淨輪」**，改由反駁員做；029 第 3 點的收斂條件改成「推不翻的阻擋級」，送審時「改判那一行的理由除外」改成「工程預設清單條目所附的推翻出處除外」；029 的「同一條被下一位新審查員再標一次就一律問使用者」保留。029 其餘（每輪全新審查員、三種阻擋級、工程預設清單就地改寫）不變。
- **取代決議 023 P12 的流程外門檻與 `HISTORY.md` 那一行格式**：原「不動資料結構／權限／凍結名單」保留，並擴充成上面能對著 diff 判的「不算流程外」清單；「註明有無獨立審查、全量測試結果」改為新格式。
- **決議 031**：build 每批審查的逐票 Spec 不變；出貨仍只看整體，只是分母改成原文逐款。假紅燈記成一條發現照 031 結案（本輪造成的當輪修、既有的照「既有問題」問使用者）；`next-round/` 唯一入口不變。
- **決議 026**：機器鎖與殺行程守門不動；流程外子集含 e2e／資料庫測試時沿用 026 的退讓做法。
- **決議 012**：書擋與批次修復不變，本決議只補紅燈後的單跑與假紅燈處理。

- 當時依據：14 輪出貨期整套測試統計（共 111 趟、約 54 小時，其中 runner 全量 92 趟、自組整套指令 19 趟；照書擋 runner 只需 28 趟，多出 64 趟、約 2,127 分，約七成由假紅燈推著整套重跑）與等待前批實例 141–448 分，皆為指揮官提供的盤點數字；Standards 軸起點的三種情況由對抗審查員以暫存 repo 實測。

代價：
- 流程外不跑出貨全量：跨模組的迴歸要等下一次出貨全量才會被抓到；「不算流程外」清單與對抗驗證員是這個缺口的主要防線。
- 不排隊：主線有別批未上線 commit 或主工作樹有別人的未 commit 改動時要多開一個工作區；先上線的那件要由另一批併入，併入後那批要重跑自己當初那套驗證（簽過全量全綠的就再跑一次全量）。
- 反駁員：每條阻擋級多一次獨立 context 的 token 與時間。前例：決議 029 背景記載 crm 第 40–42 輪反駁投票約耗 4,300 萬 token。
- 逐款對照：weave 對照表與出貨 Spec 軸的工作量隨本輪決議款數增加。
