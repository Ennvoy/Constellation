# 027 出貨承接票改收進 `next-round/` 抽屜，訪談收尾多問一題要不要併入

背景：決議 022⑨拍板「發現要留給下一輪的事立刻開票」，但沒拍票開在哪裡、下一輪由誰收。crm-system 與 AI_project_hub 兩個真實專案各自對這句話做了不同詮釋，兩種都出過事——

- **crm-system**：0914 輪的 `ship-report.md` 列了「留給下一輪的候選 9 條／待開票」，隨報告一起歸檔；0915 輪（transcript session `3a177e4f-e8f8-4359-9464-4cd160b39766` #4969）代理人先去翻上一輪怎麼做，選擇「下一輪候選（不開票）」，把 17 條（其中包含使用者親口交代「底層資料優化，出貨後要主動找他討論」）寫進 T-140 票面與 SHIP-REPORT，結果整份跟著 T-140 一起進了 `archive/`。兩輪加起來 26 條「候選」，下一輪的 `grill-close.md` 一條都沒收進來，只有 `insertFinalization` 一條技術性條目靠 `MAP.md` 留下。
- **AI_project_hub**（session `0866f059-dd15-47a7-91c2-a969fde99ba6`）：承接票直接開在 `tickets/`（T-538 01:15 開；另有 T-540、T-541），出貨歸檔時腳本明寫「這幾張不歸檔、`approved` 設 `false`」（歸檔 commit `7df5198`，20:45）；20:48 推送後正式站冒煙檢查又開出 T-542（commit `fb2ac89`）。歸檔完成後 `tickets/` 剩 4 張 open 票、`approved: false`、無 `grill-close.md`，下一個 session 的總控 Step 0 會依「有票但未核准」誤判成「票清單待核准」，轉去 weave 請使用者「重新核准」根本不是新開的舊票。

同一條規則、兩個專案各自發明一套做法，而且兩種都會讓下一輪的人白做工或漏接：crm 那種讓待辦消失（決議 022 盤點到的「接手率不到 1%」重演），hub 那種讓總控走錯路。

決定：

1. **承接票改放 `.constellation/next-round/`，不放 `tickets/`**——格式同一般票、`status: open`，目標段註明來源與發現原文。「`tickets/` 只裝本輪的票」這條界線用資料夾分開，不靠標記或關鍵字判斷。適用範圍不限於出貨審查軸的建議級發現，出貨階段（含推送後檢查）與 build 期彈窗選「記進下一輪候選」的都算，一律開票放進這裡，不另列文字候選清單。
2. **訪談收尾多問一題，排在本節所有題目最前面**：`next-round/` 有票時，用一次彈窗（不逐張各開一窗）問「併入推薦的那幾張（推薦）」／「全部留著」／「全部併入」，也可以直接打票號或寫「T-xxx 不做了」；答案要先算進「大／小流程」「是否需要 UI」「高風險標記」的估算範圍，只要選了併入就不再提供「流程外」選項（流程外不拆票、沒有地方承接）；純流程外輪次不問這一題。選擇寫進 `grill-close.md`「一句話任務摘要」，不新增欄位。
3. **weave 收尾時處理 `next-round/`**：讀摘要把併入的票 `git mv` 進 `tickets/`，票號不變，但 `zone` 與驗收條件依拆票規則重新核對（不是原樣照抄）；小流程時這些票各自獨立、不併進任務卡，輕量⑤驗證範圍涵蓋它們的驗收條件。使用者選「不做了」、或後來改用流程外做掉的票，`git mv` 到 `.constellation/archive/next-round-closed/`，決議記錄補一句原因。`next-round/` 裡的票不驗、不關——要做先經這一步搬進 `tickets/`。這條由機器擋，不只靠紀律：`close-gate.mjs`（關票刷卡機）與 `commit-gate.mjs`（commit 守門，PreToolUse 與 git 原生 pre-commit 兩條路徑）都新增守衛，凡把抽屜裡的票標成 `status: done` 一律擋下（訊息同時指路「經 weave 搬進 tickets/」與「不需要做了就搬進 archive/next-round-closed/」兩條出路），已補測試涵蓋 Write／Edit／apply_patch／staged commit 各種路徑。
4. `ticket-template.md` 的編號規則改為接續 `tickets/`、`next-round/`、`archive/`（含 `archive/next-round-closed/`）已用過的最大號。
5. **取代決議 024 D4 附帶那半句例外**——原文「或只剩出貨時開給下一輪的承接票除外」由本決議取代：承接票不會再出現在 `tickets/`，總控 Step 0「現況矛盾照實告知」不再需要這個例外。

原因：兩個專案的失敗模式互補，正好證明問題不在「要不要立刻開票」（022⑨已經拍板要），而在「開在哪裡、誰來收」這個純技術落點沒定義，逼得每個專案自己發明一套，而發明出來的兩套都失敗。用一個獨立資料夾把「屬於下一輪」和「屬於本輪」分開，總控 Step 0、開場閘門、出貨進場條件都不必為了排除承接票另加例外或猜關鍵字（原本的 `CARRY_OVER_RE` 關鍵字判定就是這類漏網之魚的來源之一）；訪談收尾多問一題的代價換來承接票有了固定收件點，不再有「開了等於消失」或「留著等於誤導總控」兩種結局。

與既有決議的關係：

- **不推翻決議 022⑨**：022⑨拍的是「發現承接事項要立刻開票，不要拖到之後」，本決議只補上票該開在哪、下一輪怎麼收——落點是純技術取捨，不是推翻。
- **取代決議 024 D4 附帶句**：024 D4 原文加的「或只剩出貨時開給下一輪的承接票除外」這半句技術性附帶（非使用者逐題拍板內容），由本決議取代，024 決定本身（D1–D4 四題）不受影響。

待辦（不在本決議落檔範圍內，需另外派工執行）：AI_project_hub 的 `.constellation/tickets/` 目前仍卡著 T-538、T-540、T-541、T-542 四張已核准搬移的承接票，且該專案有 session 在跑（transcript 22:19 仍在更新，決議 287–296 尚未進 git）——搬遷須先跟那個 session 協調、不能直接改它的工作區，且需連帶補問一次「這批票要不要併入」（T-541 動權限、T-540 動 model-console，都跟本輪重疊，應列推薦），問完寫回它自己的 `grill-close.md`。這件事跟本決議「規則要怎麼定」是兩件事，規則核准不代表搬遷已完成。

另記：P14 簽章驗證三份合一（`close-gate.mjs`／`commit-gate.mjs`／`verify-runner.mjs` 共用的簽章與解析邏輯）改採延遲同步載入 `gates/evidence.cjs`、載入或執行失敗即擋下（fail-closed），屬執行端技術判斷、不推翻任何拍板決議；實作順序是先在現行三份鏡像程式碼上補齊往返測試並跑綠，再動手抽共用模組、跑綠確認行為不變，最後才刪掉鏡像程式碼。
