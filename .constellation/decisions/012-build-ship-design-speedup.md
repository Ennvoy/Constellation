# 012 流程提速三項：平行票正式驗證整合後只跑一次＋ship 阻擋級批次修復＋小工程直通與票的最小經濟尺寸

背景：使用者反映 Constellation 實際開發比舊 Flow 更耗時。三路實證盤點（Asteria／活動計算／crm-system 的 `.constellation/` 全量數據＋crm-system 舊 `.flow/` journal）＋條文儀式審計＋Codex 跨家族對抗審查，找到多個流程級耗時根因。

決定：採納三項——①平行批次的正式驗證改整合後只跑一次：worker 只做領票→測試先行→實作轉綠＋自行以測試框架跑單點檢查（不經 runner、不落證據），runner 落證據的正式驗證只在序列整合後跑；②ship 阻擋級發現改批次修復：全軸報告出齊→去重合併同根因→一批修完→一次受影響範圍複驗→原提出軸同回合逐條標示 resolved/unresolved，修復動到共用契約／schema／權限／全域設定時仍重跑全量；③小工程直通升主線（不論 Claude Design 此刻可不可用，改按鈕級小工程一律直接改 code 給使用者過目，定稿記錄與凍結照跑）＋weave 拆票規則加「票的最小經濟尺寸」（拆細必須換得到平行度或獨立驗收價值，否則優先合併）。同場拍板否決：盲點審輪數設上限（維持現行不設上限）、效率體檢工具（先不做）；訪談彈窗批次另見決議 013。

原因：①整合前跑 runner 的簽章證明不了整合後狀態，同一張票白付兩次全價（phase-build.md 原條文明文要求 worker 跑步驟 1–4、整合後又跑同步驟 4）；②N 條阻擋級逐條各跑一輪「修復→複驗→複審」，實測審查段佔整輪 30–40%；③「小工程直接改 code」原本只寫在降級路徑，工具可用時反而要走完整產線（能力倒掛）；每票固定成本（runner＋證據＋關票＋地圖＋commit）讓為平行而拆細的票入不敷出。三項均不動「真鏈路驗證、機器擋假完成」底線。

證據：拍板脈絡＝彈窗「採納範圍」使用者回「先改1、2、4，健檢先不要」（選項原文含四項改法與健檢工具的白話說明）。當時依據：crm-system 單票 T-013 耗時 158 分鐘中 116 分（73%）在跑驗證、決議 121（db 全量 workers=1 53 分鐘）；活動計算第二輪審查＋修復佔 3h47m／9h57m（38%）；Asteria 第一輪四輪盲點審 80 條發現多數超出使用者要求；Codex 對抗審查（session 019fe9b1-cee0-7eb3-8e6c-9ae1a37377d5）判定①為最優先改動、否決「驗證全面背景化」與「24h 新鮮度改 zone 判定」兩案（傷「真」）。
