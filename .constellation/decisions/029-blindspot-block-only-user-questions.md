# 029 盲點審阻擋級只留「要問使用者的題」＋工程預設清單就地寫、不逐輪疊決議檔：撤回決議 028 B

背景：使用者先前主動提出，不要用同一位審查員做複查——決議 028 B 那套（喚回、8 輪改派、最終確認、記名）應該撤回，但要指揮官想清楚有沒有更好的做法可以兼顧速度與品質（使用者原話見下方「證據」，非本段逐字引述）。指揮官委託研究並經對抗審查（研究稿與批判稿全文見暫存 `scratchpad/bs2/study.json` 的 `judge`／`critique` 欄，本決定採批判稿修正後版本），拿 hub 本輪與 crm-system round-0915 兩案的實測資料，比較「撤回後只回到每輪全新審查員（其餘照舊）」與「阻擋級改判準＋工程預設清單」兩案，彈窗一題請使用者拍板。

決定（採對抗審查修正後版本，本決定同時修正決議 024 D2 本文）：

1. **阻擋級重新定義為「要問使用者的題」，只有三種**：
   (a) 要使用者選、選項會帶來使用者或同仁看得到的不同結果，而既有拍板推不出答案；
   (b) 兩條使用者拍板過的決議互相打架；
   (c) 指揮官的工程預設擴大或收窄了使用者拍板的範圍，需要使用者追認。
   審查員拿不準一律標阻擋。指揮官可以把審查員標的阻擋改判成自己定，條件是在工程預設清單那一條寫一句理由（例如「依 NNN 推得出」，NNN＝推得出這個答案的那條使用者拍板決議），而且**那一輪不算乾淨輪**（不計入下面收斂所需的連續兩位新審查員之一），由下一位新審查員檢查有沒有越權（第 c 類）。**同一條被下一位新審查員再標一次阻擋，指揮官不得再改判**，一律照阻擋級規則問使用者——避免反覆改判讓收斂條件永遠湊不齊。
2. **其餘發現不讓這一輪重來**：會出事但指揮官補得了的、實作細節、補丁之間的縫，照修，但不再送審一輪。指揮官自己補的，不再每輪開新的決議檔疊補丁，一律寫進固定檔案 `decisions/engineering-defaults.md`（工程預設清單）——**就地改寫，不加「修正 by」**：每條只寫要保證的結果，不寫做法；要寫程式現況事實必須附可重跑的出處（檔案:行號或查詢句），沒查過的不寫。**處置紀錄（誰提了什麼、處置了沒）不放進 decisions/**（既有規則；hub 專案曾把「索引＋處置表」寫進決議檔，同樣算違規）。
3. **每一輪、每個視角都換一位沒參與過的新審查員**，只讀送審清單本身的檔案（`CONTEXT.md`＋`decisions/`＋工程預設清單），不附上一輪的發現、變動清單或處置說明（工程預設清單裡改判那一行的理由除外）；四類問題（矛盾、未定義概念、缺席的異常路徑、該問而沒人問的問題）照找、照全部回報——找的範圍不縮小（決議 022② 否決的「縮小審查範圍」不變）。每個視角**連續兩位新審查員**都沒挑出阻擋級，就算收斂。以能開獨立 context 的方式起：Claude Code 用 Agent 工具或 Workflow（每個呼叫顯式帶 `model`），Codex 用其原生做法；主線不得兼任審查員。Claude Code 與 Codex 規則一致，不再需要降級。
4. **下游承接**：`phase-design.md` 的決議覆蓋檢查一律要讀工程預設清單；`phase-weave.md` 進場讀清單，每一條都要對到一條驗收條件，對不到不得寫 `approved`；核對中發現某條其實該由使用者拍板時，比照「決議互相矛盾」退回去問，不在 weave 裡自己拍板；`phase-ship.md` 歸檔清單加 `decisions/engineering-defaults.md`（隨輪歸檔，下一輪從空檔開始，同 `grill-close.md` 生命週期）。
5. **保留**：決議 028 A（大流程盲點審審到收斂才進 design／weave）、收斂行與使用者喊停行、換 session 接回（每輪本來就是新審查員，接回就是派下一位新人）、舊規則 grill-close 補行例外、024 D3、D4、首輪不設條數上限並列情境角度。
6. **修正決議 024 D2 本文＋連帶修訂既有決議**：024 D2 原文「收斂標準改為連續兩輪零阻擋級新發現、阻擋級＝會讓實作做錯或做不下去」由本決定第 1、3 點取代（024 檔頭已加註）；決議 028 B 整段 superseded by 029，028 A 不動（028 檔頭已加註）；022②「訪談盲點審維持現行做法不改」檔頭已加註「收尾保證範圍的改變已在 029 由使用者拍板」——022② 否決的是縮小「找什麼」與設輪數上限，這兩樣不變；本決定縮的是「哪些發現要讓這一輪重來」，性質不同，但收尾這一環的保證範圍確實變窄了，故加註提示。

原因：舊制（每輪全新審查員、阻擋級＝會出事就重來）已實測不收斂——crm-system round-0915 跑 42 輪、約 26.4 小時；第 1–39 輪中有 38 輪回報可算，合計 964 萬 token、898 分鐘（第 23 輪的回報沒進主對話，未計入），第 40–42 輪另跑反駁投票、耗約 4,300 萬 token（未計入本決定的省幅比較基準）；仍未收斂。hub 教學平台 v2 跑 43 輪、23.4 小時，使用者最終喊停。病根不是審查員本身，是補丁：hub 本輪 146 條阻擋級中補丁互相打架 77 條（53%）、需求層缺漏 51 條（35%）、實作細節 14 條（10%）、其他 4 條——按「最後由誰定」重新歸類，146 條裡約 94 條（64%）最後是指揮官自己定的，不是真的該問使用者的題；crm-system round-0915 第 1 輪之後確認成立的 11 條中補丁 9 條、實作 2 條、需求層 0 條，同樣以補丁為主。決議 028 B「喚回同一位審查員做複查」雖然實測較快（hub 本輪至今 18 個審查輪次、146 條阻擋級中，凡喚回同一位審查員複查的輪次合計挑出 18 條，100% 是補丁問題），但代價是複查者可能被指揮官的處置說明牽著走，且真正兜底的防線仍要靠一輪最終確認；凡全新審查員的輪次反而更容易挑出高嚴重度發現（合計挑出 128 條，其中 30 條高嚴重度中 26 條由新人找到）。本決定改採「每輪都是新審查員＋阻擋級只留三種要問使用者的題」，把「審查快」與「不被同一人帶著走」兩件事分開解決：審查員仍然每輪重新看全集（不喪失決議 022② 否決縮小範圍的立場），但只有真正該問使用者的題才會讓輪次不過關，其餘由指揮官直接處理並寫進工程預設清單，交給下游拆票、測試、出貨審查接住。「工程預設清單就地改寫、不逐輪疊決議檔」是為了消除 hub 已出現的問題——16 份工程預設檔（AI_project_hub 決議 316、324、327…353）佔送審集 71.5%（137,253／191,960 字元），檔案越疊越厚，每輪送審集跟著變貴，權限視角一位新審查員的累計輸入從首輪的 1,040 萬 token 漲到第二次最終確認的 1,790 萬 token。

代價與風險：
- **工程預設清單最後一輪才補的條目，後段只查「照做了沒」、不查「寫得對不對」**：拆票、測試、出貨審查都只核對是否落實成驗收條件，不會回頭質疑條目內容本身對不對——指揮官寫錯的「結果」一路綠燈到出貨都不會被攔下。使用者已撤回「改完快驗」，本決定不為此另補機制，只誠實揭露。
- **crm 那種案子估計降到個位數輪，但這是用舊制彈窗次數推的，偏樂觀、未實測**：舊制下指揮官偏寬鬆、自己定掉許多題，跟新制「審查員拿不準就擋」的前提不一致；且約有 3 題晚冒出的需求題（第 4、23、40 輪）可能到後段才發現，其中第 40 輪那題（連線池 POOL_MAX）出貨的效能量測有機會接住，第 4、23 輪那兩題沒有便宜的停止規則能提前抓到。
- **hub 那種一直冒出要問使用者的題的案子，輪數降不多**：後期新人挖到的多是高嚴重度、後段接不住的真問題，本決定刻意不砍這塊；換到的是每輪成本不再上漲（每輪約 25 分鐘），不是輪數大幅減少，多半仍要使用者喊停。
- **灰色地帶可能讓彈窗變多**：「拿不準就標阻擋」會讓部分過去由指揮官自己定的行為規則改判成要問使用者；用「指揮官可以改判、但那一輪不算乾淨輪、由下一位新人抽查有沒有越權」來緩和，不是完全消除。
- **工程預設清單隨輪歸檔，跨輪不保留**：清單移入 `archive/` 後，下一輪的審查、畫面、拆票都不會自動看到上一輪保證過的結果（例如某條「停用帳號不得直接打 API」），除非該內容另外進了 `CONTEXT.md` 或程式本身／測試守住。這跟編號決議（`decisions/NNN-slug.md`）跨輪保留不同，是本決定刻意的取捨（避免清單無限累積、跟 `grill-close.md` 生命週期一致），但代價要明講：真的需要跨輪保留的保證，要主動搬進 `CONTEXT.md` 或另立編號決議，不能指望工程預設清單本身跨輪還在。
- **hub 本輪的過渡**（技術取捨，指揮官自定，非使用者逐題拍板）：已寫的 16 份工程預設決議檔（`AI_project_hub/.constellation/decisions/316～353`）不回頭改寫成 `engineering-defaults.md`——回頭改寫要花大量時間還可能漏掉內容，只有本決定生效後新產生的工程預設才寫進固定檔案；其中 332 那份違規的「索引＋處置表」比照辦理、不回頭拆解，但不再新增這類記錄。切換後連續乾淨輪數計數歸零，從套用本決定的下一輪盲點審開始重算（不沿用舊制已經跑掉的輪次）。成敗標準的「8 輪」同樣從套用本決定後的第一輪盲點審起算。

成敗標準：下一個大流程輪次在 8 輪內自然收斂、不需要使用者喊停，即視為成功；未達成則由指揮官依決議與記憶主動追蹤、主動建議調整或撤回本決定，不必等使用者主動提起。
