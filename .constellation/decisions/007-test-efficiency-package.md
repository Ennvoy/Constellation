# 007 測試效率入條文：收斂組合包五機制＋資料庫觸發式

背景：應用專案（crm-system 為例）ship 全量驗證隨開發推進從約 1 分鐘膨脹到數小時。驗屍找到四個根因：測試預設寫在最貴層（unit 單條 0.07s vs db 單條 4.2s，差 60 倍）、DB 測試打跨區雲端（單次往返 66.6ms、單測平均 63 次）、journey 拆多支各自重付 production build 等固定成本、驗證耗時無人記錄（journey 範圍三度擴大無任何機制點名）。既有「縮圈」（票級選子集）與「書擋」（ship 紅燈節奏）都管不到 ship 全量本身的絕對耗時。

決定：採三路獨立設計提案的收斂組合包五機制——①最低層原則（測試寫在能抓到該 bug 的最低層，新增 e2e 須在票的決議記錄留一句「為什麼低層測不到」）②快形態鐵則（verification-playbook 新段「真鏈路也要快」：本地同引擎隔離庫＝真依賴、少往返批次寫法、登入態一次取得重用、輕量資料隔離、追蹤產物只留失敗）③journey 合併（同框架多 project 合併單一呼叫，昂貴固定成本一次付）④runner 逐指令計時＋ship 報告耗時對比（總耗時較上輪成長逾三成即點名最貴指令、建議開優化票；不設硬預算、不影響綠燈判定）⑤ship 全量預期超 10 分鐘背景跑、期間平行開兩軸審查。不採 budgetSec 硬預算與 smoke lane（警示疲勞／新桶維護成本，留待計時數據佐證後再議）。其中「本地隔離庫」採**觸發式**：平常只要求少往返寫法；某專案 db 層驗證超門檻時才針對該專案提本機化方案拍板，不預先建基建、不隨專案數複利。耗時行採證據筆內**獨立一行、不帶反引號**——close-gate／commit-gate 的證據行解析 regex（`COMMAND_LINE_RE`）行尾錨定「（exit N）」，把耗時塞進指令行會令驗簽解析漏配、合法關票被擋，且需同步改兩支安全閘門鏡像；獨立行被解析器天然忽略，零風險零鏡像改動。

原因：五機制是三個互相隔離的設計提案的最小公約數（分歧僅 budgetSec 與 smoke lane），每條對應一個實證根因，零新桶、零基準線、零新儀式；ship 不縮圈的正確性底線不動。觸發式呼應使用者「同時開發專案多且會更多」的顧慮與機器實況（Docker／PostgreSQL／Supabase CLI 均未安裝，本機庫＝從零蓋基建；且目前僅 crm 慢、其他專案都快）。

證據：彈窗「效率機制」使用者選「A 推薦組合」（原話「我可以接受A改動但我要先提出我的疑問，本機資料庫這件事情因為我同時開發的專案很多…需要你針對這塊跟我討論再決定」）；後續彈窗「資料庫策略」選「路線1 觸發式（推薦）」。當時依據：三份調查（母本機制盤點／crm-system 驗屍／業界快測法）＋三路獨立提案；crm 實測數字出自該專案 decisions/121（db 全量 workers=1 跑 53 分鐘）、SHIP-REPORT（test:db 31.6 分＋e2e 20.0 分）、T-030（workers=4 後降至 13.9–15.6 分）；本機實查 docker／psql／supabase CLI 皆未安裝。
