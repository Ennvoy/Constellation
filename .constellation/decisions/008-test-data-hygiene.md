# 008 測試資料衛生入條文：記號區隔＋所有權清理＋禁全庫全表清除（安全鐵則級）

背景：使用者盤查發現三個資料安全缺口——「禁全資料庫清除」「驗證後只清自己產生的資料」「測試資料與正式資料明顯區隔」在現行條文中，第一項只被間接碰到（phase-build 大事條款管的是實作時直接執行的操作、效率鐵則第 4 條是效率角度非安全禁令），後兩項完全沒寫。而條文強制真鏈路打真 DB（禁 mock），應用專案實況是測試與正式資料同住一庫（crm 測試與 882 萬列正式資料同庫，並自蓋 globalSetup 全庫快照保險防誤刪——專案在用土砲補母本沒給的保護）。

決定：補為**安全鐵則級**（非建議級）——①verification-playbook 新增「測試資料衛生」節三條：測試資料必帶可識別記號（固定前綴／專用測試帳號／專用網域 email）、清理只清「本次測試建立、帶記號」的資料（能回滾就回滾）、禁止 DROP／TRUNCATE／無條件 DELETE 出現在測試 setup／teardown（專用隔離測試庫內的 reset 明文例外，不打到未來本機化的正常做法）；②反模式清單加第 4 條「清理範圍越界」＝票不算驗證通過，與禁 mock 同級；③phase-build 大事條款補明「破壞性 DB 操作包含寫進測試程式碼裡的」；④DESIGN.md §6 第 2 點補一句同步。

原因：清理範圍越界是不可逆的資料損失風險，與效率不同層級——效率違規只值建議級，安全違規值硬擋；隔離庫例外讓鐵則與觸發式本機化（決議 007）相容。

證據：彈窗「資料衛生」使用者選「補為安全鐵則（推薦）」；使用者原話「驗證後的清除資料應該只清除自己產生的資料，且測試資料應該要跟正式資料有明顯區隔不混淆」。當時依據：全 repo grep 確認三項現況（TRUNCATE／清理／測試資料等關鍵字僅命中 phase-build:46 與效率鐵則第 4 條）；crm 同庫實況出自其 T-026／decisions/121。
