# 019 開場讀檔指令涵蓋「純查詢型 session」，並附地雷區條數

背景：2026-08-17 在 crm-system 專案實際踩到 DESIGN.md §「已知取捨」早就寫下的那條風險——
「導航模式下，知識內文的送達靠指令不靠機器」。當天使用者的開場是三個「為什麼會這樣」的問題，
執行端判斷「這是查詢不是開工」而沒有 Read `MAP.md` 全文；但查問題查到一半就開始跑 db 測試、
連正式庫，撞上地圖「地雷」區早就記載的一條（測試的還原機制會把剛匯入的 `dataset_cutoffs`
倒退回去，導致導覽列「資料截至」倒退一天）。同區另有幾條同性質的坑（長時間測試不要走
PowerShell 管線、中途砍掉 db 測試會引爆連鎖、`select distinct stat_date` 看似已優化其實掃整表），
當天是碰巧繞過的，不是判斷力躲過的。

決定：**不加任何機制**（維持 DESIGN.md 的既有取捨），只改閘門 3 置頂指令的措辭：

1. 明講**「只是回答問題／只是查一下」同樣要讀**——原句只有「開工前必讀」「動手任何工作前」，
   兩個詞都暗示「要開始做事才需要」，而純查詢型開場是最常見的入口。
2. 講清楚**不讀會漏掉什麼**：地圖的「已知缺口與地雷」區記的是**動手方式**的坑（測試怎麼跑、
   腳本怎麼下、查詢怎麼寫），而開場只注入模組索引、那一區不在裡面。
3. 附上該區的**條數**（`countMapHazards()`：標題含「地雷／缺口／未竟」的二級章節內的條目，
   `~~劃掉~~` 的已解決項不計）。

原因：
- 條數是**一個數字、永遠一行**，注入量與專案規模解耦（決議 002）因此不受影響，但「還有 N 條坑
  沒看過」比「有這個檔、共 309 行」有力得多——crm-system 當天的實際值是 92 條。
- 加機制（例如 PreToolUse 擋住沒讀過 MAP 的 session）會是第六道硬閘，違反 §「不加新硬閘」，
  且對「該讀多少才算讀過」無法給出可驗證的判準。
- 沒有 MAP.md 的專案（例如本工作流母本自己）不印第 2、3 點——提一個不存在的東西會讓讀的人
  花時間確認是不是自己漏看了。

成本：注入量 +92 字元（crm-system 實測 5,147 → 5,239，9,000 failsafe 下餘裕 3,761）。

證據：兩專案 headless 實測——crm-system（有地圖、92 條）印出完整句子與條數；Constellation 母本
（無 MAP.md）句子在「連正式庫是常態。」自然收尾、不提地圖。DESIGN.md §4「接續」與
§「已知取捨」兩處已同步。
