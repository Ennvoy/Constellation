# 024 流程大結構檢查四題：盲點審不擋畫面且收斂改連續兩輪零阻擋、給人讀的產出先看真資料樣本、繞開限制前先重量

背景：以 crm-system 與 AI_project_hub 兩專案的 transcript、決議與歸檔，對五步流程做大結構實測（一輪牆鐘拆解、關鍵路徑、退回重做、盲點審逐輪統計），提案經對抗審查收窄成四題，逐題請使用者拍板（即本決議）。四題都只改條文、不動閘門程式；另順手修 `phase-grill.md`「完整性三保險」與同檔「四保險」不一致的筆誤。

決定：

- **D1 盲點審不擋畫面製作、看圖拍板前審完**：大流程需要 UI 時，`grill-close.md` 寫定即可進 design，獨立盲點審改在背景跑（Claude Code 端用背景 agent 或 Workflow）；新題在畫面製作的空檔插問（題目加「〔盲點審〕」前綴、一題一窗、會動到畫面的題優先）。5b 看圖拍板前必須已收斂；收斂後在 `grill-close.md` 檔尾補一行「盲點審：已收斂（第 N 輪）」（狀態註記、不算新增欄位）。weave 進場與總控 Step 0 看到這一行才放行；換 session 時 grill-close 在、這一行不在，就先接回盲點審（需 UI 時畫面製作可同時繼續，5b 前要收斂）。送審決議集＝訪談決議＋盲點題答案，畫面階段新增的決議不納入（與原本相同，不擴大範圍）。無 UI 的大流程照舊依序跑完才進 weave（不與拆票並行）；Codex 端沒有背景 agent，照舊依序跑完才進 design；小流程照舊可省略。
- **D2 收斂標準改為連續兩輪零阻擋級**：審查員把每條發現分兩級——阻擋級（會讓實作做錯或做不下去：矛盾、未定義概念、缺席的異常路徑、該問沒人問的取捨）與小毛病（交叉引用沒對上、措辭、格式這類簿記）；小毛病由指揮官直接修進決議檔，不再為它送審一輪。收斂標準由「連續一輪零新發現」改為「連續兩輪零阻擋級新發現」；仍不設輪數上限。首輪指令不設發現條數上限，並列出情境推演角度（時序情境、migration 順序、各角色的 UI 路徑）。審查員仍回報全部類別，不是 022② 否決的「只審打架」。
- **D3 給人讀的產出，動工前先看真資料樣本**：流程外或小流程、改動主體是給人讀的產出（週報、推播、報表文字、口徑數字）、且改的是呈現方式或口徑時，盡量在動工前用拋棄式腳本套真資料做成樣本（私人 Artifact 或本地檔），最晚在審查與上線前；使用者看一次，要改就重做樣本；要不要升級流程照既有規則（動資料結構或權限才升），不因看樣本而自動升級。
- **D4 為繞開限制而蓋新機制前，先實測限制還在不在**：新機制是為了繞開某個既有前提或外部限制（上限、單次成本、量級）而建、且預計拆 3 張票以上時，最晚在訪談收尾用拋棄式腳本在真實環境量一次該前提對這次的真實量是否仍成立（不進 repo），數字帶進收尾彈窗。寫成 022⑩「大量資料」段的一句附則，不另設檢查點，不併進邏輯原型（它明寫不接真 DB）。另在總控 Step 0「現況矛盾照實告知」條文下加一句：`tickets/` 有票卻沒有 `grill-close.md` 視為矛盾、照實告知（出貨歸檔做到一半、或只剩出貨時開給下一輪的承接票除外），並註明這句攔不住刻意繞過。

條文落地時依對抗審稿補的執行細節（指揮官判斷，非使用者逐題拍板；使用者要改可再議）：

- D2 的分級判準：修正需要改動或補定行為、數值、條件、範圍、權限，或要在兩種說法間選一個，就是阻擋級；只動字面、指向、格式的才是小毛病；拿不準一律歸阻擋級。不動上述任何一項的純技術細節（例如函式簽章、測試波及範圍；crm 0915 輪審查員另分一級「應補」、由指揮官自決的技術缺口即屬之）照鐵律 2「事實不問人」由指揮官自決，不算阻擋級——這與「連續兩輪」依據的 crm 阻擋定義一致；若把「應補」算進阻擋級，收斂會遠慢於本決議的推估。
- D1 的放行行與範圍：使用者明示喊停時寫「盲點審：使用者喊停（第 N 輪）」，效力同收斂行（這是使用者的決定，不是輪數上限，與 012、022② 不衝突）；收斂後又經增量重訪落了新的訪談決議，刪掉收斂行重跑；舊規則下寫的 `grill-close.md` 若已記載盲點審跑完，照實告知使用者、同意後補收斂行即可；design 階段在收斂前落的決議標題帶〔畫面〕，送審清單據此排除、收斂時拿掉前綴（換 session 後才分得出送審範圍，也不讓下一輪誤排除）；盲點審新題不適用鐵律「frontier 清空前禁止動手實作」，但擋 5b 與 weave。
- D4 的量法：條文改寫成「前提對這次的真實量還成不成立」，量真實量級離上限多遠、單次成本隨什麼變——R10 的 23 萬列上限本身一直都在（決議 304 仍拿它算門檻），被推翻的是「這次會碰到上限」與「成本隨天數增加」兩個前提，照字面「量限制還在不在」會得到「還在」而照樣蓋新機制。量測限唯讀、最小樣本，會寫入、計費或加重正式站負載的先問使用者。

連帶修訂既有決議（原檔內容保留，衝突處以本決議為準）：

- 022②「訪談盲點審維持現行做法不改」→ 盲點審的時機（原本收斂才轉交下一階段）由 D1 取代、收斂標準（原本連續一輪零新發現）由 D2 取代；維持不設輪數上限（見 012）與否決縮小審查範圍的部分不變。

原因：

- D1：盲點審一輪接一輪卡在畫面之前的關鍵路徑上，每輪 40–60 分鐘、92% 是模型思考（022②）；另有真漏洞——舊條文先寫 `grill-close.md` 再跑盲點審，總控 Step 0 只看 grill-close 就往下走，盲點審沒跑完就換 session 時會被無聲跳過。使用者不選 crm 決議 355 的「驗收後才審」：驗收後才審可能要回頭改已驗收的畫面（crm 0915 輪第 42 輪 53 條發現中有 2 題動到畫面），使用者最在意畫面與定版一致。
- D2：大案停不下來、後段多是簿記。hub 教學平台 v2 跑 43 輪、23.4 小時未自然收斂，使用者以 hub 決議 133 手動喊停（第 38–42 輪 4／4／6／3／4 條、剩餘集中在簿記型）；crm 0915 輪 42 輪橫跨 5 天、審查員約 20 小時；兩案後段每輪穩定 3–6 條。crm 三個中小案 6–12 輪、半天內收斂，改標準對它們影響小。選「連續兩輪」不選「一輪」：使用者問「選這個會不會有問題在其他環節才被找到」，指揮官答——後面拆票寫驗收條件、實作時 worker 標 blocked、出貨 Spec 軸、使用者驗收畫面都抓得到一部分，但「該問卻沒人問」的例外情境後面各關都以既有決議為標準、抓不到；crm 0915 輪有 3 次「這輪零阻擋、下一輪又冒出阻擋」（第 17→18、19→20、36→37 輪），一輪就停會漏，連續兩輪都攔得住。首輪不設上限：crm 決議 322 那輪（12 輪）首輪指令寫「最多 12 條發現」、回報正好 12 條；第 6 輪主線指定往「還沒被任何一條碰過的角落」掃、第 9 輪指定換到既有第 1～5 項做系統性掃描，這兩輪的發現逐條比對後全數指向更早落的決議。這不能證明首輪一定會漏（那兩輪是主線刻意排的角度），但把這些角度寫進首輪指令、取消條數上限是零成本的補法。
- D3：hub 週報那輪走流程外，上線後才看到真週報、翻案兩次（決議 215 規則版上線半天即由 216 推翻，216 上線後的誤判再由 217 修正），真正白做約 2–4 小時；同專案決議 214、217 已有「套真資料的示意頁看過再拍板」先例。代價約 10–20 分鐘＋1 題。
- D4：crm R10 以舊決議 065「Tableau 單次約 23 萬列上限 → 必須逐日切分」為前提建成功帳本（決議 303），這個前提從未重量；決議 304 以唯讀實測（pm 型 3 次請求）量到 1 天與 30 天都約 11 秒、列數離上限很遠，T-094～T-103 這批 10 張票有 9 張作廢，實工窗口約 7 小時。原提案的觸發條件「有兩種以上做法」在這案不會觸發（當時沒人想到第二種做法），所以觸發改為「為繞開某個前提而建」。該輪沒有 `grill-close.md`、Step 0 照樣放行進實作；那輪是正式站出事時的緊急作戰，新加的矛盾提示攔不住刻意繞過，只擋無心漏掉的訪談收尾。出貨時開給下一輪的承接票放在 `tickets/`（`phase-ship.md`「發現的處理」），而歸檔步驟寫的是「把本輪 `tickets/` 移入 archive」，執行者可能把承接票留在原處，留下來就會出現「有票、沒有 grill-close」；所以矛盾提示除了歸檔做到一半，也排除只剩承接票（目標段註明來源軸）的狀態。
