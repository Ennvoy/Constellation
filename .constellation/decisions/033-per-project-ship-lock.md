# 033 出貨鎖改成每專案一把：只有同專案才排隊，殺行程守門讀全部專案並修正兩個提前放行的縫

> 取代決議 026 第 1–2 點「整台機器一把」的範圍（單一 `machine` 鎖、`--scope ship` 對整台機器排隊），改為每個專案一把；026 第 3 點的殺行程守門保留並修正（讀所有專案、同 session 放行縮小）。同時取代決議 032 第 2(a) 點末句「機器鎖（出貨全量排隊）不動」。

背景：
- 決議 026（2026-09-25）為了擋下兩個專案的出貨全量互相誤殺，裝了一把「整台機器一把」的鎖（`~/.constellation/leases/machine/holder.json`）：任何專案的 `--scope ship` 開跑前都要搶它，被佔就排隊；決議 032 把「整套測試只在頭尾跑」寫明，並註明「機器鎖不動」。
- 2026-10-03 使用者先問同專案是什麼情況才會發生、平常開發的 worktree 與 workflow 會不會碰到（原話見證據），查證結果：這把鎖只管 `--scope ship`（出貨前的整套完整測試），逐張票的驗證不受它管；整套測試一輪只在最後出貨時跑一次；平常開發的分身工作區與分工流程基本上碰不到它。會因此「同專案要等」的只有：同時開兩個對話做同一個專案、又剛好同時出貨。使用者接著提出機器鎖這個機制好像也可以拿掉（原話見證據）。
- 查證流程比較了「整個拿掉」「維持現狀」「改成同專案才等」：整個拿掉會同時失去兩個保護——同一個專案同時跑整套會互相刪除對方的測試資料、以及殺行程守門靠鎖的登記才知道哪些行程是別人的（決議 026 的兩次誤殺，正是因為看不出哪支全量是誰的）；維持現狀則是不同專案之間仍會無謂地排隊。推薦方案另經兩位對抗驗證者檢查並提出修正，已納入下列決定各點（尤其第 3 點兩個「提前放行」的縫、第 1 點的 worktree 與目錄連結正規化、第 2 點的提醒範圍）。

決定（使用者拍板「改成同專案才等」；實作限定為縮小鎖的範圍與修正守門，不新增機制、不新增設定欄位）：

1. **鎖的鍵從「整台一把」改成「每專案一把」**：鍵＝專案主工作樹根的雜湊（沿用 `gates/evidence.cjs` 的 `signingRoot`＋`repoRootToken`，與簽章綁同一套根：同一個 repo 的各個 worktree 算同一專案；目錄連結〔junction／symlink〕經 realpath 收斂成同一個字串；路徑大小寫與斜線寫法差異也收斂）。登記改成 `~/.constellation/leases/<鍵>/holder.json`，內容多一欄 `key`；`lease.mjs` 的各個函式以鍵為第一個參數，新增 `projectKey(root)` 與 `listHolders()`（掃 `leases/` 底下全部目錄），`list` 指令列出全部專案的登記。舊版 `leases/machine/` 目錄視為其中一份登記：`listHolders`、殺行程守門、開跑提醒都讀得到；舊登記沒有 `key` 欄位，專案鍵由它的 `root` 算出。`projectKey` 載入 `gates/evidence.cjs` 是用 `createRequire` 延遲同步載入，不是檔頭靜態 import：殺行程守門也讀 `lease.mjs`，靜態 import 會讓 `evidence.cjs` 壞掉時守門整支載入失敗、被 dispatcher 當成 fail-open 靜默放行，違反 DESIGN §11.5「模組壞掉不影響殺行程守門」；延遲載入後，載入失敗只讓守門的「同專案」判斷丟例外，`kill-guard` 把它當成不同專案而擋下（多擋，不放行）。
2. **`verify-runner.mjs`**：`acquireShipLease`、`isReentrantLease` 帶專案鍵（子孫重入判定只看本專案那一份登記）；排隊迴圈本體不動，只有「同一把鍵」的持有者會讓 `--scope ship` 排隊。`noteShipLeaseIfHeld` 改成讀所有專案的登記，在出貨全量開跑時與紅燈收尾時（逐票驗證開跑時照舊）：只要有別人的出貨鎖有人持有（活著，且不是自己或自己的祖先）就印一行提醒，沿用原句的結構，行動指引改成「若這次紅了，先等對方結束再單跑紅的那幾支判定」（原句寫「重跑一次判定」，用在出貨全量上會被讀成整套重跑，與決議 032 書擋節奏、與下面的假紅燈代價自相矛盾）；詞句從「機器鎖目前被別的出貨全量持有中……逐票驗證不受影響」改成「出貨鎖目前被別的出貨全量持有中……本次驗證不受影響」，因為同一句現在也用在出貨全量上。執行中的排隊／開跑／失效接手等其他訊息一字不動（含「機器鎖被佔用，排隊等待」），避免牽動條文引用的「開跑」訊號。
3. **`kill-guard.mjs`**：改成讀全部專案的登記取聯集，逐份檢查：「持有者已死」與「同 session」兩個分支原本直接 `return PASS`——只有一份登記時等價於「跳過這一份」，多份登記後會放行整條指令、蓋掉另一份仍活著的別人登記；兩處都改為只跳過這一份、繼續檢查下一份。同 session 放行的範圍縮小：只有 hook 輸入的 cwd 換算成專案根（再解回主工作樹根）後的專案鍵等於該登記的專案鍵，才跳過；否則同 session 也當別人處理（沒帶 cwd 退回守門行程自己的 cwd）。保護名單改成所有「別人持有」的登記裡的 runner pid 與子指令外殼 pid 的聯集；擋下訊息點名真正被殺的那個專案。
4. **文件同步**：`DESIGN.md`（§5 閘門 4 列、跨 session 出貨使用中燈段、殺行程守門段、§7 跨 session 共用同一台機器、§9 降級表、§10 目錄樹註解、§11.5 已知限制新增本決議的代價）、`README.md`、`.constellation/CONTEXT.md`（詞條改稱「出貨鎖／使用中燈」）、`SKILL.md`（等別人那條改「同專案的出貨鎖被佔用」；流程外子集退讓那句拿掉「照決議 026」的依附，保留「用自己經 `gates/serve.mjs` 起的站、只跑子集、不跑整套」；「機器鎖照舊」改「同專案的出貨鎖照舊、跨專案不排隊」）、`phase-ship.md` 步驟 1、`verification-playbook.md`（殺行程守門比對所有專案的登記）、`lease.mjs`、`kill-guard.mjs` 與 `evidence.cjs` 檔頭註解（`evidence.cjs` 的「誰用這支模組」補 `lease.mjs` 延遲載入一條）；`lease` CLI 輸出的三句「機器鎖」改稱「出貨鎖」；`phase-ship.md` 步驟 1 把「看 `lease list`」限定為「本專案排隊中才看、只看本專案那一份」。決議 026、032 舊檔只在檔頭加註被取代，內文不改。

代價（使用者拍板時已知，據實記）：
- **假紅燈機率上升**：兩個專案同時跑整套時，資源與記憶體吃緊造成假紅燈的機率比以前高；crm 的最終那趟若因此紅了，要整套重跑約 80 分鐘。對策是書擋節奏（決議 032 第 1 點）：紅了先等別專案的全量結束，再單跑紅的那幾支判定，單跑就綠算假紅燈；最終那趟仍要同一次完整全綠才能簽章。
- **記憶體不足被系統砍掉**：runner 被整支砍掉時收尾不會跑，crm 可能在正式庫留下殘留，下一輪開跑前須先還原。
- **殺行程守門的保護範圍沒有變大**：只保護登記裡的 runner 與子指令外殼兩個 PID，孫行程不在保護內（原有限制，本決議不補強）。
- **過渡期小縫**：本決議上線前就已開跑、仍登記在舊 `leases/machine/` 的行程，新版 runner 不會因它排隊（只提醒，守門照擋）；那批行程跑完這個縫就消失。**併回主線前須先確認沒有活著的舊登記**：用現行（舊）版本跑 `node gates/lease.mjs list`，若 `leases/machine/` 有活著的持有者就等它跑完再併——這個縫裡新版提醒句寫「本次驗證不受影響、照跑」，與實際相反（新舊兩邊會同時對正式庫跑整套，正是這把鎖原本要防的互刪）。
- **「同專案」的界線＝同一個 git repo 及其 worktree（出貨前審查補記：拍板後才釐清的範圍界線，不是拍板時已知的代價）**：另一份 clone 不算同專案，即使內容與指令完全相同（例：`crm-system` 與 `crm-system-gcp` 根 commit 相同，但是兩份獨立 clone，鍵不同）；用 `--separate-git-dir` 建的 repo，其 worktree 會退回以 worktree 自己的路徑當鍵，跟主工作樹不同把（`signingRoot` 原有限制）。兩份 clone 若共用同一顆資料庫，要自己錯開出貨時段；本決議不加機制。

原因：
- 使用者的實際使用方式（一個專案只開一個對話）下，這把鎖的排隊作用幾乎用不到，卻讓不同專案之間無謂地互等；但它防的兩件事——同專案同時跑整套互刪測試資料、把別人的全量當孤兒殺掉——是真的出過事的，不能連它一起拿掉。每專案一把是兩者的交集：只在確實會互相踩到的範圍內排隊。
- 殺行程守門必須讀所有專案的登記：鎖縮小後，別的專案的全量不再被排隊擋在前面、更常同時在跑，守門護的範圍不能跟著縮。「已死」「同 session」兩個分支改成跳過這一份，是因為多份登記後原本的提前放行會讓另一份活著的登記失去保護。

與既有決議的關係：
- **取代決議 026 第 1–2 點的範圍**：單一 `machine` 鎖與對整台機器排隊，改為每專案一把；026 第 3 點守門保留，改讀全部專案；第 4 點三處條文的措辭同步修訂；026「第二版清單」不動。
- **取代決議 032 第 2(a) 點末句**：「機器鎖（出貨全量排隊）不動」改為「同專案的出貨鎖照舊、跨專案不排隊」；032 其餘各點不變，書擋節奏（第 1 點）正是上面假紅燈對策的依據。
- 決議 020（只殺自己登記的、失效只改名不殺持有方）與 025（歸屬證據）不變。
