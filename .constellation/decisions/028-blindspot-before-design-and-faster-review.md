# 028 盲點審併回畫面開工前收斂＋複查輪改喚回加速：推翻決議 024 D1 時機、修改決議 022②

背景：以 AI_project_hub 本輪（19 題訪談、第 1 輪就有 13 題動到畫面）與 crm-system 一輪（決議 322，用 SendMessage 喚回同一位審查員複查）的實測結果，重新檢視決議 024 D1「盲點審不擋畫面製作、背景跑、5b 前收斂」這套時機規則是否划算，逐題請使用者拍板（即本決議）。

決定：

- **A（時機）**：大流程獨立盲點審一律跑到收斂（或使用者喊停）並在 `grill-close.md` 檔尾寫好收斂行後，才進 design（需要 UI）或 weave（不需要 UI）。取代決議 024 D1 整套「不擋畫面製作、背景跑、畫面空檔插問、會動畫面的題優先問、送審範圍不含畫面階段新落的決議、〔畫面〕標題前綴」時機規則。
- **B（複查加速）**：盲點審改成分工制——第 1 輪由新的獨立審查員（各視角各一）看決議全集，首輪不設條數上限並列情境角度；**必須用 Agent 工具起（每個呼叫帶 model），不用 Workflow**（Workflow 起的 agent 無法用 SendMessage 喚回），並把各審查員的名字或 agentId 記在主線看得到的地方。第 2 輪起（複查輪）用 SendMessage 喚回同一位審查員（各視角各自喚回自己那位），訊息附本輪變動清單（新增與修改的決議檔、主線對上一輪每條發現的處置：落成哪條決議／指揮官直接修了什麼小毛病／不採納與理由），要求它①重讀決議全集、②逐條自行判斷主線的處置是否真的解決了它原本的疑慮（不把處置說明當事實接受）、③再掃一次新盲點與變動造成的新矛盾；不設每輪條數上限。改派新審查員的時機：SendMessage 沒有續用成功、審查員回報記不清先前內容、換 session（一律視為叫不回）、或同一位複查者接手後累計滿 8 輪仍未收斂（中途插一次新審查員看全集抽查，這輪算新人第 1 輪，之後由這位新審查員接續複查）；改派時連續零阻擋輪數從零重算。收斂：複查輪連續兩輪零阻擋級後，派一位完全沒參與過的新審查員看決議全集做最終確認——不看訪談對話、不看先前審查員的報告與主線處置說明；最終確認零阻擋級才真正收斂、寫收斂行；有阻擋級就照常問使用者／落檔，回到複查輪（由最終確認那位接續當複查者），再連續兩輪零阻擋級後再派一位新人最終確認。使用者喊停行效力同收斂行，隨時可停。Codex 端（沒有 SendMessage 喚回、沒有 Agent 工具）：每輪照舊由新審查者看全集，收斂標準仍是連續兩輪零阻擋級，沒有最終確認這一步。
  - **落地規格**（依可行性查證修正，屬執行細節，不改變使用者核准的本質）：改派時機、8 輪門檻、最終確認「完全沒參與過」的定義，是指揮官依 SendMessage 實際限制（無法保證每次都續用成功）補上的操作細節。**與彈窗字面的差異**：B-1、B-2、B-3 彈窗字面是「同一位老師只看改過的地方」，但落地規格要求複查者①重讀決議全集——這是指揮官依 crm 322 實例（每次續用都要求重讀全文）與決議 022②「否決縮小審查範圍」的既有立場補上的：變動清單只是複查的重點提示，不是限制審查範圍，避免複查者因為只看改過的地方而漏掉舊決議之間的新矛盾。同理，「首輪必須用 Agent 工具起、不用 Workflow」與「記下審查員名字／agentId」彈窗原文也未明講，是指揮官依 SendMessage 只能喚回用 Agent 工具起的對象這個技術限制補上的操作細節。以上三點雖與彈窗字面不同，但都是為了不改變使用者核准的本質（複查要更快、但不能因此變得不可靠）——落地時建議主線向使用者一句告知這個差異。
  - **保留不變**：決議 024 D2（阻擋級／小毛病分級、小毛病指揮官直接修不送審、連續兩輪零阻擋級）、收斂行與使用者喊停行、換 session 接回、舊規則 grill-close 補行例外、024 D3、D4。
  - **連帶修訂**：決議 022②（使用者當時選「盲點審維持現行做法」）——本決定經使用者彈窗核准，改變每輪的審查方式（首輪起法、複查輪喚回、改派時機、最終確認）。

原因：

- A：使用者對第 1 題的回覆就已經覺得「還是會一樣一直改畫面」，追問兩輪後又指出丟 Claude Design 設計時「來回改動很麻煩且浪費 token」（使用者原話；「雲端一來一回，改一次就要重新推一次」是指揮官對這句話的技術性解讀，用來說明為什麼雲端設計的來回成本比本地改 code 更高）。hub 本輪邊審邊做讓畫面重做 3 次（37.3／30.3／24.9 分），重做 55.2 分鐘、約 115 萬 token，占畫面工時 59.7%；第 1 輪 19 題中 13 題動畫面，代表決議 024 D1 賭的「盲點審新題大多不動畫面」在這個案例不成立。故收回 D1 整套時機規則，改用「全部審完才開工」換取「畫面只做一次」。024 當初用 crm 0915 第 42 輪「53 條中 2 題」估代價，取樣偏晚，低估了盲點審新題動到畫面的機率。
- B：A 的代價是盲點審整段被放回畫面開工前的關鍵路徑上，勢必拉長開工前等待——所以同一輪一併討論怎麼壓縮複查輪耗時。crm 決議 322 那個案例**顯示**「喚回同一位審查員複查」比「每輪都換新人重新看全集」快很多。使用者聽完弊端說明（同一位審查員可能被處置說明牽著走而有盲點、最後仍要多繞一圈讓新人驗證、速度證據只有一例且該例有每輪條數上限）後仍選擇要改，因為新增的「最終確認」正是用來兜住「被帶著走」這個弊端；不設條數上限也是為了修正 crm 322 那個案例的取樣限制。

代價：

- A 與 B 是綁在一起的取捨：A 把盲點審整段放回畫面開工前，靠 B 壓短複查輪來撐。
- 每次收斂至少多一次新審查員看全集的最終確認——對照 hub 本輪每輪新審查員 30–73 分、crm 0915 每輪約 15–24 分，最終確認本身無速度證據。
- 最終確認若挑出阻擋級發現，需再繞兩輪複查＋一次新人最終確認。
- 喚回的審查員會被主線的處置說明帶著走——以「要求逐條自行判斷」與「最終確認派完全沒參與過的新人」兩道機制兜住，消不掉、只能稀釋。
