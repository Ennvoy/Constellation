# 026 跨 session 共用一台機器：機器鎖排隊＋殺行程守門，取代口頭協調

> 第 1–2 點的「整台機器一把」已 **superseded by 033**：出貨鎖改成每個專案一把，只有同專案（含同 repo 的其他工作區）的出貨全量才排隊，跨專案不排隊；第 3 點的殺行程守門保留，改為讀所有專案的登記並修正兩個提前放行的縫。其餘各項仍有效。

背景：09-25 凌晨，crm-system（round-0915）與 ai-project-hub 兩個獨立 session 同時把出貨全量壓上同一台機器，全靠 SendMessage 即時聊天協調，暴露出「靠人／靠訊息記得」撐不住的兩個洞。

02:18 crm 啟動 round-0915 出貨全量（`verify-runner.mjs --scope ship`，PID 47592）；02:25 hub 的出貨子代理啟動一支指令列完全相同的全量（兩個專案共用同一支母本 `verify-runner.mjs`），02:28 把 02:18 那支（其實是 crm 的）當成自己的孤兒行程 `taskkill` 掉。crm 發現 runner 無聲消失、log 0 位元組，SendMessage 問 hub 是不是誤殺，hub 承認、通知自己子代理「不得再碰 crm 的路徑與埠」——但這通知只是叫醒一個新分身接手，原本正在執行 kill 的那個分身照樣殺完。crm 02:45 重啟第六趟（PID 27848），02:54 同一個子代理**第二次**殺掉它；這次不是認錯行程——它自己的 journal 寫著「PID 27848 (unrelated session…) is still competing for resources… I'll clear that one out」，是明知道那是別的 session、仍決定清掉。訊息攔不住已經在執行的行程，只有機械擋得住。

crm 這次要求 hub 真正的硬停止；hub 改用 `TaskStop` 停掉整個出貨子代理與 workflow（不再只靠訊息勸阻），並主動提出「這輪我先不跑，等你跑完再開」——這是後續值得留住的好做法：**先跑到的優先，另一方主動退讓、只做不衝突的輕活**。hub 沒有乾等：用 `CronCreate` 排一次性鬧鐘（後隨 crm 更新的 ETA 從 06:04 改到 06:06），期間先做被允許、不衝突的 T-529 補驗小工作，只用自己的 3011 站、不碰整套 vitest／playwright。06:06 排程觸發、07:17 輕量段跑完彙報後，hub 進入完全閒置——**這次沒有再排新的鬧鐘，也沒有訂閱 crm 的閒置通知**，只等一句「07:30 前後」的口頭 ETA。crm 這邊第七趟全量雖然全綠，但紅軍抓到兩條權限漏洞要修，加上 08:30–11:00 是正式庫抓取器的上傳窗不能碰，實際完工時間一路後延；crm 自己 09:57 起用 `CronCreate` 排了 11:03 的喚醒（並在 prompt 裡寫好「醒來還沒收到通知就每 5 分鐘輪詢到 12:00」的備援），隨後同樣進入閒置。

hub 這邊卻沒有任何機制在等——07:17 之後，直到 **使用者在 09:55:53 手動打「現在？」把它叫醒**，中間空等了 158 分鐘，沒有任何背景的東西會自己結束並通知它。被叫醒後 hub 查行程／連接埠，看不到 crm 的 runner 也看不到 3000 埠，才自行推斷「crm 應該跑完了」（不是收到確認），開始自己的全量；52 分鐘後（比自估的 1～2 小時快很多）在 10:48 主動推播「hub 全量結束」給 crm，比 crm 自己排的 11:03 提早 15 分鐘——crm 的 cron 準時觸發時已經收到這則訊息，跳過輪詢分支直接開跑第十趟。兩次誤殺另外讓 crm 多花約 15 分鐘清正式庫殘留＋40 分鐘白跑，加上 02:30～02:58 間近十封協調訊息。

決定：採納「機器使用中燈」的修正版最小版本——新增跨 session 的機器鎖工具、runner 出貨全量自動排隊、新增殺行程守門、修訂三處條文，把「先跑到的優先、另一方排隊」做成機器預設值，不再靠聊天訊息即時談。具體：

1. **`gates/lease.mjs`**（工具，非閘門）：單一 `machine` 資源鎖，`~/.constellation/leases/machine/holder.json` 用 `wx`（檔案已存在即失敗）建立，內容含專案根、session、runtime、pid、啟動時間、用途、預估結束時間；失效判定沿用決議 020「PID＋建立時間」的手法（查得到卻已死才作廢，不猜、不殺持有方的行程），只提供 `list` 指令。
2. **`verify-runner.mjs` 的 `--scope ship`**：開跑前自動取鎖，被佔就排隊等待、輪到自動開跑，跑完照常觸發背景完成通知；逾時（`--max-wait` 預設 4 小時）以代碼 3 結束、不計入斷路器。
3. **新閘門 `gates/kill-guard.mjs`**：掛在既有 `pre-tool-use.mjs` 上，擋下「把別的 session 持有機器鎖的行程當孤兒殺掉」與「按名稱整批殺」，命中時講明是哪個專案的全量、要停請走 SendMessage——這是新增的硬性擋下，依 `DESIGN.md` §5 末段「加閘門需回本文件修訂」，本次修訂已使用者核准（拍板脈絡見下方證據）。
4. **條文三處**：`phase-ship.md` 步驟 1（主 session 用背景執行起 runner、排隊中可停開跑後不准砍、開跑後看一次燈）、`verification-playbook.md` 新增「跨 session 共用這台機器」（只殺自己起的、閘門擋別人的、SendMessage 只講燈表達不了的事）、`SKILL.md` 補一條通則（等別人時背景要有東西會自己結束並叫醒你，沉默不算同意）。

原因：09-25 這一輪真正的失敗點不是「沒有協調」，是協調完全靠自然語言即時談、沒有機器可查的鎖——第一次口頭通知攔不住已在執行的殺行程，第二次是明知故犯；hub 07:17 之後的 158 分鐘沒有任何背景機制會自己結束並叫醒它，只能靠使用者手動介入。這兩個洞只有把「排隊」與「誰佔著」做成行程綁定的機器狀態才根治得了，光靠寫進條文要求「記得通知」「記得排鬧鐘」，明天換一組沒讀過教訓的 session 一樣會重演。

第二版清單（本次不做，留待更多證據或需求出現才加）：`lease run`／`lease wait`（給 runner 以外的重活包鎖）、先到先排的隊伍目錄（最小版本改用單純搶鎖）、Codex 的 `--no-wait` 與沙箱寫入實測、`db:<key>` 讀寫租約（要先定好跟 `machine` 鎖的取鎖順序，避免死鎖）、機器記憶體下限、時段限制（如正式庫上傳窗）、session 開場注入「機器現在誰佔著」。
