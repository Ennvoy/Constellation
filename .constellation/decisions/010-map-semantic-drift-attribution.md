# 010 語意段落補第三道：來源歸因（洞 2），並清掉 crm 的廢棄同步標記

背景：決議 009 只修了地圖的路徑類過期（洞 1／洞 3），留下洞 2——MAP.md 第二～四段（資料表口徑、已知缺口、地雷）記的是語意，佔 crm-system 那份地圖 251 行中的 223 行（89%），「改內容不改檔名」時前兩道全盲。使用者實際撞到的正是這一類。同時 crm 的 MAP.md 檔頭仍留著決議 009 已廢除的 `constellation-map-synced-at` 標記，程式不再讀取，留著只會誤導人。

決定：新增第③道**語意漂移歸因**——機器讀不懂語意，改問一個它答得出的問題「這條的依據還是原樣嗎」。第二～四段的條目幾乎都寫了自己的來源（migration 檔名、腳本路徑、報告檔），拿 `git diff --name-status baseline..HEAD` 的變更集合比對每一行提到的來源，命中就點名那一行；模組索引段排除（歸①②管），已被①判定為死路徑的行不重報。三層防誤報：行內若已寫出可從根解析的路徑就以路徑為準、**只有完全沒指名路徑的行才退回裸檔名比對**（跨目錄同名檔會撞）、glob 樣式退一層取父目錄（`_lib/stats-*.ts` → `_lib`）。條文面同步補兩處：ship 收尾把「校對」寫成「語意三段逐條複驗，優先看閘門點名的行」，phase-build 補「票補掉的缺口／拆掉的地雷當下就刪那條」——**過時的缺口留著比沒寫還糟，下一輪會照著它繞路或重做已完成的事**。另清掉 crm MAP.md 的廢棄標記（只動那一行，不碰使用者未提交的其他修改）。

原因：洞 2 是「機器測不出語意」的硬限制，繞不過去，但可以退一步縮圈——把「複驗兩百多行」壓成「複驗三四行」，讓 ship 的逐條複驗便宜到真的做得下去。③是可能級提示（來源動過不等於描述就錯），與①的確定級刻意分開表述，避免可能級的雜訊稀釋確定級的可信度。預防面（build 當下就刪）比偵測面更根本，成本也更低。

證據：使用者指示「修洞2+清註解」。當時依據：三輪實測且**兩次被真實資料打臉後才收斂**——(1) 第一版用裸檔名比對，crm 上第 191/192 行誤命中（那兩行講 `app/api/import/_lib/activity.ts`，真正變更的是 `packages/contracts/api/activity.ts`），加「行內有真路徑就不退回裸檔名」後消失；(2) 改用全行掃描後，`app/api/import/_lib/stats-*.ts` 被切成 `stats-` 前綴誤報「不存在」，加 glob 父目錄處理後歸零。最終 crm 真實資料 223 個可掃行只點名 3 行（1.3%），逐條核對皆為真命中（`repo.ts`「只有讀取端」、`packages/contracts/api/activity.ts` 的重疊檢查、契約 README 檔案數）。scratchpad 造純 M 變更（三檔改內容、檔名零變動）驗證洞 2 本體：第②道完全沒報，第③道精準報 3 行，模組索引段／「同上」／未動過的／承前省略片段全部零誤報。效能實測分冷熱兩種：冷快取下三版對比 v0 7021ms → v1 8216ms → v2 9128ms（增量約 2.1 秒，即憲法記的代價，屬最壞情況）；熱快取下整支閘門只要 2388ms，三次 git 合計 1453ms（status 504／log 575／diff 374）。已把②③原本各跑一次的 `git diff` 合併成一次，省下約 374ms。
