# 009 地圖過期偵測改零維護：基準自動取得＋死路徑精準點名

背景：使用者在 crm-system 撞到 MAP.md 裡的過時資訊，回頭問「能不能從機制上避免」。實測該專案開場注入，警示其實**有**正常出現（「上次同步 bff2ff3 之後有 27 個檔案增刪改名」），但擋不住踩坑，挖出四個洞：①`constellation-map-synced-at` 靠人手更新，該專案標記停在 8/4 而地圖內容之後改過三次，警示從此永久常亮＝變背景雜訊；②偵測維度對不上過期維度——閘門只看檔案增刪改名，但 MAP.md 252 行裡只有 28 行（11%）記路徑，其餘 215 行（資料表口徑 133、缺口 35、地雷 47）是語意，同期 193 個純內容修改完全在盲區，憲法「地圖只記路徑」的立論在自己的第二～四段不成立；③警示只說「27 個檔案動過」不指哪一行，核對成本高到必然被跳過；④BACKLOG.md 在憲法外、零機制守。

決定：本次只修 ①③（使用者拍板選項一），②④留著不動。①**廢除人工 sha 標記**，過期基準改由閘門用 `git log -1 -- .constellation/MAP.md` 自動取得「地圖最後一次被 commit 的 commit」；地圖有未提交改動時視為正在校對，第②道不提示。③**新增死路徑點名**：把地圖裡寫到的路徑逐一比對檔案是否還在，不在就報「第 N 行 `xxx` 已不存在」。零誤報靠兩道過濾——去尾斜線後仍需含 `/`（擋掉指令、表名、單檔名、`overview/` 型承前省略），且**頂層片段必須真的存在於 repo 根**（擋掉 `[id]/_lib/`、`admin/tokens/`、`.../callcenter/projects/` 型多層承前省略）。動 DESIGN.md §4、gates/session-start.mjs、phase-ship.md 三處。

原因：任何要人手動維護的同步點都有同一個結構性缺陷——要求「改地圖」與「改標記」每次都同時做到，漏一次基準就永遠停在過去；而天天亮的警示等於沒亮。死路徑檢查則是全套機制裡唯一「確定、指得到哪一行、修完就熄」的檢查，正好補上洞③的無指向性。②沒修是因為語意過期無法用機器測（只能靠 ship 逐條複驗、無機器保證），憲法已改為據實載明這個缺口，不假裝有守。

證據：彈窗「先修哪個」使用者選「零維護基準＋精準點名（推薦）」。當時依據：在 crm-system 實跑 `gates/session-start.mjs` 三次——改前警示常亮；第一版規則報出 7 條**全是誤報**（承前省略片段），加上「頂層須存在」後歸零；scratchpad 最小 repo 正向驗證，8 種樣本中精準命中該報的 2 條（`app/gone.tsx`、`lib/legacy/`）、6 種干擾樣本零誤報，第②道自動取到基準 `8f2f4d0` 並報出其後的 1 個刪除；修好地圖後兩道警示在「未 commit」與「已 commit」兩種狀態下皆熄滅。
